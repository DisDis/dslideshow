# Производительность backend

Действующие контракты файлового индекса, случайного прохода, SystemInfo
и освобождения ресурсов. Команды общего прогона — в
[README backend](../backend/README.md#локальные-проверки).

## Случайный проход и индекс файлов

`DiskStorage` выбирает случайный элемент из ещё не выбранных, меняет его местами
с последним доступным и сдвигает границу доступной части массива. Сдвигов
остальных элементов нет: выбор занимает O(1), полный неизменный набор — O(N).
Заранее выбранный `next` уже считается выбранным в текущем цикле. При одном
файле `current` и `next` могут указывать на один файл; запрета повтора на границе
двух циклов нет.

Обход каталога асинхронный, рекурсивный. Тип `File`, полученный от `Directory.list`,
используется без дополнительного `typeSync` на каждой записи. Работа порциями
передаёт управление event loop; это относится также к пропущенным записям.
Правила следования симлинкам остаются прежними. Служебные временные файлы
загрузки не публикуются в индексе и не удаляются индексатором.

Новый индекс строится отдельно и становится рабочим целиком. Одновременные
запросы объединяют пересборку; файловые события во время обхода требуют повторной
проверки. Поздний результат после `release()` не изменяет состояние. Ошибка
обхода сохраняет предыдущий рабочий индекс вместо публикации частичного списка.
Операции `next()` выполняются последовательно, пара `current/next` изменяется
после подготовки результата.

Если состав не изменился, остаток текущего прохода сохраняется. После изменения
удалённые URI исключаются из выбора, новые могут попасть в оставшуюся часть
прохода, а уже выбранные URI не возвращаются до следующего цикла. Замена
содержимого по прежнему пути не даёт этому URI дополнительного показа в цикле.
Новые файлы могут продлевать цикл; постоянный приток файлов не гарантирует
завершения цикла. Память для учёта выбранных URI сохраняется до его окончания.

Watcher служит подсказкой для актуализации, а не файловой транзакцией.
На Linux рекурсивное наблюдение через `Directory.watch` не поддерживается;
обход на границе цикла сохраняется как запасной способ обнаружения изменений
во вложенных каталогах. Между получением индекса и открытием файла внешняя
программа всё ещё может удалить или заменить файл.

Контракт пустой медиатеки и восстановление её frontend остаются в
[общей очереди](plans/roadmap.md#медиатека-и-длительная-работа).
Текущий индекс не добавляет экран пустоты, новые RPC-команды или аварийное
удаление оставшихся `.part`.

## Сбор SystemInfo

Динамический снимок собирается по запросу. Одновременные запросы используют
один выполняющийся сбор; готовый снимок переиспользуется в течение одной
секунды по монотонным часам. Возврат кеша сохраняет исходный `lastUpdate`.
Обновление CPU/OS при инициализации также объединяется, сетевой кеш сохраняет
минутный интервал. Новых периодических таймеров нет; штатный frontend по-прежнему
запрашивает сведения при старте и раз в минуту.

На Linux `/proc/loadavg` и `/proc/cpuinfo` читаются асинхронно без `cat`.
По решению пользователя `/proc/meminfo` используется сразу, без проверки версии
`free`: `memUsed = MemTotal - MemAvailable`, swap — разность общего и свободного
объёма, единицы остаются КиБ. Отсутствующие поля или ошибка чтения оставляют
запасной сбор через `free`.
`uptime -p` сохранён ради совместимости строкового формата, включая недели
и завершающий перевод строки. Настраиваемый `sensorsScript` продолжает возвращать
произвольные пары `name=value`, включая температуру, RPM и текстовые значения.
Чтение штатного тахометра Raspberry Pi 5 и диагностика частичных ошибок скрипта
описаны в [руководстве системных датчиков](sensors.md).

Системные команды имеют предел 3 секунды, затем TERM и KILL через секунду,
а их суммарный stdout/stderr ограничен 64 КиБ. Linux-исполнитель использует
уже установленный `setsid` для отдельной группы процессов без дополнительного
процесса-обёртки. Отсутствие утилиты даёт ошибку команды и прежние значения
по умолчанию. Таймер срока выполняется в event loop: при его блокировке
завершение команды задержится до возобновления обработки событий. Отмена
действительно посылает сигналы группе и ожидает выход и закрытие потоков.
Проверки на настоящих локальных процессах включают дочерний процесс,
игнорирующий TERM, удержание pipe после выхода родителя и закрытие сервиса
во время запуска. Этот этап не устанавливает системные утилиты.

Формат `SystemInfo`/`UpdateInfo`, единицы, типы датчиков и прежнее поведение
при недоступных измерениях сохранены по решению пользователя. В частности,
этот этап не вводит nullable-поля, новые признаки доступности или возврат
последнего удачного значения вместо прежних значений по умолчанию. Дальнейшее
уточнение контракта ошибок метрик потребует отдельного согласования.

## Логи и освобождение ресурсов

Подробные записи успешных RPC, их длительности и полные WebSocket-сообщения
перенесены на `FINE`; сообщения об ошибках, подключениях и состоянии сервисов
сохранены. При обычном `INFO` форматирование подробностей не выполняется.
Для диагностики можно задать `log.hw_frame` и `log.web` равными `FINE` в
существующей конфигурации.

Ограничение прогресса upload/OTA до четырёх обновлений в секунду уже было
реализовано предыдущим этапом и здесь не меняется. Закрытие аппаратного сервиса
ожидает освобождения Storage и SystemInfo; завершение унаследованного
`GPhotoStorage.release()` ожидает базовое освобождение индекса.
Защита `init/release` также запрещает создание таймера Google Photos после
закрытия во время начального обхода. Ошибка уже выполняющегося запроса SystemInfo
передаётся штатным `ErrorResult` с исходным RPC id; существующий тип добавлен
в обе стороны backend-сериализатора и проверен через настоящий транспорт.

## Локальные проверки

Из корня репозитория, без обновления зависимостей:

```bash
(cd backend && dart analyze && dart test --concurrency=1)
(cd common && dart analyze && dart test)
```

HTTP-регрессиям backend нужен доступ к локальным сокетам. Запрет сокетов
в sandbox даёт `Operation not permitted` и не является результатом проверки
сетевого поведения.

Регрессии используют временные каталоги, управляемые потоки, часы и исполнители
команд. Они проверяют полноту случайного цикла, согласованность пары, конкурентные
запросы, изменения и ошибки обхода, поздние результаты, очистку ресурсов,
сроки кеша и завершение системных команд. Пороги быстродействия в unit-тестах
не используются.

Локальные измерения и их инструменты находятся только в `benchmarks/`;
команды запуска приведены в [README стенда](../benchmarks/README.md).
Сохраняются исходники, SDK, конфигурация, сырые результаты и идентификаторы
baseline/candidate. Время первого выбора включает индекс и выбор элемента;
его нельзя называть чистым временем обхода. Throughput и отзывчивость
проверяются разными сценариями, чтобы цепочка немедленно завершённых Future
сама не подменяла измеряемую блокировку event loop.
