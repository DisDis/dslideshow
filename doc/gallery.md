# Галерея: миниатюры, загрузка и версии кеша

Актуальность: сверено с кодом 29.10.2026. Точка входа —
[README config_app](../config_app/README.md). Галерея и управляемый загрузчик
реализованы; генератор миниатюр использует FFmpeg/JPEG. Поведение прежней
реализации и исходные измерения сохранены в
[baseline-исследовании](../benchmarks/reports/gallery-implementation-2026-10-26/baseline-analysis.md).

## Поведение панели

Сетка получает серверные квадратные JPEG-миниатюры 256, 512 или 1024 px по
размеру плитки и DPR. Доступные варианты задаются enum в конфигурации.
Фото, анимации и видео обрабатываются одним FFmpeg без ffprobe. EXIF учитывается,
прозрачность накладывается на фон (по умолчанию `#202020`), качество JPEG — 60.
Для анимации/видео фильтр `thumbnail` выбирает представительный кадр из первых
30 кадров. Он сравнивает гистограммы этой группы, не ищет лучший кадр во всём
ролике. Размер группы настраивается. Перед сравнением кадры уже уменьшены.

Оригиналы не перекодируются: fullscreen, zoom, GIF-анимация и фоторамка используют
исходные файлы. Плитка видео до запуска показывает JPEG-постер через общий
загрузчик миниатюр; нажатие запускает прежний Web/Linux-плеер с оригиналом.
На платформе без плеера постер остаётся доступен.

Один загрузчик фотографий на подключение обслуживает сетку и fullscreen.
Приоритеты: fullscreen → видимые плитки → prefetch по одной соседней строке
с каждой стороны viewport (не более одной активной prefetch-передачи).
Одинаковые запросы объединяются. Уход последнего потребителя отменяет очередь
или HTTP-запрос, включая чтение тела; слот освобождается после завершения
передачи/отмены. При открытии fullscreen сетка освобождает свой спрос, при
возврате пересчитывает viewport. Декодирование имеет отдельную очередь;
полученный ImageStream используется для показа без второго resolve/decode.

Обычное обновление перечитывает каталог и сохраняет версии неизменившихся
файлов. Ошибка обновления оставляет прежний список видимым. Ответ 409 на
изображение вызывает объединённую сверку каталога; смена версии обновляет и
открытый fullscreen. Удалённая запись показывает ошибку. Автоматических
повторов загрузки изображений нет: повтор выполняется явным действием пользователя.
Ошибка миниатюры не запускает массовую загрузку оригиналов.

Смена сервера, кода авторизации или разрыв соединения закрывают прежний scope:
его поздние ответы не попадают в новую сессию. Старый backend поддерживается
через `/list` только при 404/405 нового catalog endpoint. Ошибки авторизации,
5xx, неизвестная schema и повреждённая thumbnail policy показываются как ошибки.
В legacy-режиме обновление меняет cache key оригиналов, поскольку старый сервер
может отдавать их с длительным HTTP-кешированием.

## API и инвалидация

Все маршруты используют существующий код доступа `<code>`.

| Запрос | Результат |
| --- | --- |
| `GET /cache/<code>/v2/catalog` | JSON schema 2: server ID, catalog revision, capabilities, thumbnail policy и typed entries |
| `POST /cache/<code>/v2/catalog/refresh` | JSON `{operationId, mode}`; `mode` — `scan` либо `forceInvalidate`; новый снимок |
| `GET/HEAD /cache/<code>/v2/thumbnail/<mediaId>/<sourceRevision>/<policy>/<bucket>` | JPEG, policy из каталога, bucket из настроенного enum; ленивое создание |
| `GET/HEAD /cache/<code>/get/<path>?rev=<sourceRevision>` | Оригинал с проверкой версии; прежний URL без `rev` продолжает работать |

`kind` различает фото, GIF, видео, каталог, неподдерживаемый и неизвестный тип.
`thumbnailPolicy` содержит `version=4`, `revision` (SHA-256 параметров рендера)
и `sizes` (существующий числовой wire-формат enum). Сегмент `<policy>` имеет вид
`4-<revision>`; клиент строит его из каталога. В hash входят качество, фон,
размер группы кадров и доступные размеры. Настройки очередей/кеша не меняют hash.
Оба значения входят в серверные и клиентские cache keys. Изменение настроек
после перезапуска даёт новый URL, сохраняя версии оригиналов и выбор элементов.
Старые производные не мигрируются: прежние файлы с SHA-256 digest удаляются
при восстановлении кеша.
Устаревшая policy возвращает 409, некорректные параметры — 400.
Клиент не определяет вид медиа по URL миниатюры. Каталоги остаются в списке;
новая навигация по папкам не добавляется.
JSON legacy `/list` теперь корректно экранирует имена и строится асинхронно.

Идентификаторы и поколения источников хранятся в `<images>.gallery/` рядом с
каталогом оригиналов, вне его дерева. Например, для `/data/images` состояние —
`/data/images.gallery`, производные — `/data/images.gallery/thumbnails`.
Пользователю службы нужны права записи в этот каталог. Потеря или повреждение
метаданных создаёт новый namespace и не переиспользует прежние версии.
Удаление и обнаруженное повторное создание файла дают новую идентичность.

Web upload и GooglePhoto публикуют только полностью записанные staging-файлы
через атомарное переименование. Общий журнал публикаций работает между isolates,
сохраняет dirty-состояние перекрывающихся операций и меняет версию даже при
совпадении размера/времени файла. Незавершённые публикации восстанавливаются
после смерти владельца; на Linux проверяются PID и время старта процесса.
Зарезервированные `.upload-<32hex>.part` и производные не попадают в каталог
медиа. GooglePhoto ожидает окончания тела и закрытия writer, освобождает
HttpClient и отменяет загрузки при shutdown.

Внешние правки обнаруживаются сканированием stat-метаданных, событиями файловой
системы и периодической сверкой при чтении каталога (не чаще необходимости;
максимальный возраст снимка — 30 секунд). Управляемые публикации дополнительно
проверяются через общий publication token, в том числе во вложенных папках.
Внешняя замена с сохранением всех stat-метаданных может остаться незамеченной.
После такого импорта требуется явный `forceInvalidate`; обычный Refresh его
не выполняет. Операция меняет общий content epoch и создаёт новые производные
только по последующему спросу, без eager-обработки коллекции.

Пример сервисной инвалидации; `GALLERY_BASE` — адрес вида
`http://host:port/cache/<code>`. Для новой операции нужен новый ID; повтор той же
отправки сохраняет ID (сервер помнит последние 64 завершённые операции):

```sh
gallery_operation_id="$(python3 -c 'import uuid; print(uuid.uuid4())')"
curl --fail-with-body -X POST "$GALLERY_BASE/v2/catalog/refresh" \
  -H 'Content-Type: application/json' \
  --data "{\"operationId\":\"$gallery_operation_id\",\"mode\":\"forceInvalidate\"}"
```

Отмена ожидания POST не отменяет уже применённую инвалидацию. Ошибки API
типизированы: 400 — запрос, 403 — доступ, 404 — отсутствует, 409 — версия,
415 — неподдерживаемый источник, 429 — бюджет занят, 503 — сервис недоступен.
Для перегрузки возвращается `Retry-After`.

Производные имеют strong ETag по байтам и `private, max-age=604800, immutable`;
оригиналы — `private, no-cache` и слабый stat validator. Source revision не
является strong ETag. Поддерживаются HEAD, 304, одиночный Range, If-Range и 416.
Range применяется к GET; HEAD игнорирует его и возвращает длину полного файла.
If-Range допускает частичный ответ только с точным strong ETag. Дата и слабый
ETag консервативно дают полный 200: stat-метаданные не доказывают отсутствие
нескольких замен за секунду. Несколько диапазонов также дают полный ответ.
CORS включает OPTIONS и
разрешает читать validators, Content-Length/Range и Retry-After. Даже готовая
производная проверяется на актуальность источника перед выдачей.

## Бюджеты и ограничения

Начальные лимиты — параметры реализации, их пригодность для RaPi5 ещё не
подтверждена аппаратным сравнением.

| Ресурс | Значение по умолчанию |
| --- | --- |
| Клиентские фото HTTP | 4 активных тела; prefetch занимает максимум 1 слот, включая отмену; timeout 30 с |
| Клиентское тело / сумма активных encoded payload | 200 MiB / 256 MiB, включая удерживаемые ready leases |
| Декодирование клиента | 2 активных first-frame decode |
| Web encoded LRU | 24 MiB / 128 объектов в памяти |
| Native encoded LRU | 512 MiB / 2048 объектов в `getApplicationCacheDirectory()/gallery-encoded-v1` |
| Каталог backend | 64 выполняющихся/ожидающих операций суммарно; один scan за раз |
| Thumbnail workers / очередь / ожидающие consumers | 4 / 8 / 32 |
| Thumbnail disk LRU | 512 MiB / 2048 объектов |
| Negative cache генератора | 64 записи, TTL 3 с |
| Источник генератора | До 200 MiB и 64×1024×1024 пикселей |
| Результат генератора | До 8 MiB, сторона до 1024 px |
| Worker / ожидание consumer | 20 с / 30 с |
| Серверная выдача файлов | 12 тел, включая оригиналы и видео; слот удерживается до consumer done/cancel |
| Каталог клиента | Timeout 20 с, JSON до 64 MiB |

Эти лимиты не являются общим ограничением RPC/upload/всего shelf. Backend
генерирует миниатюры через `FfmpegThumbnailWorker` без isolate на каждый запрос:
одна задача — один FFmpeg, до четырёх задач одновременно. Число потоков
decoder/filter/encoder ограничено 1. Входной формат определяет FFmpeg; набор
поддерживаемых форматов зависит от установленной сборки. Проверены JPEG, PNG,
GIF, WebP и seekable MOV. Пути передаются списком аргументов без shell,
`-protocol_whitelist file,pipe` запрещает сетевые протоколы. Прямое чтение
файла позволяет демультиплексору перемещаться по контейнеру видео.

Размер файла проверяется через stat до и после FFmpeg, decoder `max_pixels`
ограничивает размеры кадра. Это не строгий предел фактически прочитанных байтов
при внешнем росте файла и не общий предел RSS процесса. Публикация дополнительно
проверяет актуальность источника, а работа ограничена deadline. Автоматический
JPEG lowres больше не выбирается через probe; большие кадры декодируются нативно,
что может увеличить память относительно предыдущего пути. После EXIF выполняются
точный центральный crop, scale без upscale, наложение фона, `thumbnail` и JPEG.
Фильтр буферизует до `frameSelectionFrames` уменьшенных кадров YUV 4:2:0;
память растёт с размером группы и вариантом enum, сверх памяти самого декодера.

Результат всегда JPEG `mjpeg`, `yuvj420p`, без метаданных ориентации. Публичная
шкала качества 1..100 отображается в qscale 31..2 (60 → 14); это не прежняя
шкала Dart image. В Dart поступает только ограниченный encoded JPEG; hash
готового JPEG вычисляется MD5 с передачей управления event loop; он служит
ETag и checksum при восстановлении дискового кеша. Крупные, повреждённые и
неподдерживаемые источники дают ошибку плитки, оригинал остаётся доступен.
Клиентский предел тела 200 MiB действует также для fullscreen.

Нужен `ffmpeg` из PATH; проверены 5.1.9 и 8.0.1. Фон рисуется в RGB:
`drawbox replace=1` на RGBA приводил к SIGSEGV в FFmpeg 5.1.9. Пакет `ffmpeg`
включён в зависимости DEB.
При отсутствии executable журнал содержит его имя, API возвращает 503;
Dart fallback отсутствует. Codec-тесты обязательны и не пропускаются молча.
Один deadline включает запуск, decode, выбор кадра, encode и hash.
Отмена/timeout/shutdown дожидаются завершения ребёнка и stdin/stdout/stderr,
при необходимости TERM через 200 мс усиливается до KILL. Cleanup может занять
время сверх deadline; следующий worker не получает слот раньше. Учтена отмена
во время `Process.start`. Застрявшее системное файловое I/O может задержать cleanup.
Отключение HTTP-клиента до ответа не передаётся Shelf как немедленная отмена
ожидающей генерации: действуют worker/waiter deadlines и общие budgets.
Отмена уже начавшегося файлового тела освобождает его FD и cache lease.

## Настройки gallery

Это отдельная секция корневой конфигурации рядом с `slideshow`, `welcome` и
`web` (поле `webServer` в Dart). Значения ниже — defaults; при компактном сохранении они опускаются.
Сохранённые изменения вступают в силу после перезапуска рамки.

```json
{
  "gallery": {
    "maxConcurrentMediaStreams": 12,
    "thumbnail": {
      "sizes": ["small", "medium", "large"],
      "jpegQuality": 60,
      "backgroundColor": "#202020",
      "frameSelectionFrames": 30,
      "maxWorkers": 4,
      "maxQueued": 8,
      "maxWaiters": 32,
      "cacheMaxBytes": 536870912,
      "cacheMaxEntries": 2048,
      "timeoutSeconds": 20
    }
  }
}
```

| Поле | Допустимые значения |
| --- | --- |
| `sizes` | Имена `GalleryThumbnailSize`: `small`=256, `medium`=512, `large`=1024; произвольных размеров нет |
| `jpegQuality` | Целое 1..100 |
| `backgroundColor` | Непрозрачный RGB, строка `#RRGGBB` |
| `frameSelectionFrames` | Целое 2..120, размер начальной группы для `thumbnail` |
| `maxWorkers` / `maxQueued` / `maxWaiters` | Целые 1..32 / 0..1024 / 1..4096 |
| `cacheMaxBytes` / `cacheMaxEntries` | Целые 1..1099511627776 байт / 1..1000000 объектов |
| `timeoutSeconds` | Целое 1..600; waiter ждёт не меньше 30 с и worker timeout + 10 с |
| `maxConcurrentMediaStreams` | Целое 1..128 |

Отсутствующие/неверные значения возвращаются к default соответствующего поля.
Неизвестные размеры пропускаются, дубли убираются, порядок нормализуется;
пустой список или список только неизвестных значений означает все три defaults.
В бизнес-логике используются значения enum, строки — только на границе JSON.
Настройки относятся к серверу; клиентские очереди и memory/encoded LRU сохраняют
прежние бюджеты. `maxOutputBytes` не больше 8 MiB и заданного дискового бюджета.

Кеши публикуют только завершённые файлы. Eviction не удаляет payload, пока его
удерживает HTTP consumer/декодер. Native-кеш хранит SHA-256 ключи вместо URL с
кодом доступа, переживает restart и убирает собственные неполные файлы.
Корневой UI isolate получает дисковое владение неблокирующей `.owner.lock` до
startup cleanup. При занятом/недоступном каталоге и в worker isolates используется
ограниченный memory cache 24 MiB / 128 объектов. Общий store сохраняет один
дескриптор блокировки до завершения процесса; standalone close удерживает его
до освобождения decoder pins и окончания cleanup. Ошибка инициализации сначала
отменяет/дожидается отложенной очистки и только затем освобождает владение.
Попадание в native-кеш проверяет файл и обновляет порядок LRU только в памяти:
записи metadata и `fsync` перед показом нет. Standalone backing close объединяет
обновления времени доступа и сохраняет их атомарно без `fsync`; ошибка этой
необязательной записи не мешает освобождению ресурсов. Shared store не закрывается
при смене маршрута/сессии. При завершении процесса восстановленный порядок LRU
может быть приблизительным.

Новые payload и metadata клиентского native-кеша записываются полностью и закрываются перед
атомарным переименованием; явного `fsync` перед передачей декодеру нет. Это
восстанавливаемый кеш: после потери питания последние записи могут исчезнуть или
повредиться. При открытии проверяются metadata, identity, тип и длина файла,
остатки незавершённых записей удаляются. Ошибка декодирования инвалидирует
запись; явный повтор загружает её заново. Проверки checksum содержимого клиентского кеша нет,
поэтому повреждение с прежней длиной, которое принимает декодер, может остаться
незамеченным. Оригиналы на рамке эта политика кеша не затрагивает.
Decoded Flutter ImageCache — отдельный ресурс; лимит encoded LRU не означает
такой же предел общей RSS. Автоматической подготовки всей фототеки нет.

## Диагностика на рамке

Галерея исполняется в web-isolate. В конфигурации выставьте уровень **Web** в ALL
(`"log": {"web": "ALL"}` — фрагмент существующей конфигурации), сохраните и
перезапустите приложение. Уровни main/hw_frame на неё не влияют.
Для следующего ручного запуска из консоли можно сохранить stdout и stderr:

```sh
cd /opt/dslideshow
./dslideshow.sh 2>&1 | tee /tmp/dslideshow-gallery.log
```

Откройте галерею и дождитесь ошибки/загрузки плитки. Если процесс уже запущен,
сначала завершите этот экземпляр: одновременно запускать две фоторамки нельзя.

| Категория | Диагностика |
| --- | --- |
| `WebService` | INFO: пути и активные настройки генератора; FINE: catalog/refresh, запрос/ответ миниатюры, mediaId/revision/size/policy, HTTP status и время |
| `GalleryCatalogService` | FINE: сканирование и число записей; WARNING: повреждённые метаданные и ошибки watcher |
| `ThumbnailService` | INFO: восстановленный кеш и бюджет; FINE/FINER: очередь, объединение, cache hit/negative hit и генерация; WARNING: ошибки генерации/диска/инициализации |
| `FfmpegThumbnailWorker` | FINE: источник, размер, PID, время, завершение и отмена; FINER: executable и точный массив аргументов; WARNING: причина, exit code и stderr |
| `MediaFileResponder` | Ошибки открытия/чтения файла, включая обрыв уже начатого тела |

Неожиданные Dart-ошибки выводятся вместе со stackTrace. Причина FFmpeg пишется
после завершения процесса и закрытия pipes; при SIGSEGV это `exit=-11`, даже
если stderr пуст. Пример диагностической строки:

```text
[web] WARNING:FfmpegThumbnailWorker: FFmpeg failed source=".../photo.jpg" size=256 executable="ffmpeg" pid=... exit=-11 reason=decodeFailed elapsedMs=... stderr=""
```

Stderr читается с прежним пределом 64 KiB, в журнал попадает максимум первые
8192 символа с отметкой `[truncated]`. Пути и stderr экранируются; бинарный stdout
и код авторизации из URL в новые сообщения не записываются. Подробности остаются
в локальном журнале, HTTP по-прежнему возвращает безопасный тип ошибки.
Повтор сразу после отказа может попасть в negative cache (TTL 3 с): это тоже
видно при ALL и не запускает новый FFmpeg. Отмена, устаревшая revision и занятые
очереди отмечаются на FINE; сбои генератора/файлов — на WARNING.

На FFmpeg 5.1.9 найдено и исправлено падение `drawbox replace=1` на RGBA.
Фон теперь переводится в RGB, заполняется и накладывается на исходный RGBA.
Поведение прозрачности, EXIF и выбора кадра сохранено. Policy 4 обновляет URL
даже у открытого клиента со старым каталогом через существующий ответ 409.
[Сценарий, результаты контейнера и RaPi](../benchmarks/reports/gallery-ffmpeg51-diagnostics-2026-10-27/report.md).

## Открытая приёмка

Состояние на 29.10.2026: полный A/B RaPi5/Wi-Fi, визуальная приёмка на устройстве
и FrameTiming UI не выполнены. Ограниченная LAN/CLI-диагностика выше их не заменяет.
Пригодность начальных четырёх FFmpeg workers для параллельной работы с фоторамкой
не подтверждена аппаратным сравнением. Новая навигация по папкам, pagination,
полная фоновая генерация коллекции и замена shelf не входят в реализованный объём.

Перед будущим A/B зафиксировать release baseline/candidate, одинаковые
SDK/engine/runtime, медиа, параметры и заранее выбранные пороги. Матрица включает
1k/10k/50k flat/nested, большие реальные неизменённые фото и независимые fixtures,
окно/DPR, cold/warm cache, быстрый/медленный/обратный scroll, resize/fullscreen,
смешанное видео, один/несколько клиентов и конкурирующее управление/RPC.

| Контракт | Критерий приёмки |
| --- | --- |
| Transport/leases и отмена | На ключ один transport, cap удерживается до конца body/cleanup, отмена видна серверу; pending ImageCache listener не удерживает ненужную сеть, повторный показ работает. |
| Viewport и повторные циклы | Demand ограничен viewport+prefetch, видимые задачи не голодают; после прогрева tasks/FD/memory выходят на plateau. |
| Генератор и серверные ожидания | Одновременный miss объединён; abort ожидающего клиента не удерживает работу сверх worker/waiter deadlines; ошибочная генерация не отравляет кеш. |
| Инвалидация и публикация | Замена во время hash/decode/stream, удаление, partial upload, crash/restart и forceInvalidate не публикуют старую revision; ресурсы освобождены. |
| Качество и совместимость | Фото/GIF/EXIF/alpha, zoom и video/seek/close сохраняют качество оригинала; Web/Linux, old/new server и CORS сохраняют смысл queue/revision/errors без storm. |
| Нагрузка и управление | Корректные 429/Retry-After, конечная нагрузка backend и сохранённая отзывчивость конфигурации/RPC; нет UX/resource регрессий. |

Собирать реальные bytes/cache tiers, TTFB/body p50/p95/p99, active/queued,
ошибки/отмены, CPU/RSS/HWM/FD/threads/I/O backend и workers, память/frame time
клиента и задержку RPC. Handler bytes не называть wire bytes; пропуски не заменять
нулями. Приёмка требует меньших байтов для той же последовательности просмотра,
подтверждённых cap/abort/bounds и улучшения наблюдаемой отзывчивости; одного RPS
или меньшего числа загруженных фото недостаточно.

Аппаратный прогон требует отдельно согласованного окна по
[руководству RaPi5](raspberry-pi-benchmarks.md), без автоматического расписания.
Изолированный GPU-стенд запускается только в OpenGL через supervisor с остановкой
и восстановлением службы; конкуренция с работающей фоторамкой — отдельный
согласованный сценарий. ОС, драйверы, firmware и flutter-pi не меняются.
Vulkan и 24-часовой прогон не входят в приёмку. При недоступности устройства
сохранить команды следующего прогона и оставить аппаратный статус открытым.
