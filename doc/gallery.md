# Галерея: управление медиатекой, дубликаты и кеш

Актуальность: сверено с кодом 31.10.2026. Точка входа —
[README config_app](../config_app/README.md). Галерея и управляемый загрузчик
реализованы; генератор миниатюр использует FFmpeg/JPEG. Поведение прежней
реализации и исходные измерения сохранены в
[baseline-исследовании](../benchmarks/reports/gallery-implementation-2026-10-26/baseline-analysis.md).

## Поведение панели

Сетка получает серверные квадратные JPEG-миниатюры 256, 512 или 1024 px по
размеру плитки и DPR. Доступные варианты задаются enum в конфигурации.
Фото, анимации и видео обрабатываются одним FFmpeg без ffprobe. EXIF учитывается,
прозрачность накладывается на фон (по умолчанию `#202020`), качество JPEG — 60.
Для анимации/видео фильтр `thumbnail` выбирает представительный кадр из первых
30 кадров. Он сравнивает гистограммы этой группы, не ищет лучший кадр во всём
ролике. Размер группы настраивается. Перед сравнением кадры уже уменьшены.

При обычном просмотре оригиналы не перекодируются: fullscreen, zoom,
GIF-анимация и фоторамка используют исходные файлы. Исключение — явный
[поворот оригинала](#поворот-оригинала), меняющий файл по команде пользователя. Плитка видео до запуска показывает JPEG-постер через общий
загрузчик миниатюр; нажатие запускает прежний Web/Linux-плеер с оригиналом.
На платформе без плеера постер остаётся доступен.

Один загрузчик фотографий на подключение обслуживает сетку и fullscreen.
Приоритеты: fullscreen → видимые плитки → prefetch по одной соседней строке
с каждой стороны viewport (не более одной активной prefetch-передачи).
Одинаковые запросы объединяются. Уход последнего потребителя отменяет очередь
или HTTP-запрос, включая чтение тела; слот освобождается после завершения
передачи/отмены. При открытии fullscreen сетка освобождает свой спрос, при
возврате пересчитывает viewport. Декодирование имеет отдельную очередь;
полученный ImageStream используется для показа без второго resolve/decode.

Обычное обновление перечитывает каталог и сохраняет версии неизменившихся
файлов. Ошибка обновления оставляет прежний список видимым. Ответ 409 на
изображение вызывает объединённую сверку каталога; смена версии обновляет и
открытый fullscreen. Удалённая запись показывает ошибку. Автоматических
повторов загрузки изображений нет: повтор выполняется явным действием пользователя.
Ошибка миниатюры не запускает массовую загрузку оригиналов.

Смена сервера, кода авторизации или разрыв соединения закрывают прежний scope:
его поздние ответы не попадают в новую сессию. Панель использует общий контракт
разделов `published`, `hidden` и `trash`. Ошибки авторизации, отсутствующий API,
5xx, неизвестная schema и повреждённая thumbnail policy показываются как ошибки.
Перехода на прежние маршруты нет; backend и панель обновляются вместе.

## API и инвалидация

Все маршруты используют существующий код доступа `<code>`.
`<section>` — значение `GalleryMediaSection`: `published` (файлы `images`,
участвующие в показе), `hidden` (`images.gallery/hidden`) или `trash`
(`images.gallery/trash`). При настроенном каталоге состояния используются
его подкаталоги. Неизвестный раздел даёт 400, неверный код доступа — 403.

| Запрос | Результат |
| --- | --- |
| `GET /cache/<code>/v2/<section>/catalog` | `GalleryCatalog`, JSON schema 2: section, catalog revision, capabilities, thumbnail policy и `GalleryEntry` |
| `POST /cache/<code>/v2/<section>/catalog/refresh` | JSON `{operationId, mode}`; `scan` доступен всем разделам, `forceInvalidate` — только published |
| `GET/HEAD /cache/<code>/v2/<section>/thumbnail/<mediaId>/<sourceRevision>/<policy>/<bucket>` | JPEG любого раздела, policy из каталога, bucket из настроенного enum; ленивое создание |
| `GET/HEAD /cache/<code>/v2/<section>/original/<mediaId>/<sourceRevision>` | Исходные байты с проверкой ID и версии; Range и условные запросы поддерживаются |
| `GET /cache/<code>/v2/<section>/metadata/<mediaId>/<sourceRevision>` | `GalleryMetadata` с теми же section, ID и версией; `Cache-Control: no-store` |

Ссылка на медиа — `GalleryMediaRef {section, mediaId, sourceRevision}`.
`section` обязателен в JSON каталогов, записей, ссылок, metadata и результатов
операций; отсутствующее, null или неизвестное значение отклоняется. В Dart-конструкторах
раздел также обязателен. Общая запись содержит
`path`, `name`, `kind`, `thumbnailSupported`, опциональные `sizeBytes` и
`fileChanged` (ctime, а не историческое время переноса). В каталогах папки имеют
пустую `sourceRevision`; команды и чтение медиа требуют непустую версию.
Пути передаются для отображения; HTTP-чтение и команды адресуют файл по ссылке.

`GalleryFileOperations.resolveMedia` использует индекс нужного раздела и проверяет
один файл. Сканирование всей коллекции на каждый original/metadata/thumbnail не
выполняется. `GalleryMediaTools` обслуживает все разделы общей ограниченной
очередью и кешем метаданных. Ключи метаданных, миниатюр, изображений и выбора
включают раздел; совпавшие ID разных разделов не разделяют содержимое кеша.

Внутри `GalleryFileOperations` корень выбирается через `directory(section)`,
а индексы hidden/trash хранятся в карте по `GalleryMediaSection`. Один алгоритм
перемещения обслуживает скрытие, корзину и восстановление; при восстановлении
в published подбирается свободное имя, при занятом пути hidden/trash возвращается
`conflict`. Создание записей и проверка путей также используют раздел, без
`bool hidden` и неявной корзины по умолчанию. Инициализируются только участвующие
в операции разделы: недоступность другого корня не мешает переносу или чтению.
Отказ при инициализации выбранного hidden/trash возвращается в результате
соответствующего элемента пакета; остальные элементы продолжают обрабатываться.

`kind` различает фото, GIF, видео, каталог, неподдерживаемый и неизвестный тип.
`thumbnailPolicy` содержит `version=4`, `revision` (SHA-256 параметров рендера)
и `sizes` (существующий числовой wire-формат enum). Сегмент `<policy>` имеет вид
`4-<revision>`; клиент строит его из каталога. В hash входят качество, фон,
размер группы кадров и доступные размеры. Настройки очередей/кеша не меняют hash.
Оба значения входят в серверные и клиентские cache keys. Изменение настроек
после перезапуска даёт новый URL, сохраняя версии оригиналов и выбор элементов.
Старые производные не мигрируются: прежние файлы с SHA-256 digest удаляются
при восстановлении кеша.
Устаревшая policy возвращает 409, некорректные параметры — 400.
Клиент не определяет вид медиа по URL миниатюры. Каталоги остаются в списке;
новая навигация по папкам не добавляется.
Прежние маршруты чтения и старые модели корзины удалены без алиасов.

Индекс каталога существует только в памяти и строится сканированием оригиналов.
`mediaId` — SHA-256 относительного пути; версия оригинала — SHA-256 stat-полей
и общей метки принудительной инвалидации. Содержимое фотографий для этого не
хешируется. Замена или повторное создание по тому же пути сохраняет ID;
при отличающихся stat-полях меняется версия. Переименование меняет ID.
Ревизия снимка вычисляется потоковым хешированием отсортированных путей и
stat-полей, без создания второго полного JSON. `serverId` в API отсутствует;
клиент использует существующий контекст адреса и авторизации.

Рядом с оригиналами находится `<images>.gallery/`: например,
`/data/images.gallery` для `/data/images`. Единственное состояние каталога на
диске — `catalog.epoch`, ровно 32 ASCII-байта. Он создаётся при первом запуске
и заменяется при `forceInvalidate`; обычное сканирование и файловые действия
его не переписывают. Размер не зависит от количества медиа. `catalog.json`
больше не читается и не создаётся; миграции старого тестового индекса нет.
Потеря или повреждение `catalog.epoch` даёт новую метку и новые версии кеша,
но сохраняет ID путей. Неизменённые файлы сохраняют кеш после перезапуска.
Пользователю службы нужны права записи в каталог состояния.
Производные находятся в `thumbnails/`, пользовательская корзина — в `trash/`,
скрытые файлы — в `hidden/`;
весь каталог состояния нельзя удалять как кеш миниатюр.

Web upload, GooglePhoto, Яндекс Диск и поворот публикуют только полностью записанные
staging-файлы через атомарное переименование. До замены прежний оригинал
остаётся доступен; промежуточное содержимое не обслуживается как готовое медиа.
Зарезервированные `.upload-<32hex>.part` и производные не попадают в каталог
медиа. Облачные Storage ожидают окончания тела и закрытия writer. Пауза,
отключение аккаунта и штатный shutdown не прерывают текущий скачиваемый файл:
он проверяется и публикуется, затем освобождаются сетевые ресурсы.
Остановка запрещает начинать следующие файлы.

Публикацию облачных загрузок выполняет сам `CloudStorage` в backend-isolate,
без RPC в web-isolate и без явного `markDirty` каталога галереи. Загрузка
не инициирует обновление открытого списка; пользователь пользуется кнопками
обновления. Файловый watcher backend-каталога не отправляет обновления в UI.

Версия конкретного оригинала определяется по типу, размеру, `mtime` и `ctime`
из `FileStat`. После успешной HTTP-загрузки, поворота, переноса в корзину или
восстановления вызывается `GalleryCatalogService.markDirty()` в том же
web-isolate. Метод только помечает снимок устаревшим; следующий запрос каталога
перечитает оригиналы. Несколько уведомлений до чтения объединяются. Уведомление
во время scan сохраняет необходимость следующей сверки. Неизменённые фото
сохраняют версии и кеш. Файлов уведомлений, `publication.version`, класса
`GalleryPublication`, отдельных JSON/`.pending` и проверок PID больше нет.

Внешние правки обнаруживаются сканированием stat-метаданных, событиями файловой
системы и периодической сверкой при чтении каталога (не чаще необходимости;
максимальный возраст снимка — 30 секунд). Запись внешним процессом, включая
вложенные папки без watcher-события, обнаруживается при периодической сверке
или явном обновлении. Межизолятных уведомлений в текущей схеме нет; Google
Photos пока не учитывается. После перезапуска индекс строится заново.
Любая замена с сохранением всех stat-полей может остаться незамеченной.
После такого импорта требуется явный `forceInvalidate`; обычный Refresh его
не выполняет. Операция меняет общий content epoch и создаёт новые производные
только по последующему спросу, без eager-обработки коллекции.

Пример сервисной инвалидации; `GALLERY_BASE` — адрес вида
`http://host:port/cache/<code>`. Для новой операции нужен новый ID; повтор той же
отправки сохраняет ID (сервер помнит последние 64 ID обновлений только в памяти,
до перезапуска; это отдельный контракт от файловых действий корзины):

```sh
gallery_operation_id="$(cat /proc/sys/kernel/random/uuid)"
curl --fail-with-body -X POST "$GALLERY_BASE/v2/published/catalog/refresh" \
  -H 'Content-Type: application/json' \
  --data "{\"operationId\":\"$gallery_operation_id\",\"mode\":\"forceInvalidate\"}"
```

Отмена ожидания POST не отменяет уже применённую инвалидацию. Ошибки каталога
и миниатюр типизированы: 400 — запрос, 403 — доступ, 404 — отсутствует, 409 — версия,
415 — неподдерживаемый источник, 429 — бюджет занят, 503 — сервис недоступен.
Для перегрузки возвращается `Retry-After`. Дополнительные причины новых
[операций управления](#операции-http) перечислены отдельно.

Производные имеют strong ETag по байтам и `private, max-age=604800, immutable`;
оригиналы — `private, no-cache` и слабый stat validator. Source revision не
является strong ETag. Поддерживаются HEAD, 304, одиночный Range, If-Range и 416.
Range применяется к GET; HEAD игнорирует его и возвращает длину полного файла.
If-Range допускает частичный ответ только с точным strong ETag. Дата и слабый
ETag консервативно дают полный 200: stat-метаданные не доказывают отсутствие
нескольких замен за секунду. Несколько диапазонов также дают полный ответ.
CORS включает OPTIONS и
разрешает читать validators, Content-Length/Range и Retry-After. Даже готовая
производная проверяется на актуальность источника перед выдачей.

## Управление медиатекой

В разделе галереи доступны «Медиатека», «Скрытые», «Дубликаты» и «Корзина». Наличие
действий определяется capabilities backend: старый сервер сохраняет просмотр,
но не получает неработающих кнопок изменения файлов. Каталоги остаются в списке,
но не выбираются для файловых операций. Рекурсивный перенос папок не реализован.

### Состояние панели

Состояние интерфейса разделено между Bloc по жизненному циклу задач:
`GalleryBloc` загружает каталог, `GalleryManagementBloc` управляет разделом,
выбором и корзиной, `GalleryViewerBloc` — открытым файлом, его версией,
метаданными и действиями. `GalleryDuplicatesBloc` хранит состояние поиска,
опрос сервера и решения сравнения; отдельный `GalleryComparisonMetadataBloc`
читает краткие сведения только видимой карточки. `GalleryUndoBloc` хранит
идентичности исходных файлов независимо от закрытия экрана и при каждом
действии перечитывает текущую корзину.

`GalleryGroupComparisonBloc` индексирует размеры текущей проверенной группы,
хранит счётчики числа пикселей и уточняет их по ответам смонтированных карточек.
Он не загружает сведения сам: смена страницы сохраняет сравнение всей группы,
смена группы освобождает индекс. `GalleryFilePathBloc` хранит раскрытие пути;
виджеты расположения также остаются `StatelessWidget`.

Экраны используют `StatelessWidget`, Bloc передаёт типизированные состояния
и эффекты. Диалоги, навигацию и уведомления выполняет представление.
Подписки, таймеры и запросы освобождает создавший их Bloc; его закрытие
не закрывает общий HTTP-клиент сессии и не останавливает серверный поиск.
Прерывание ожидания изменения файла не означает отмену уже выполненной
операции. После неизвестного результата файловой команды список обновляется;
следующее действие проверяет новый снимок и отправляет новую команду.

Локальная анимация панелей просмотра сохраняет небольшой `StatefulWidget`
с `AnimationController` и `TickerProvider`; состояние файла ему не принадлежит.
Контроллеры синхронного масштаба сравнения принадлежат отдельному ресурсу
представления и освобождаются вместе с ним. Загрузчик изображений и видеоплееры
сохраняют собственное владение ресурсами; изменение архитектуры экранов
не переносит их контроллеры в бизнес-логику.

### Большие коллекции: 50 000+ медиафайлов

**50 000 и более медиафайлов — штатный сценарий фоторамки**, который нужно
учитывать при дальнейших изменениях API, состояния интерфейса и файловых
операций. Нельзя рассчитывать на маленький каталог, создавать виджет или
контроллер для каждого файла, заранее читать все оригиналы/EXIF либо
генерировать все миниатюры при открытии галереи.

Это архитектурный ориентир; он не задаёт обязательный размер каждой тестовой
выборки. Новые проверки используют минимальные данные для границ пакета,
лимитов, частичного отказа и восстановления. Создание 50 000 реальных файлов
не входит в обычную функциональную проверку.

Сетка строится лениво: спрос на изображения ограничен viewport и одной
соседней строкой с каждой стороны; размеры очередей и кешей не растут вместе
с библиотекой. Снимок каталога индексируется по идентификатору и версии один
раз при обновлении; выбор нескольких файлов, открытый просмотр и проверки
актуальности дублей используют индексы. Тик ожидания поиска не пересоздаёт
индексы всей коллекции. EXIF запрашивается для открытого файла либо видимой
пары сравнения.

Каталог пока передаётся целиком, без серверной пагинации: сканирование,
первичный JSON-разбор и построение индексов зависят от числа файлов и длины
путей. На диск индекс и список файлов не записываются; сохранённая метка
`catalog.epoch` имеет постоянный размер. Клиентский предел каталога — 64 MiB JSON. Поиск дублей допускает до
100 000 кандидатов; лимиты JSON результата, корзины и пакетных операций
перечислены в [бюджетах](#бюджеты-и-ограничения). Это отдельные защитные
ограничения, а не обещание неограниченного числа записей. Превышение лимита
возвращает ошибку, результат не обрезается молча.

Предпросмотр одного файла корзины проверяет только его запись и путь, без
обхода всей корзины. Получение полного списка корзины и первое чтение её
индекса остаются линейными. Корзина хранится обычным деревом файлов,
постоянного manifest и журнала операций нет. Индекс существует только в памяти;
явное обновление перечитывает файловую систему. Удаление файлов корзины
не сканирует каталог оригиналов.

Серверная команда содержит не более 1000 файлов и 256 KiB JSON. Панель
разбивает удаление из корзины на пакеты до 1000 файлов, восстановление — до
50 файлов; каждый пакет дополнительно ограничен размером JSON.
Перенос из медиатеки и действия сравнения сохраняют предел 1000 файлов
на команду. Локальные проверки не измеряют скорость и ресурсную стоимость
больших операций на накопителе рамки.

В существующем наборе есть отдельные регрессии на 50 001 модельную запись: получение каталога без усечения,
доступ к концу сетки с ограниченным спросом, выбор и сверку версий файлов.
Они проверяют поведение и границы загрузки, без утверждения о времени ответа,
памяти и плавности интерфейса на устройстве. Аппаратный прогон для такой
коллекции требует отдельного согласования.

### Выбор и просмотр файла

Галерея использует общие `SettingsContent`, тематические карточки и отступы
панели настройки. Просмотр сохраняет полноразмерное медиа, но его шапка
и карточка сведений используют те же цвета, типографику и кнопки. При ширине
просмотра от 1000 логических пикселей сведения располагаются справа,
иначе — снизу; внутри карточки прокручиваются сами поля.

Расположение в сведениях показано «хлебными крошками»: ведущий `/` обозначает
корень `images`, папки разделены и переносятся между сегментами, имя файла
выведено отдельным заголовком. В сравнении дубликатов акцент сделан на ближайшей
папке; в свёрнутой карточке показано только её имя. «Полный путь» раскрывает
все папки и выделяемый текст `/album/photo.jpg`, который можно скопировать
обычными средствами выделения. Длинный сегмент в цепочке ограничен двумя строками с
подсказкой; раскрытый путь и имя файла переносятся без усечения. В корне показан
`/`, без искусственного имени папки. Пока metadata не пришли, просмотр показывает
имя без предположений о расположении. Для корзины используется исходный путь.
Представление принимает относительный POSIX-путь API; абсолютные пути и сегменты
`.`/`..` отклоняются. Технический URL, код доступа и физический корень сервера
из URI изображения не извлекаются и не показываются.

Чекбокс или долгое нажатие выбирают медиафайл. Пока есть выбор, нажатие плитки
меняет выделение. Постоянная панель медиатеки содержит **только счётчик,
«В корзину» и крестик**. При пустом выборе счётчик показывает 0, кнопки
неактивны. Крестик снимает выбор; панель остаётся на месте, поэтому сетка
не сдвигается при выборе первого файла или очистке. Такая же постоянная
панель корзины показывает её действия. В медиатеке массового поворота
и «Выбрать всё» нет. В корзине доступны «Выделить всё» и «Очистить корзину»;
при пустой корзине обе кнопки неактивны. «Очистить корзину» действует
на весь показанный снимок корзины независимо от текущего выделения.
Рамка выделения рисуется поверх изображения: её появление не меняет размер
миниатюры и не запускает повторное декодирование уже показанного кадра.

«В корзину» в сетке и просмотре сначала открывает подтверждение: количество
и первые 10 имён. Отмена или закрытие диалога не отправляет команду серверу.
Каждый файл в подтверждениях переноса и окончательного удаления занимает
отдельный пронумерованный блок с фоном и границей. Показано только имя,
без полного пути и его повторения; длинные имена переносятся без усечения.
В подтверждении выбранных дубликатов под именем также показан размер в МБ,
точные байты доступны в подсказке. Разделение не меняет состав команды.
При большем выборе после списка написано точное количество остальных файлов,
которые переместятся в корзину; команда охватывает весь подтверждённый выбор.
Подтверждение привязано к выбранным файлам и их версиям: если за это время
выбор или файлы изменились, требуется проверить выбор и повторить действие.
Очистка корзины также запрашивает необратимое удаление: количество,
суммарный размер и первые 10 имён. Файлы, поступившие после создания
подтверждения, в эту операцию не добавляются.
Перед окончательным удалением суммарный размер подписан как ожидаемый
освобождаемый объём, после первых десяти имён показано число остальных файлов.
Объём — сумма размеров всех файлов подтверждённого снимка, а не замер
физически свободных блоков файловой системы. Сам перенос в корзину места
не освобождает.

Во время массовой операции панель корзины показывает «Обработано X из Y»
по подтверждённым ответам пакетов. Ошибки отдельных файлов сохраняются
в итоговом окне. Если результат текущего запроса неизвестен, отправка
следующих пакетов останавливается, план очищается и список обновляется.
Показывается уведомление о неизвестном результате. Следующее действие
использует актуальный снимок; удаления снова требуют подтверждения.
Если обновление не удалось, перед новой операцией нужно повторить загрузку
списка. Сохранённого результата для воспроизведения прежней команды нет.
Выход из экрана прекращает отправку следующих пакетов, но начатый пакет
может завершиться на backend. Следующий вход обновляет содержимое корзины.

Окно результатов показывает общее количество ошибок и первые **10 имён**,
а не строит список всей коллекции. Имена берутся из исходного снимка операции,
даже если следующий каталог уже не содержит неудавшийся файл. Подтверждение
выбранных дублей также показывает количество и не более 10 файлов; команда
применяется ко всему выбранному пакету. Диалоги сохраняют готовые изображения
на фоне и их текущие запросы. Полностью перекрывающий экран просмотра
по-прежнему освобождает спрос скрытой сетки; приостановка видео в сетке
учитывается отдельно от видимости миниатюр.

После выхода из выбора нажатие фотографии открывает просмотр. Поворот одного
файла, «В корзину» и «Сведения» находятся внутри этого просмотра. Информация
открывается справа на широком экране и снизу на узком; кнопка «Сведения»
не скрывает общие панели просмотра и управления видео. Возврат сохраняет
позицию сетки. После переноса открытого файла в корзину просмотр закрывается,
появляется «Отменить». Внешнее исчезновение файла показывает «Файл недоступен»
и отключает файловые действия.

Полные метаданные запрашиваются лениво по `mediaId` и `sourceRevision`:
имя, путь, формат, размер файла и разрешение, дата съёмки отдельно от времени
файла, EXIF Orientation, камера, объектив, ISO, выдержка, диафрагма и фокусное
расстояние. Для видео выводятся доступные длительность и сведения о кодеке.
Также доступны цветовой профиль, глубина цвета и альфа-канал; GPS раскрывается
отдельно. Отсутствующие теги не заполняются придуманными значениями. Если EXIF
не содержит часового пояса, дата съёмки не получает несуществующий UTC offset.

EXIF читает backend пакетом Dart `exif`; фактические размеры берутся из
заголовка контейнера, включая файлы без EXIF. ICC читается из контейнера,
сведения о видео — через `ffprobe` из пакета FFmpeg. ExifTool не требуется.
Клиент не скачивает оригинал ради панели информации и не загружает
подробности всей сетки. Кеш учитывает версию файла.
Чтение выполняется в worker-isolate без декодирования пикселей. Адаптер
ограничивает чтение с диска и разбор EXIF в памяти отдельными бюджетами
по 16 MiB; после разбора принимает не более 1024 тегов. Deadline 30 секунд
проверяется между шагами чтения, отмена ожидает закрытия файлов worker;
это не жёсткое прерывание зависшего системного I/O.
Для владения дескрипторами используется изолированный адаптер внутреннего
API `exif` 3.3.0; при обновлении пакета нужны его регрессионные проверки.
Произвольные MakerNotes, XMP и IPTC не имеют полного покрытия ExifTool.
Смена файла/версии и закрытие сведений отменяют ненужный запрос; поздний ответ
не заменяет информацию нового файла. Транспорт управления отделён от загрузки
каталога и изображений.

### Поворот оригинала

Явное действие «Повернуть влево/вправо на 90°» изменяет оригинал на диске.
JPEG обрабатывается `jpegtran -perfect`: без повторного сжатия с потерями
и без обрезки краёв. Если размеры/преобразование не допускают такой операции,
возвращается отказ, исходный файл сохраняется.

PNG поворачивается пакетом Dart `image` с сохранением пиксельного формата: поддерживаются
RGB и grayscale 8/16 бит, с альфа-каналом и без него. Palette, низкая глубина
1/2/4 бита, прозрачность через `tRNS` и APNG отклоняются, чтобы не превратить
источник в упрощённый или непрозрачный кадр. GIF, видео и другие форматы
не поворачиваются.

Для JPEG используется EXIF, который оставляет `jpegtran -copy all`.
Исходные APP1-блоки обратно не записываются. Пакет `exif` читает теги до/после
преобразования; изменение их нормализованного представления даёт WARNING
`Rotation EXIF changed` без имён/значений тегов и GPS.
Сравнение охватывает прочитанные пакетом теги, а не произвольные MakerNotes
и не побайтное равенство EXIF. `GalleryRotationMetadata` удалён.
Orientation отдельно проверяется как часть геометрии видимого поворота;
он не нормализуется, размеры EXIF и встроенная миниатюра могут остаться прежними.
Поворот пикселей рассчитан так, чтобы прежний Orientation, включая зеркальные
варианты, давал запрошенный видимый поворот.

Для PNG применяется EXIF Orientation, включая зеркальные варианты, затем
запрошенный поворот. Dart записывает правильные Orientation=1 и размеры
в EXIF, удаляет прежнюю встроенную миниатюру. Дата съёмки и сведения камеры
сохраняются. В обоих форматах интерфейс получает фактическое разрешение
из заголовка изображения; ICC-профиль проверяется по содержимому.
PNG сохраняет поддерживаемые стандартные EXIF-поля и независимые блоки
контейнера; неизвестные блоки, небезопасные для копирования после изменения
пикселей, отбрасываются. Семантика смещений в произвольных MakerNotes
и актуальность полей XMP не гарантируются.
Временный файл создаётся рядом с оригиналом с зарезервированным именем.
Готовый результат закрывается и проверяется, затем одним `rename` заменяет
оригинал на том же разделе. Отдельного удаления оригинала перед заменой нет;
ошибка до публикации оставляет его целым. Журнал, digest результата для
восстановления и история запросов поворота не сохраняются.
Повторные действия в просмотре блокируются
на время операции. Для обратного поворота выполняется новая операция;
история оригиналов не хранится.

Успех обновляет сведения, `sourceRevision`, открытое изображение и миниатюры
галереи. Решения поиска дублей для прежней версии нельзя применить к новой.
Галерея не координирует действие с текущим/следующим слайдом и не добавляет
RPC в renderer: недоступное медиа остаётся случаем показа заглушки. Расширение
общего поведения слайдшоу в эту возможность не входит.

### Корзина

Для медиатеки `/data/images` корзина находится в **`/data/images.gallery/trash`**,
в общем каталоге состояния галереи, отдельно от его `thumbnails/` и `duplicates/`.
При явно заданном каталоге состояния путь — `<gallery state>/trash`.
Вложенность сохраняется: `/data/images/folder1/test1.jpg` перемещается в
`/data/images.gallery/trash/folder1/test1.jpg`; путь восстановления выводится из
относительного пути внутри корзины. Manifest, sidecar-файлы и история
операций не создаются.
Она не входит в обход оригиналов, поиск дублей и очистку кеша миниатюр.
Удалять весь `images.gallery` как расходный кеш нельзя: в `trash/` находятся
пользовательские файлы. Очистка миниатюр работает только в `thumbnails/`.
Пользователю службы
нужны права записи в этот каталог. Перенос выполняется на том же файловом
разделе; копирование с последующим удалением между разделами не используется.
Невозможный атомарный перенос возвращает ошибку и сохраняет исходный файл.
Родительские папки создаются до `rename`; вся цепочка их создания не является
одной транзакцией. При отказе могут остаться пустые папки. Используется обычный
асинхронный `File.rename` с проверкой целевого пути непосредственно перед
переносом, без FFI. Если путь в корзине уже занят при проверке, перенос
возвращает `conflict`, оба файла сохраняются. Проверка и перенос — отдельные
действия: если внешний процесс создаст целевой файл между ними, `File.rename`
может заменить его. Для фоторамки это согласованное ограничение; собственные
операции сервиса выполняются последовательно.

Настроенный корень оригиналов может быть символической ссылкой, включая
цепочку относительных ссылок локального стенда `backend/bin/web_server_test.dart`.
Файловые операции фиксируют его каноническую цель и проверяют дочерние пути
внутри неё. Дочерние ссылки и выход из корня запрещены. Корзина находится
в настроенном каталоге состояния галереи, а не рядом с физической целью
ссылки оригиналов. Перенастройка
корня при работающем сервисе отклоняется с `revisionMismatch` и диагностикой
`reason=rootChanged`; после такой перенастройки нужен перезапуск сервиса.
Физическое пересечение деревьев оригиналов и корзины также запрещено.

В корзине доступны знакомые сетка, выбор и просмотр файла. В сведениях
показаны исходный путь и время изменения записи файла в файловой системе
(на Linux — ctime). Отдельная историческая дата переноса не хранится;
поле `fileChanged` общего JSON-контракта передаёт это производное время.
Действия — «Восстановить»
и «Удалить навсегда»; в просмотре они заменяют поворот и обычное «В корзину».
Миниатюры корзины создаются общим генератором с обычными бюджетами,
очередью и освобождением ресурсов. Полноэкранный просмотр получает исходный файл.

**Автоочистки нет.** Необратимое удаление требует подтверждения количества
файлов, их суммарного размера и показывает первые 10 имён. «Отменить» после переноса выполняет обычное
восстановление. Уведомление с действием имеет отдельный крестик и скрывается
через 8 секунд; обычные сообщения — через 4 секунды. Закрытие уведомления
не восстанавливает файлы, они остаются в корзине. Позднее их можно восстановить
из раздела корзины. При конфликте имени сервер выбирает свободное имя вида
`photo (restored 1).jpg`; занятые при проверке пути пропускаются, фактический
путь возвращается в результате. Ограничение гонки между проверкой и
`File.rename` действует и при восстановлении. После восстановления каталог
может назначить новый `mediaId`.

Список строится из текущих файлов. Идентификатор включает относительный путь
и stat-версию, поэтому старый Undo не захватывает другой файл, позже появившийся
по тому же пути. Предпросмотр проверяет только запрошенный файл в индексе;
проверка версии выполняется перед действием. После перезапуска источник
истины — файловая система. Команды и результаты на диск не записываются:
повторный запрос заново проверяет файлы и может вернуть `notFound`.
Очередь изменений и индекс корзины хранятся в памяти; после перезапуска
незавершённые команды не продолжаются, список заново строится из файлов.

В ответе пакета возвращается фактический результат каждого файла. Ошибка
служебного обновления кеша после успешного `rename` не превращает выполненный
перенос в отказ. При частичном отказе успешные элементы исчезают из списка,
ошибочные остаются выделенными. После неизвестного ответа список перечитывается.
Undo восстанавливает только исходные записи, всё ещё присутствующие в корзине;
отсутствующие записи не объявляются успешно восстановленными.

Совместимость с экспериментальными форматами корзины и публикаций не
поддерживается: версия не публиковалась, миграции и очистка прежнего manifest
не выполняются. Содержимое прежнего `images.trash` автоматически не переносится.
Каталог корзины читается как обычное дерево медиафайлов.
Неизвестные и неподдерживаемые файлы не удаляются как мусор кеша.

Перенос на том же разделе **не освобождает место**. Сумма размеров файлов
не означает точный прирост свободных байтов после удаления, например при
hardlink. Корзина не запрещает повторную загрузку из облака. Для этого файл
должен оставаться в hidden; облачное удаление не выполняется.

### Скрытые файлы

«Скрыть из показа» перемещает файл из `images/<путь>` в
`images.gallery/hidden/<путь>`, сохраняя всю вложенность, в том числе
`yandex.drive.<accountId>`. При явно заданном каталоге состояния используется
`<gallery state>/hidden`. Это пользовательские файлы, а не кеш миниатюр.
Путь возвращения выводится из дерева файлов, без manifest и базы происхождения.

В backend Storage общий корень hidden и предварительная проверка наличия
в двух деревьях принадлежат `DiskStorage`. Облачный Storage самостоятельно
публикует скачанные файлы, а пользовательские операции скрытия и возвращения
в показ выполняет галерея. Пользователь скрывает уже опубликованный файл, а наличие
его в hidden предотвращает импорт при следующих сверках.

В «Скрытых» доступны обычная сетка и просмотр, массовое и одиночное
«Вернуть в показ», перенос в общую корзину. Undo скрытия перечитывает hidden
и возвращает только ещё существующие исходные записи. Конфликты имён,
проверка версии, границы пакетных команд и ошибки отдельных файлов обрабатываются
тем же механизмом файловых операций. Восстановление из корзины возвращает
файл в `images`, без сохранения прежнего скрытого состояния.

Google Photos и [Яндекс Диск](yandex-disk.md) проверяют соответствующий путь
в originals и hidden до загрузки и перед финальной публикацией. Файл в hidden
не скачивается заново по тому же пути. После выхода из hidden запрет прекращается;
корзина и окончательное удаление не создают постоянной записи запрета.
Наличие идентичного содержимого по другому пути не является запретом.

Скрытие не меняет renderer и не переключает текущий слайд принудительно:
для уже открытого/предзагруженного недоступного файла сохраняется существующая
заглушка. Скрытые файлы не входят в обычный обход слайдшоу.

### Поиск и сравнение дубликатов

Поиск охватывает статические изображения в медиатеке **и hidden**, включая
все папки аккаунтов. Корзина, видео и GIF исключены. Участник результата
содержит `section: published|hidden`, скрытые ID имеют отдельное пространство.
Одинаковые относительные пути в двух корнях не смешиваются. В карточке
показано «В показе» или «Скрыто»; перед подтверждением удаления последних
видимых экземпляров отображается предупреждение, если останутся только скрытые.
Панель не разрешает выбрать все экземпляры группы из текущего снимка обоих корней.

Шапка страницы показывает количество групп и состояние поиска, кнопку
«Новый поиск». Панель текущей группы содержит её номер, тип совпадений,
количество файлов, переход назад и «Следующая группа»; при открытии сервер
по-прежнему проверяет актуальность участников и может пропустить уже
разрешённые группы. Порядок групп и участников не меняется. До десяти
участников показаны компактными карточками: имя и подписанный чекбокс
«В корзину» сверху, фото рядом со сведениями на широком экране и над ними
на узком. «Открыть фото» увеличивает изображение в отдельном диалоге с
масштабированием. Владельцы изображений и запросов сведений сохраняются
при выборе файла и открытии диалога нового поиска.

Пояснения скрыты под «Как выбирается кандидат?», сведения последнего успешного
поиска — под «О последнем поиске». Ошибки и диагностические причины отказа
остаются видимыми; в пустом успешном результате диагностические счётчики также
показаны сразу. Нижняя панель доступна независимо от прокрутки: количество
уникальных выбранных файлов из всех групп, суммарный объём в десятичных МБ,
«Снять выбор» и «В корзину». Пересекающиеся группы не удваивают сумму.
Размеры берутся из снимка результата поиска, байты доступны в подсказке;
перенос в корзину не подписывается как освобождение места. Обычное изменение
чекбокса обновляет агрегаты по одному участнику без обхода всей медиатеки.

«Новый поиск» открывает диалог: точные копии, похожие фото либо оба режима.
Начальное значение соответствует последнему режиму задания; до первого
поиска выбраны оба. Это черновик: закрытие или отмена не отправляет запрос,
не меняет выбранный режим и решения по файлам. «Начать поиск» применяет режим
и запускает прежний API. После ошибки или остановки backend возвращает
предыдущие готовые группы; в текущей сессии страницы восстанавливаются решения
по сохранившимся ID и версиям, изменившиеся файлы исключаются. Новый успешный
результат очищает прежние решения. Выбор не хранится на диске. Эти изменения
представления не меняют Czkawka, её параметры и нормализацию групп.

Первый объём — статичные фотографии локальной медиатеки. Можно выбрать точные
копии, похожие изображения или оба режима; похожие видео не анализируются.
Поиск выполняет Czkawka CLI на backend. Требования к executable, совместимым
версиям и упаковке перечислены в [README backend](../backend/README.md).
Похожий режим использует `--image-filter Lanczos3`: фильтр уменьшения перед
перцептивным хешированием устойчивее к копиям другого разрешения, чем штатный
`Nearest`. Остальные параметры сходства и точный режим не изменены. В реальном
примере 7 побайтно одинаковых файлов 1080×1920 и один 800×1422 доступны вместе
в похожей группе из 8; при обоих режимах точная группа из 7 сохраняется
отдельно. Это не устраняет ограничение группировки Czkawka 12.0.1, когда у
обоих разных перцептивных хешей уже есть несколько одинаковых экземпляров.
Переключение фильтра применяется при новом поиске на обновлённом backend;
предыдущий результат в `job.json` автоматически не пересчитывается.
Capability сообщает наличие API; отсутствие executable возвращает ошибку
сервиса, а не пустой список.

Backend запускает CLI, ожидает завершения и **только затем читает итоговый JSON**.
Два режима выполняются последовательно в одной задаче; группы публикуются
после проверки всех результатов. В панели видны индикатор активности,
прошедшее время и «Остановить». Процентов, паузы и потокового разбора progress
bars нет; этап выводится только в диагностике результата/ошибки, не как
прогресс CLI. Одновременно выполняется один поиск. Переход
в другой раздел не останавливает процесс; после возврата или нового входа
читается его состояние. Перезапуск backend переводит незавершённый поиск
в `interrupted`; автоматического возобновления нет.

Полные группы удерживаются для текущей задачи и предыдущего успешного поиска;
история до 64 ID запуска содержит только небольшие результаты без групп.
Повтор старого завершённого запуска, чьи группы уже вытеснены, возвращает 404
и не запускает ту же операцию заново. На диске сохраняется текущая задача.

«Остановить» завершает процесс и дожидается cleanup перед освобождением слота.
Незавершённый JSON не становится успешным результатом. Ошибка или остановка
не подменяет предыдущие готовые группы частичными. Повреждённый/отсутствующий
JSON, неподдерживаемая схема и ошибка CLI отличаются от валидного пустого
результата «Совпадения не найдены». Изменившиеся или не соответствующие
снимку каталога кандидаты отбрасываются; путям из JSON не доверяется право
изменять произвольные файлы.

Настроенный alias корня приводится к каноническому пути до запуска CLI;
тот же путь используется для ключей снимка и сверки отчёта. Это нужно,
поскольку Czkawka возвращает канонические абсолютные пути даже для запуска
через `images`-симлинк. Дочерние ссылки по-прежнему исключаются. Перед и после
режима проверяется доступность того же корня: исчезнувшая директория не
становится успешным пустым отчётом даже при exit code 0 утилиты.

При отказе карточка показывает конкретную причину и дальнейшее действие,
этап, известную версию CLI, режим и код завершения. Ошибка HTTP-соединения
с сервером выводится отдельно от ошибки самой утилиты. В завершённом пустом
результате видны количества подготовленных кандидатов, совпавших файлов,
отклонённых записей отчёта и пропущенных при подготовке файлов. Число
кандидатов — входной безопасный снимок, **не число реально декодированных
или просканированных CLI файлов**: итоговый JSON Czkawka этого не сообщает.
При подготовке каждый кандидат открывается только для проверки прав чтения
и сразу закрывается, без чтения изображения; одновременно открыт максимум
один такой дескриптор. Нечитаемые кандидаты отмечаются как пропущенные,
а отказ чтения всех кандидатов завершает задание ошибкой хранилища. Это
проверка доступа на момент снимка, не разбор всех последующих предупреждений
декодера: код 0 и итоговый JSON не раскрывают каждую внутреннюю ошибку CLI.
При частичном пропуске сводка доступна под «О последнем поиске» рядом с группами.
Идентификатор задания в карточке совпадает с безопасным отпечатком в логах;
пути и сырой вывод процесса в неё не попадают.

Точные и похожие группы подписаны отдельно. Точный режим проверяет содержимое,
а не имя, размер или время файла. Разное сжатие, EXIF и разрешение могут дать
похожие снимки с различающимися байтами. Сходство не является вероятностью
«одинаковые на 99%» и не гарантирует обнаружение после сильного кадрирования.

Повторные группы с одинаковым набором ID/версий объединяются независимо от
порядка участников и режима поиска. Если тот же набор найден как точные и
похожие копии, остаётся одна группа «Точные копии». Более широкая похожая
группа с дополнительными файлами сохраняется отдельно: одинаковые и лишь
похожие файлы не приравниваются. Нормализация выполняется в worker-isolate
после поиска и при чтении сохранённого результата; просмотр не переписывает
`job.json`. Восемь побайтно одинаковых файлов дают одну группу из восьми.

В группе может быть два и более файла. Сравнение показывает список до 10
карточек: целый кадр с индивидуальным zoom/pan, имя/путь, размер и разрешение.
Если участников больше, кнопки страниц позволяют просмотреть остальных;
выбор сохраняется между страницами и группами. Автоматического выбора нет.
Чекбоксы выбирают файлы, а общая кнопка «В корзину» **всегда** открывает
подтверждение: количество и первые 10 имён. Отмена не отправляет файловую
команду. Галерея и просмотр одного файла требуют такого же подтверждения.
После списка при большем выборе указано, сколько ещё файлов переместится
в корзину; ограничение списка не ограничивает состав операции.

Для смонтированных карточек лениво читаются сведения, не более четырёх
HTTP-запросов метаданных одновременно на подключение. Смена страницы и закрытие
сравнения отменяют ненужные запросы, включая ожидающие своей очереди;
подробный EXIF находится только в просмотре одного файла. Во время запроса
показана «Загрузка сведений…»; после отказа — причина и отдельная кнопка
«Повторить загрузку сведений». Ошибка изображения имеет другую кнопку —
«Повторить загрузку изображения». Дата съёмки и время изменения файла
подписываются раздельно. Разрешение из отчёта Czkawka используется как fallback;
ответ metadata обновляет карточку сразу и кешируется по ID/версии.

Разрешение сравнивается по `width × height` во **всей актуальной группе**,
включая другие страницы. В каждой непустой группе есть **один** рекомендуемый
экземпляр: максимум числа пикселей, при равенстве — первый в порядке группы.
Размер файла не разрешает равенство. Рекомендованное разрешение зелёное,
остальные равные максимумы и промежуточные — жёлтые; минимумы при различающемся
числе пикселей — красные. Если все разрешения равны, первый зелёный, остальные
жёлтые, даже при разных пропорциях кадра. У точных копий всегда рекомендован
первый: их содержимое равноценно, поступление metadata не меняет предпочтение.
Постоянных подписей «Одинаковое/Максимальное/Минимальное разрешение» рядом с
размерами нет; пояснения доступны в tooltip и семантике для озвучивания.
Рекомендуемая карточка целиком выделена зелёной рамкой толщиной 3 px и лёгким
оттенком фона. Плашка «★ Рекомендуется сохранить» находится сверху карточки,
перед изображением и сведениями; причина доступна в tooltip плашки и разрешения.
Внизу сведений повторной подписи нет. Это отличает кандидата без опоры только
на цвет числа пикселей. При уточнении рекомендации плашка и рамка переходят
на другой файл, сохраняя состояние изображения, запросы и ручные чекбоксы.

Отсутствующая, неполная или неположительная пара размеров не участвует в
сравнении пикселей. В похожей группе с неполными данными рекомендован максимум
из известных разрешений с явной пометкой предварительности; если неизвестны
все — первый с пояснением об отсутствии размеров. Прочие неизвестные размеры
нейтральны. Для похожих групп размеры отчёта доступны без чтения невидимых
файлов. Уточнение metadata может сменить предварительного кандидата, но равенство
разрешается по исходному порядку группы, а не по порядку ответов или текущей
странице. Индексы числа пикселей и позиций уточняются за логарифмическое время;
кадры, выбор чекбокса и тики поиска не вызывают полного пересчёта группы.

«★ Рекомендуется сохранить» — рекомендация по разрешению/порядку, а не
оценка резкости, артефактов, реальной детализации или программного увеличения.
Ни выбор формата, ни байты не используются как доказательство качества.
Размер файла всегда показан в мегабайтах (MB/МБ, 1 MB = 1 000 000 байт),
с двумя знаками после десятичного разделителя текущего языка. Ненулевой размер
меньше 0,01 MB показан как «< 0,01 МБ», нулевой — «0,00 МБ»; крупные размеры
также остаются в MB. Точное целое число байт доступно в tooltip. Это общее
представление сведений просмотра/корзины, карточек дубликатов, списка
подтверждения и суммарного объёма перед окончательным удалением. Сравнение
и команды продолжают использовать исходные байты без округления. Минимальный при различающихся размерах
отмечен «Занимает меньше места; это не оценка качества». Эта отметка нейтральная,
равные размеры не выделяются. Рекомендация не меняет чекбоксы, решения о корзине
или защиту последнего экземпляра. Декодирование изображений, зависимости,
группировка Czkawka не менялась; отличие параметров похожего поиска описано выше.

Статус `GalleryDuplicateJob` пока передаёт все найденные группы клиенту.
При открытии и переходе к следующей группе отдельный запрос проверяет её
участников на backend по наличию в оригиналах и версии файла. Недоступные
участники исключаются; группа с менее чем двумя актуальными файлами
пропускается. Из группы из трёх файлов после удаления одного показываются
оставшиеся два. Сервер сам ищет следующую подходящую группу, поэтому клиенту
не нужен запрос на каждую пропущенную. После переноса проверка повторяется.
После последней группы доступен повторный просмотр.

`duplicates/job.json` хранит нормализованные результаты поиска (группы и
участников), состояние/время задачи и диагностику Czkawka: кандидатов,
совпадений, пропусков и ошибок. Решения пользователя, число принятых решений
и журнал операций в него не записываются. Результат не переписывается при
просмотре и переносе в корзину: завершённость выводится из наличия файлов.
Ручной пропуск группы и выбор чекбоксов живут только в открытом экране;
после его закрытия доступные группы можно просмотреть заново.

Панель проверяет оставляемый экземпляр по текущему снимку группы. Файловые
операции backend независимы от поиска дублей: проверяют ссылки и ревизии
каждого файла и используют общий сервис корзины. Они не изменяют и не
инвалидируют сохранённый результат поиска; изменившиеся группы пользователь
актуализирует новым поиском. Серверная проверка существования последней копии
при переносе не выполняется. Czkawka не получает команд удаления.

## Операции HTTP

Ниже `<base>` означает `/cache/<code>/v2`; код доступа тот же, что у каталога.
JSON-ответы команд и metadata имеют `Cache-Control: no-store`, каталоги —
`private, no-cache`. Возможности:
`metadata`, `mutations`, `rotation`, `trash`, `hidden`, `duplicates`; прежние
`thumbnails`, `revisionedOriginals` и `refresh` сохраняются. Наличие capability
не гарантирует наличие внешней утилиты или поддержку каждого формата.

| Запрос | Результат |
| --- | --- |
| `POST <base>/rotate` | `GalleryRotateRequest` → `GalleryMetadata` с новой версией |
| `POST <base>/operations` | `GalleryOperationRequest` → `GalleryOperationResult` с состоянием каждого элемента |
| `GET <base>/duplicates` | Текущая `GalleryDuplicateJob`: ID, состояние, время, режимы, группы, пропуски и ошибка |
| `GET <base>/duplicates/<jobId>/groups/<index>` | `GalleryDuplicateGroupPage`: первая группа с ≥2 актуальными файлами начиная с index; фактический index и group, либо group=null/index=число групп в конце |
| `POST <base>/duplicates` | `GalleryDuplicateStartRequest` → состояние запущенной задачи |
| `POST <base>/duplicates/<jobId>/stop` | Остановка указанного поиска; тело не требуется |

Поле `rotation` принимает `left`/`right`, `action` — `trash`/`restore`/`purge`/`hide`/`unhide`,
а `modes` — значения `exact`/`similar`. Примеры тел запросов:

```json
{"operationId":"rotate-001","section":"published","mediaId":"media-id","sourceRevision":"revision","rotation":"left"}
```

```json
{"operationId":"trash-001","action":"trash","items":[{"section":"published","mediaId":"media-id","sourceRevision":"revision"}]}
```

Для `restore` и `purge` используются ссылки с `section: trash`, ID и версией
записи корзины. Удаление выбранных дубликатов использует тот же запрос без
ссылки на задачу поиска. Сырые пути не являются входом файловой команды.

Раздел задаётся только в каждой ссылке `items[]`; общего fallback в запросе нет.
`hide` принимает published, `unhide` — hidden, `trash` — published или hidden,
`restore`/`purge` — trash. Поворот доступен только published. Восстановление
из hidden и trash всегда возвращает файл в published. Смешанный пакет удаления
дубликатов содержит ссылки обоих исходных разделов.

```json
{"operationId":"dedup-trash-001","action":"trash","items":[{"section":"hidden","mediaId":"media-id","sourceRevision":"revision"}]}
```

```json
{"operationId":"search-001","modes":["exact","similar"]}
```

В `GalleryOperationResult.items` возвращаются исходные `section` и `mediaId`,
`state` (`succeeded`/`failed`), типизированная `error` и при наличии
`destination` (`GalleryMediaRef` после переноса в hidden/trash) или `restoredPath`.
Undo перечитывает каталог раздела destination и использует актуальную ссылку.
HTTP 200 пакетной операции не означает успех всех файлов.
Закрытие HTTP-запроса не отменяет уже применённую файловую операцию;
автоматической повторной отправки изменений нет. Клиентское ожидание может
закончиться раньше серверной обработки. Для файловых команд `operationId`
сопоставляет запрос, ответ и логи; результат не сохраняется. После ошибки
клиент обновляет список и следующее действие создаёт новую команду.
Поворот также не сохраняет результат или журнал на диск. `operationId` нужен
для связи запроса и логов; каждый запрос проверяет `sourceRevision`.
После успешной замены повтор со старой версией получает `revisionMismatch`
и не поворачивает файл ещё раз. После ошибки клиент запрашивает актуальный
каталог; следующее явное действие использует новую команду и текущую версию.

| HTTP | Типизированная причина |
| --- | --- |
| 400 | `invalidRequest` |
| 403 | `forbidden` |
| 404 | `notFound` |
| 409 | `revisionMismatch`, `conflict`, `cancelled` |
| 413 | `outputLimitExceeded` |
| 415 | `unsupported` |
| 422 | `processingFailed` |
| 429 | `busy`; `Retry-After: 1` |
| 503 | `unavailable`; `Retry-After: 1` |
| 504 | `timeout` |

Ошибка передаётся JSON-объектом `{"code":"..."}`. Ошибки отдельных файлов
также возвращаются в пакетном результате. В `GalleryDuplicateJob` используется
состояние `idle`, `running`, `stopping`, `completed`, `cancelled`, `failed`
или `interrupted`; наличие ошибки не трактуется как отсутствие совпадений.

`GalleryDuplicateJob.diagnostics` — необязательный объект; старый backend
может его не возвращать. Он содержит `stage` (`snapshot`, `versionProbe`,
`scanning`, `validation`, `persistence`), необязательные `failureReason`,
`toolVersion`, `exitCode`, `mode`, флаг `rootAliased` и счётчики `candidateCount`,
`matchedFileCount`, `rejectedResultCount`, `snapshotSkippedCount`.
`matchedFileCount` считает уникальные принятые файлы, а не сумму вхождений
в обеих группировках. Неизвестные диагностические этапы/причины разбираются
как `unknown`, неизвестный диагностический режим — как `null`. Основные
поля статуса и режимы команд сохраняют строгий прежний контракт.

После завершения CLI результат целиком читается через `readAsString()` и
разбирается в worker-isolate. `maxResultBytes` и `maxStateBytes` удалены;
структура JSON, пути и версии файлов по-прежнему проверяются. `job.json`
сохраняется целиком через временный файл и rename. Чтение требует памяти для
полного JSON; отдельные лимиты HTTP-транспорта клиента в таблице сохраняются.

Очередь каталога не удерживается на время обработки CLI или поворота; файловые
изменения сериализуются отдельно. Лимит времени дочерней команды не означает
такого же предела общего wall time: завершение процесса и pipes входит
в обязательный cleanup. После TERM через 200 мс при необходимости отправляется
KILL; ожидание закрытия pipes ограничено 2 с. Лимиты новых служб заданы
параметрами реализации; дополнительных полей конфигурации `gallery` для них
пока нет. Эти параметры не являются строгим
лимитом RSS утилиты и не подтверждают безопасность параллельной нагрузки на RaPi5.

Эти лимиты не являются общим ограничением RPC/upload/всего shelf. Backend
генерирует миниатюры через `FfmpegThumbnailWorker` без isolate на каждый запрос:
одна задача — один FFmpeg, до четырёх задач одновременно. Число потоков
decoder/filter/encoder ограничено 1. Входной формат определяет FFmpeg; набор
поддерживаемых форматов зависит от установленной сборки. Проверены JPEG, PNG,
GIF, WebP и seekable MOV. Пути передаются списком аргументов без shell,
`-protocol_whitelist file,pipe` запрещает сетевые протоколы. Прямое чтение
файла позволяет демультиплексору перемещаться по контейнеру видео.

Размер файла проверяется через stat до и после FFmpeg, decoder `max_pixels`
ограничивает размеры кадра. Это не строгий предел фактически прочитанных байтов
при внешнем росте файла и не общий предел RSS процесса. Публикация дополнительно
проверяет актуальность источника, а работа ограничена deadline. Автоматический
JPEG lowres больше не выбирается через probe; большие кадры декодируются нативно,
что может увеличить память относительно предыдущего пути. После EXIF выполняются
точный центральный crop, scale без upscale, наложение фона, `thumbnail` и JPEG.
Фильтр буферизует до `frameSelectionFrames` уменьшенных кадров YUV 4:2:0;
память растёт с размером группы и вариантом enum, сверх памяти самого декодера.

Результат всегда JPEG `mjpeg`, `yuvj420p`, без метаданных ориентации. Публичная
шкала качества 1..100 отображается в qscale 31..2 (60 → 14); это не прежняя
шкала Dart image. В Dart поступает только ограниченный encoded JPEG; hash
готового JPEG вычисляется MD5 с передачей управления event loop; он служит
ETag и checksum при восстановлении дискового кеша. Крупные, повреждённые и
неподдерживаемые источники дают ошибку плитки, оригинал остаётся доступен.
Клиентский предел тела 200 MiB действует также для fullscreen.

Нужен `ffmpeg` из PATH; проверены 5.1.9 и 8.0.1. Фон рисуется в RGB:
`drawbox replace=1` на RGBA приводил к SIGSEGV в FFmpeg 5.1.9. Пакет `ffmpeg`
включён в зависимости DEB.
При отсутствии executable журнал содержит его имя, API возвращает 503;
Dart fallback отсутствует. Codec-тесты обязательны и не пропускаются молча.
Один deadline включает запуск, decode, выбор кадра, encode и hash.
Отмена/timeout/shutdown дожидаются завершения ребёнка и stdin/stdout/stderr,
при необходимости TERM через 200 мс усиливается до KILL. Cleanup может занять
время сверх deadline; следующий worker не получает слот раньше. Учтена отмена
во время `Process.start`. Застрявшее системное файловое I/O может задержать cleanup.
Отключение HTTP-клиента до ответа не передаётся Shelf как немедленная отмена
ожидающей генерации: действуют worker/waiter deadlines и общие budgets.
Отмена уже начавшегося файлового тела освобождает его FD и cache lease.

## Настройки gallery

Это отдельная секция корневой конфигурации рядом с `slideshow`, `welcome` и
`web` (поле `webServer` в Dart). Значения ниже — defaults; при компактном сохранении они опускаются.
Сохранённые изменения вступают в силу после перезапуска рамки.

```json
{
  "gallery": {
    "maxConcurrentMediaStreams": 12,
    "thumbnail": {
      "sizes": ["small", "medium", "large"],
      "jpegQuality": 60,
      "backgroundColor": "#202020",
      "frameSelectionFrames": 30,
      "maxWorkers": 4,
      "maxQueued": 8,
      "maxWaiters": 32,
      "cacheMaxBytes": 536870912,
      "cacheMaxEntries": 2048,
      "timeoutSeconds": 20
    }
  }
}
```

| Поле | Допустимые значения |
| --- | --- |
| `sizes` | Имена `GalleryThumbnailSize`: `small`=256, `medium`=512, `large`=1024; произвольных размеров нет |
| `jpegQuality` | Целое 1..100 |
| `backgroundColor` | Непрозрачный RGB, строка `#RRGGBB` |
| `frameSelectionFrames` | Целое 2..120, размер начальной группы для `thumbnail` |
| `maxWorkers` / `maxQueued` / `maxWaiters` | Целые 1..32 / 0..1024 / 1..4096 |
| `cacheMaxBytes` / `cacheMaxEntries` | Целые 1..1099511627776 байт / 1..1000000 объектов |
| `timeoutSeconds` | Целое 1..600; waiter ждёт не меньше 30 с и worker timeout + 10 с |
| `maxConcurrentMediaStreams` | Целое 1..128 |

Отсутствующие/неверные значения возвращаются к default соответствующего поля.
Неизвестные размеры пропускаются, дубли убираются, порядок нормализуется;
пустой список или список только неизвестных значений означает все три defaults.
В бизнес-логике используются значения enum, строки — только на границе JSON.
Настройки относятся к серверу; клиентские очереди и memory/encoded LRU сохраняют
прежние бюджеты. `maxOutputBytes` не больше 8 MiB и заданного дискового бюджета.

Кеши публикуют только завершённые файлы. Eviction не удаляет payload, пока его
удерживает HTTP consumer/декодер. Native-кеш хранит SHA-256 ключи вместо URL с
кодом доступа, переживает restart и убирает собственные неполные файлы.
Корневой UI isolate получает дисковое владение неблокирующей `.owner.lock` до
startup cleanup. При занятом/недоступном каталоге и в worker isolates используется
ограниченный memory cache 24 MiB / 128 объектов. Общий store сохраняет один
дескриптор блокировки до завершения процесса; standalone close удерживает его
до освобождения decoder pins и окончания cleanup. Ошибка инициализации сначала
отменяет/дожидается отложенной очистки и только затем освобождает владение.
Попадание в native-кеш проверяет файл и обновляет порядок LRU только в памяти:
записи metadata и `fsync` перед показом нет. Standalone backing close объединяет
обновления времени доступа и сохраняет их атомарно без `fsync`; ошибка этой
необязательной записи не мешает освобождению ресурсов. Shared store не закрывается
при смене маршрута/сессии. При завершении процесса восстановленный порядок LRU
может быть приблизительным.

Новые payload и metadata клиентского native-кеша записываются полностью и закрываются перед
атомарным переименованием; явного `fsync` перед передачей декодеру нет. Это
восстанавливаемый кеш: после потери питания последние записи могут исчезнуть или
повредиться. При открытии проверяются metadata, identity, тип и длина файла,
остатки незавершённых записей удаляются. Ошибка декодирования инвалидирует
запись; явный повтор загружает её заново. Проверки checksum содержимого клиентского кеша нет,
поэтому повреждение с прежней длиной, которое принимает декодер, может остаться
незамеченным. Оригиналы на рамке эта политика кеша не затрагивает.
Decoded Flutter ImageCache — отдельный ресурс; лимит encoded LRU не означает
такой же предел общей RSS. Автоматической подготовки всей фототеки нет.

## Логи управления медиатекой

Диагностика является критерием приёмки файловых действий, метаданных и поиска:
записываются действие, запуск, итог, частичный результат,
отмена и повтор после неизвестного ответа. Итог содержит количества
успешных и неуспешных действий. Локальные тесты проверяют записи
рабочих logger вместе с результатом операции.

| Компонент | Диагностика |
| --- | --- |
| `GalleryFileOperations` | INFO: начало/итог команды, действие, success/failure; WARNING: частичный отказ, ошибка пути или вспомогательного кеша; FINE: отдельный файл, раздел, безопасный тип отказа, сканирование индексов и прямой lookup. |
| `GalleryCatalogService` | FINE: markDirty, начало/итог scan, количество, изменение снимка; запись 32-байтовой метки только при создании/инвалидации. WARNING: повреждённая метка или безопасный тип/OS-код отказа её чтения/записи. |
| `GalleryMediaTools` | INFO: начало, итог/отмена поворота, направление и выбранная утилита; FINE: metadata/cache и отмена чтения; WARNING: типизированный отказ или изменение прочитанного EXIF JPEG без значений тегов. |
| `GalleryGroupComparisonBloc`, `GalleryFilePathBloc` | FINE: открытие/закрытие сравнения, число известных разрешений, полнота, число равных максимумов, индекс кандидата и причина рекомендации; пропуск metadata чужой версии; раскрытие пути с глубиной. WARNING: отклонённый неотносительный путь без его содержимого. Сравнение не пишет INFO на каждый файл. |
| `GalleryDuplicateSearch`, `GalleryDuplicatesBloc` | FINE: `searchOptionsOpened/Confirmed/Cancelled` для локального черновика режима, `selectionCleared` с количеством, `previousSelectionRestored` с безопасным jobId и количеством актуальных решений. Начало/итог/отказ/остановка задания и файловые операции используют INFO/WARNING-сводки; имена файлов и пути в эти записи не попадают. |
| `GalleryDuplicateService` | INFO: режимы, запуск и итог режима/задачи, количества групп/файлов, безопасный `imageFilter=Lanczos3` для похожего режима, stop/cancel; WARNING: отказ/лимит. Опрос состояния не создаёт INFO на каждый тик. |
| `ProcessGalleryToolRunner` | FINE: запуск/завершение/отмена процесса и exit code; WARNING: timeout, лимит вывода и ошибка. Аргументы и stdout/stderr не выводятся. |
| `GalleryManagementRoutes` | Безопасная категория маршрута, HTTP status/типизированная ошибка, без авторизованного URL. |
| Bloc галереи и `GalleryManagementRepository` | Запрос/принятие подтверждения с token/action/count, отмена и отказ устаревшему подтверждению; запуск/итог действия, количество файлов, частичный отказ и повтор. Metadata/cache/polling на FINE. Данные состояния/событий целиком не печатаются. |

На INFO используются сводки на операцию, не строка на каждый файл коллекции
из 50 000+ медиа. Для подробностей включается FINE либо ALL; обычная отмена
не выдаётся за аварийный отказ. Новые логи управления не включают код доступа,
полный URL, имена/пути файлов, GPS, полный EXIF и сырой вывод утилит.
`operationId` в логах отсутствует; это поле API сохраняется для проверки
контракта команды. Выводимые клиентом ID заданий имеют вид
`id-<первые 12 hex SHA-256>`, без недоверенной строки целиком.

Backend пишет эти записи в стандартный журнал службы, клиент — в свою консоль.
Для установленной рамки уже после отдельно согласованного запуска:

```sh
journalctl -u dslideshow --since '10 minutes ago' --no-pager
```

Локальные VM-проверки диагностики выполняются командами из
[руководства тестов](testing.md). Получение журналов устройства в текущую
локальную проверку не входит.

`backend/bin/web_server_test.dart` эмулирует web-isolate с `FakeRemoteService`,
использует тот же **`log.web`**, что и настоящая служба, и помечает записи
`web-local`. Уровень `log.main` этим стендом больше не выбирается.
После изменения настроек или кода backend процесс нужно перезапустить;
hot reload клиента его не обновляет.

Стенд по-прежнему включает службу через 1 секунду после инициализации;
авторизация WebSocket также сохраняет существующую задержку 1 секунду.
Лог начала авторизации содержит `delayMs=1000`. Эти интервалы не следует
путать со временем сканирования каталога или создания первой миниатюры.

На INFO видны выбранный уровень логов, изменение enabled, готовность HTTP
listener и жизненный цикл WebSocket/auth без кода доступа. При FINE/ALL
`GalleryManagementRoutes` пишет одну короткую строку результата catalog, refresh,
original или metadata; `WebService` — thumbnail. Указаны HTTP status,
а при отказе — код причины и безопасный
тип ошибки. `_GalleryRequestTrace`, идентификаторы `request=web-N`, фазовые
записи и замеры времени удалены. Потребители медиа по-прежнему освобождают
lease при завершении или отмене выдачи. Cold/warm кеш, очередь и ошибки
генератора миниатюр видны в `ThumbnailService`.

Для запуска из каталога backend:

```sh
dart run bin/web_server_test.dart
```

У поиска дублей дополнительно выводятся `stage`, `mode`, `reason`, известные
версия и exit code/class, количества кандидатов/совпадений/отклонений и
`rootAliased`. Эти данные позволяют отличить недоступную CLI, несовместимую
версию, падение процесса, ошибку формата, ограничение и отказ хранилища.
Сырой stdout Czkawka дочитывается без сохранения; аргументы с путями,
stdout/stderr и исключения с авторизованным URL не используются как текст
новых сообщений WebService/поиска.

## Диагностика на рамке

Галерея исполняется в web-isolate. В конфигурации выставьте уровень **Web** в ALL
(`"log": {"web": "ALL"}` — фрагмент существующей конфигурации), сохраните и
перезапустите приложение. Уровни main/hw_frame на неё не влияют.
Для следующего ручного запуска из консоли можно сохранить stdout и stderr:

```sh
cd /opt/dslideshow
./dslideshow.sh 2>&1 | tee /tmp/dslideshow-gallery.log
```

Откройте галерею и дождитесь ошибки/загрузки плитки. Если процесс уже запущен,
сначала завершите этот экземпляр: одновременно запускать две фоторамки нельзя.

| Категория | Диагностика |
| --- | --- |
| `WebService` | INFO: пути и активные настройки генератора; FINE: результат миниатюры, HTTP status, безопасный код отказа |
| `GalleryManagementRoutes` | FINE: результат чтения и команд с route/HTTP status; WARNING: неожиданный отказ с безопасным типом ошибки |
| `GalleryCatalogService` | FINE: сканирование и число записей; WARNING: повреждённые метаданные и ошибки watcher |
| `ThumbnailService` | INFO: восстановленный кеш и бюджет; FINE/FINER: очередь, объединение, cache hit/negative hit и генерация; WARNING: ошибки генерации/диска/инициализации |
| `FfmpegThumbnailWorker` | FINE: источник, размер, PID, время, завершение и отмена; FINER: executable и точный массив аргументов; WARNING: причина, exit code и stderr |
| `MediaFileResponder` | Ошибки открытия/чтения файла, включая обрыв уже начатого тела |

Неожиданные Dart-ошибки выводятся вместе со stackTrace. Причина FFmpeg пишется
после завершения процесса и закрытия pipes; при SIGSEGV это `exit=-11`, даже
если stderr пуст. Пример диагностической строки:

```text
[web] WARNING:FfmpegThumbnailWorker: FFmpeg failed source=".../photo.jpg" size=256 executable="ffmpeg" pid=... exit=-11 reason=decodeFailed stderr=""
```

Stderr читается с прежним пределом 64 KiB, в журнал попадает максимум первые
8192 символа с отметкой `[truncated]`. Пути и stderr экранируются; бинарный stdout
и код авторизации из URL в новые сообщения не записываются. Подробности остаются
в локальном журнале, HTTP по-прежнему возвращает безопасный тип ошибки.
Повтор сразу после отказа может попасть в negative cache (TTL 3 с): это тоже
видно при ALL и не запускает новый FFmpeg. Отмена, устаревшая revision и занятые
очереди отмечаются на FINE; сбои генератора/файлов — на WARNING.

На FFmpeg 5.1.9 найдено и исправлено падение `drawbox replace=1` на RGBA.
Фон теперь переводится в RGB, заполняется и накладывается на исходный RGBA.
Поведение прозрачности, EXIF и выбора кадра сохранено. Policy 4 обновляет URL
даже у открытого клиента со старым каталогом через существующий ответ 409.
[Сценарий, результаты контейнера и RaPi](../benchmarks/reports/gallery-ffmpeg51-diagnostics-2026-10-27/report.md).

## Визуальные критерии UX-правок

До реализации UX-изменения зафиксировать конкретные наблюдаемые признаки
результата: что пользователь должен сразу различать, где находится основной
акцент и какая информация остаётся видимой. Например, для рекомендации
дубликата критерий — заметная рамка всей карточки и верхняя плашка ровно
одного кандидата; одного зелёного числа разрешения недостаточно. Для списка
подтверждения — визуально отдельный блок каждого файла и читаемое имя без
повторения полного пути.

Подготовить небольшой реалистичный набор из двух-трёх файлов с длинными
похожими именами, совпадающими разрешениями и размерами. Использовать его
для проверки страницы и связанных диалогов, на которые распространяется
изменяемый сценарий: например, просмотра, нового поиска, переноса в корзину
или окончательного удаления. Простые имена вроде `a.jpg` не заменяют проверку
читаемости похожих имён с различающимися суффиксами.

Первую визуальную сверку проводить на первой законченной итерации интерфейса,
чтобы обнаружить неудачный акцент или лишний текст до дальнейших доработок.
Сопоставлять зафиксированные признаки с получившимся кадром в разрешённом
runtime или VM-рендере: наличие подписи в дереве виджетов не подтверждает её
заметность. При завершении повторно проверить те же признаки во всей
затронутой цепочке страницы и диалогов. Использовать только уже разрешённый
состав проверок; эта процедура сама по себе не разрешает браузер или устройство.

## Локальное покрытие управления медиатекой

Модели/JSON проверяются в `common/test/gallery_management_test.dart`.
Backend-проверки охватывают зеркальное дерево корзины и восстановление файлов,
конфликты имён и симлинки, реальные кодеки/EXIF/ICC, управление дочерним процессом,
JSON Czkawka и актуальность групп. UI-тесты проверяют строгий состав панели
выбора, ленивые метаданные и их отмену, поворот/версии, частичный отказ и Undo,
подтверждение trash/purge, отмену без HTTP-команды и отказ устаревшему
подтверждению. Сравнение проверяет первый ответ сведений, кеш, ошибки
и независимый повтор сведений/изображения, ожидание/остановку поиска
и защиту оставляемого экземпляра.
Проверки расположения охватывают обе формы пути, корень, буквальные имена,
скрытые предки, полное раскрытие и отсутствие абсолютного пути. Сравнение
проверяет экстремумы вне текущей страницы без фоновых metadata-запросов,
равенство числа пикселей, неизвестные размеры, уточнения metadata и версии,
независимость рекомендации от выбора/байтов и безопасные логи. Layout-smoke
в VM выполняется на EN 320 px с text scale 1.5; он не заменяет браузерную
визуальную проверку.
Новые проверки очистки используют компактные реальные файловые fixtures
и модельные запросы на границах размеров пакета; массовая физическая
библиотека для них не создаётся.
[Распределение покрытия и команды](testing.md).

Новые функции проверяются локальными unit/widget-тестами в VM. Эти проверки
не подтверждают запуск Web bundle, BrowserClient/CORS, физическое отключение
питания или влияние CPU/I/O дочерних процессов на плавность рамки. В текущей
работе пользователь согласовал только локальные проверки: браузер и устройство
не запускались. Аппаратная проверка новых операций остаётся отдельным
согласованным прогоном OpenGL; общая приёмка галереи ниже также остаётся открытой.

## Открытая приёмка

Состояние на 29.10.2026: полный A/B RaPi5/Wi-Fi, визуальная приёмка на устройстве
и FrameTiming UI не выполнены. Ограниченная LAN/CLI-диагностика выше их не заменяет.
Пригодность начальных четырёх FFmpeg workers для параллельной работы с фоторамкой
не подтверждена аппаратным сравнением. Новая навигация по папкам, pagination,
полная фоновая генерация коллекции и замена shelf не входят в реализованный объём.

Перед будущим A/B зафиксировать release baseline/candidate, одинаковые
SDK/engine/runtime, медиа, параметры и заранее выбранные пороги. Матрица включает
1k/10k/50k flat/nested, большие реальные неизменённые фото и независимые fixtures,
окно/DPR, cold/warm cache, быстрый/медленный/обратный scroll, resize/fullscreen,
смешанное видео, один/несколько клиентов и конкурирующее управление/RPC.

| Контракт | Критерий приёмки |
| --- | --- |
| Transport/leases и отмена | На ключ один transport, cap удерживается до конца body/cleanup, отмена видна серверу; pending ImageCache listener не удерживает ненужную сеть, повторный показ работает. |
| Viewport и повторные циклы | Demand ограничен viewport+prefetch, видимые задачи не голодают; после прогрева tasks/FD/memory выходят на plateau. |
| Генератор и серверные ожидания | Одновременный miss объединён; abort ожидающего клиента не удерживает работу сверх worker/waiter deadlines; ошибочная генерация не отравляет кеш. |
| Инвалидация и публикация | Замена во время hash/decode/stream, удаление, partial upload, crash/restart и forceInvalidate не публикуют старую revision; ресурсы освобождены. |
| Качество и совместимость | Фото/GIF/EXIF/alpha, zoom и video/seek/close сохраняют качество оригинала; Web/Linux, old/new server и CORS сохраняют смысл queue/revision/errors без storm. |
| Нагрузка и управление | Корректные 429/Retry-After, конечная нагрузка backend и сохранённая отзывчивость конфигурации/RPC; нет UX/resource регрессий. |
| Диагностические логи | Запуск, итог, частичный отказ, повтор и отмена связываются по безопасному ID; видны количества и код ошибки. INFO остаётся сводным при 50k+, URL с кодом доступа и содержимое EXIF не раскрываются. Отсутствие нужной диагностики не допускает завершённой приёмки. |

Собирать реальные bytes/cache tiers, TTFB/body p50/p95/p99, active/queued,
ошибки/отмены, CPU/RSS/HWM/FD/threads/I/O backend и workers, память/frame time
клиента и задержку RPC. Handler bytes не называть wire bytes; пропуски не заменять
нулями. Приёмка требует меньших байтов для той же последовательности просмотра,
подтверждённых cap/abort/bounds и улучшения наблюдаемой отзывчивости; одного RPS
или меньшего числа загруженных фото недостаточно.

Аппаратный прогон требует отдельно согласованного окна по
[руководству RaPi5](raspberry-pi-benchmarks.md), без автоматического расписания.
Изолированный GPU-стенд запускается только в OpenGL через supervisor с остановкой
и восстановлением службы; конкуренция с работающей фоторамкой — отдельный
согласованный сценарий. ОС, драйверы, firmware и flutter-pi не меняются.
Vulkan и 24-часовой прогон не входят в приёмку. При недоступности устройства
сохранить команды следующего прогона и оставить аппаратный статус открытым.
