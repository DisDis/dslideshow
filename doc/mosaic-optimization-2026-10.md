# Mosaic / MosaicFade: завершённое исследование Canvas-маски на RaPi5

Проверка 25.10.2026, release, OpenGL, экран 2560×1600 / DPR=1 / около 50 Hz.
Сетки 100×100 / 150×150 / 200×200, исходные JPEG до 8000×6000, GIF и H.264.
FixedAnimationController, расписание, seed, направления, fadeFraction, 8-битная
alpha, ближайшая фильтрация маски и качество исходных изображений сохранялись.
Flutter-pi, ОС и прошивка не изменялись; Vulkan и 24h не запускались.

Исследование завершено. Принятая реализация работает в production; разовые
точечные/треугольные пробы, их конфигурации и pixel-audit target удалены
из текущего стенда. Ниже сохранены измерения зафиксированных сборок,
ограничения и описание архивных вариантов.

## Где расходовалось время

Исходный Canvas-путь для каждого кадра вычисляет alpha каждой ячейки,
заполняет массив цветов и вызывает `drawRawAtlas` для 10–40 тысяч квадратов.
Маленькая маска затем применяется через ShaderMaskLayer к целому слайду,
включая Texture/RepaintBoundary. Полноэкранный путь композиции уже сохранён
без изменений; исследуется именно построение маски.

На статических фото вывод близок к пределу дисплея: около 2.1 s на переход
с номиналом 1000 ms и фиксированным контроллером. Поэтому важен запас
UI-времени, а не только FPS. FrameTiming raster включает ожидания native
renderer/вывода и не является чистым временем GPU; сокращение UI-времени
может сопровождаться большим временем ожидания на raster-потоке.

Стенд исследования сравнивал неизменённый Canvas atlas, существующий shader
backend и две пробы `MosaicProbe-vertices-*` / `MosaicProbe-points-*`. Оба backend
маски работали внутри OpenGL. Пробы сохраняли размер маски и alpha. Треугольник
покрывал центр одного пикселя; точка размером 1 с выключенным antialias также
рисовала ровно один пиксель маски. Экранные ячейки и оригиналы не объединялись
и не уменьшались.

## Кандидат: группы точек с точной alpha

1. Порядок индексов по `startTimes` кешируется в неизменяемом расписании.
   Canvas вызывает `prepareCanvasOrder()` в `MosaicFadeEffect.prepare()`;
   сортировка завершается до запуска анимации. Shader не создаёт этот порядок.
2. Координаты центров пикселей маски записываются один раз в Float32List.
3. В отсортированном порядке `alphaAt(index, progress)` монотонна. Двоичный
   поиск находит конец группы с одинаковой alpha, используя **исходную функцию**
   с прежним округлением и обработкой равенства порогу.
4. Прозрачные ячейки пропускаются, остальные рисуются группами `drawRawPoints`.
   До одного draw для бинарной Mosaic, до 255 ненулевых групп для MosaicFade.
5. Размер маски, ImageShader matrix, пограничный сдвиг, nearest sampling,
   blend mode и ShaderMaskLayer сохраняются. Shader backend получает ту же
   текстуру порогов; временные atlas-массивы нужны только при её загрузке.

Поиск alpha требует порядка 255·log(N) проверок вместо N в худшем случае.
Это не оценка всей отрисовки: копирование/обработка координат native/GPU
по-прежнему зависит от количества видимых точек. Подготовка требует сортировки
O(N·log(N)); её стоимость измеряется отдельно. Прогресс, пороги и fade не
квантуются заново, скрытые кадры и дополнительные временные шаги не вводятся.

## Проверки

Замороженная исходная реализация хранится только как регрессионный эталон
в `dslideshow_flutter/test/support/atlas_reference_mask.dart`. В основном
приложении нет диагностических режимов или benchmark-инструментации.

Пиксельные тесты проверяют бинарную/плавную маску, все пять направлений,
сетки 1 / 100 / 150 / 200, fadeFraction=0 / .3 / 1, равные пороги,
округление alpha, прозрачные и перекрывающиеся виджеты. Полные 2560×1600 кадры
сравниваются с atlas; отдельно проверяются сохранённые RenderObject при
обратном прогрессе, смене расписания, размера и backend, освобождение ресурсов.

На устройстве архивный набор `mosaic-visual` сохранил 21 позицию каждого
из двух эффектов **на каждой из трёх сеток** и два эталона A/B. В `audit/*.json`
полные raw RGBA кадры представлены SHA-256; PNG-превью служат для просмотра.
В той серии исправлен пропуск всех сеток кроме первой в visual audit. Обычные
captures 0/50/100% проверяли только первую сетку.

## Подтверждённые результаты

Контрольные сборки выполнялись в порядке кандидат → baseline, с одинаковым
`mosaic-confirm.json`, одним прогревом и тремя повторами. На фото оба варианта
близки к 50 Hz; выигрыш здесь — снижение UI-времени и увеличение запаса до бюджета кадра.

| Эффект | Сетка | UI p95 было → стало, ms | Изменение UI |
| --- | ---: | ---: | ---: |
| Mosaic | 100×100 | 1.132 → 0.198 | -82.5% |
| Mosaic | 150×150 | 2.756 → 0.342 | -87.6% |
| Mosaic | 200×200 | 3.915 → 0.440 | -88.8% |
| MosaicFade | 100×100 | 1.609 → 1.173 | -27.1% |
| MosaicFade | 150×150 | 3.353 → 1.786 | -46.7% |
| MosaicFade | 200×200 | 5.156 → 2.438 | -52.7% |

Время перехода на фото осталось около 2.1 s; на GIF — около 4.0–4.1 s.
Устойчивого выигрыша wall time в этих сценариях нет. UI p99 и максимумы
также проверены и доступны в JSON/CSV; рост FPS из снижения UI-времени
автоматически не следует. Большие фото декодируются в полном разрешении.

Цена подготовки: сортировка Canvas занимает приблизительно 4 / 10 / 20 ms
для 100 / 150 / 200. Она выполняется один раз в prepare, кешируется и
не повторяется на шагах анимации. Это дополнительная стоимость подготовки,
а не бесплатное устранение работы; её особенно важно измерять при дальнейшем
увеличении сетки. Стоимость native/GPU-отрисовки всех видимых точек остаётся.

**На RaPi5 совпали все 126 полных контрольных кадров 2560×1600**,
два эффекта × три сетки × 21 позиция, плюс 12 исходных кадров A/B.
Монотонность и ограничение шага фиксированного контроллера проверяются
для каждого measured-повтора. Shader mask backend остаётся дополнительным
контролем OpenGL, Canvas — backend по умолчанию.

### Видео: повторное A/B и ограничения

Первую видеосерию (baseline → кандидат) дополнительно повторили в обратном
порядке с Baseline-контролями без эффекта. Сборки и runtime те же, общий
внешний `mosaic-video-confirm.json`, один прогрев и три повтора.

| Эффект, 200×200 | Сценарий | Исходный → новый, ms | Первая / обратная серия |
| --- | --- | ---: | ---: |
| Mosaic | photo-video | 3726.5 → 2394.0 | -38.2% / -35.8% |
| MosaicFade | photo-video | 3782.7 → 2947.6 | -20.4% / -22.1% |
| Mosaic | video-photo | 3805.1 → 2366.5 | -33.1% / -37.8% |
| MosaicFade | video-photo | 3711.2 → 3038.8 | -24.8% / -18.1% |

Baseline-контроли в повторе изменились менее чем на 0.3%. На 200×200 выигрыш
видео устойчив в обоих порядках: Mosaic около 33–38%, MosaicFade около 18–25%.
На 100×100 результат MosaicFade менее однозначен: UI p95 с видео вырос
примерно с 1.6–1.9 до 1.9–2.1 ms, даже когда wall time уменьшился.
В первом photo→video длительность практически совпала; в повторе получено
ускорение. Поэтому универсального выигрыша на каждой метрике/сценарии
не заявляется. UI-кадров сверх бюджета ~20 ms нет во всех 363 measured-повторах.

Нативных падений нет, но приёмка видеоплагина **не является успешной**:
сохранены MissingPluginException при cancel и GStreamer-CRITICAL.

| Видеосерия | Ошибки cancel | GStreamer-CRITICAL | Статус запуска |
| --- | ---: | ---: | --- |
| baseline-video | 0 | 14 | passed |
| candidate-video | 3 | 12 | failed |
| candidate-video-repeat | 4 | 15 | failed |
| baseline-video-repeat | 1 | 17 | failed |

Ошибка cancel воспроизвелась и в исходной сборке. Эти ограниченные выборки
не позволяют оценить её частоту или доказать отсутствие влияния таймингов.
Cleanup ошибки не превращены в успех и сохранены со стадией/каналом в сырых
архивах. Все measured-переходы завершились, шаги анимации плавные. Видео→видео
не проверялось; flutter-pi остаётся отдельной будущей работой.

### Итог проверки

11 коротких прогонов, 363 measured-повтора, нативных падений нет.
Восемь запусков успешны; три видеозапуска помечены failed из-за cleanup.
Максимальная температура 60.6°C, throttle_bits=0. Служба фоторамки восстановлена.

На момент исследования прошли 16 регрессионных тестов эффектов, 23 теста
стенда, 13 Python-тестов, локальный аудит прототипов и тест предпросмотра
конфигуратора. Web release сборка прошла. Анализатор стенда был чист;
в основном приложении оставались семь прежних info. Финальное ревью включало
точность alpha, обратный прогресс, владение ресурсами, общий кеш, явное
включение проб, полноту данных и ограничения видео.

## Историческое воспроизведение и текущие проверки

[Индекс отчётов](../benchmarks/reports/README.md) описывает сохранённые материалы.
Историческое A/B воспроизводится из frozen baseline/candidate в
[release-archives](../benchmarks/reports/mosaic-2026-10-25/release-archives/),
конфигураций и исходников стенда из raw/source-материалов этого исследования.
Нужны прежние медиа, SDK/engine и native runtime. Приведённые ниже имена
обозначают архивные наборы; в текущем `benchmarks/config/` их нет.

* diagnostics: 25 случаев, Canvas/shader/точки/треугольники, фото, три сетки.
* confirm: 13 случаев, Canvas/shader, два эффекта и контроль без эффекта.
* visual: шесть случаев, все три сетки, 126 полных контрольных кадров.
* media: 15 случаев, фото 48 Мп и оба направления GIF, сетки 100/200.
* video: восемь случаев, фото→видео / видео→фото, сетки 100/200, один декодер.
* video-confirm: те же восемь случаев плюс два Baseline-контроля; обратное A/B.

Везде, кроме visual, один прогрев и три measured-повтора, номинал 1000 ms.
Visual использовал один повтор без прогрева, номинал 500 ms. Видео→видео
в этот точечный набор не входило; известные native cleanup ошибки не скрывались.
Повторный video-confirm задавался общим внешним JSON после сборки тех же AOT;
обе сборки использовали один и тот же файл без перекомпиляции. Диагностические
пробы выполнялись только в эксперименте, например `MosaicProbe-points-MosaicFade`
использовал Canvas.

Текущий production-код проверяют штатные
[smoke](../benchmarks/config/smoke.json),
[standard](../benchmarks/config/standard.json) и
[visual](../benchmarks/config/visual.json); прежние экспериментальные варианты
они не включают. Сборка и OpenGL-запуск через supervisor с восстановлением
службы описаны в [аппаратном руководстве](raspberry-pi-benchmarks.md).

Текущие локальные регрессии:

```bash
(cd dslideshow_flutter && flutter test --no-pub test/mosaic_optimization_test.dart test/effect_regression_test.dart)
(cd benchmarks && flutter test --no-pub)
```

Артефакты находятся в `benchmarks/reports/mosaic-2026-10-25/`:
сырые архивы и SHA-256, идентификаторы обеих сборок, конфигурации, снимки
изменённых исходников, логи локальных проверок и итоговые JSON/CSV.

В каталоге отчёта сохранён `analyze.py` для повторного анализа raw-архивов.
Распакованные дубли и зависевший от них HTML удалены; итоговые JSON/CSV
и полные исходные измерения остаются доступными. Пара release-сборок находится
в `release-archives/` рядом с этими данными.

Следующее исследование — оставшаяся raster/выводная стоимость GIF/видео и
подготовка при дальнейшем росте сетки. Новые варианты должны сохранять
точную mask alpha, плотность, sampling и все шаги контроллера. Эти данные
не заменяют проверку длительной стабильности или отдельную приёмку RaPi4.
