# Обнаружение фоторамок в локальной сети из нативного config_app

Статус: **предложение к реализации**.
Последняя содержательная сверка с кодом: **29.10.2026**.
Открытый объём: реализация протокола, публикация рамок, поиск на странице login,
подготовка платформенных сборок и приёмка.

Цель — при открытии страницы login нативного DSlideshow Config на Windows,
macOS, Linux, Android или iOS автоматически найти фоторамки в доступном
сегменте локальной сети. На этой же странице показать результаты и кнопку
**«Повторить»**; выбранная рамка заполняет адрес подключения вместе с её
текущим web-портом. Пользователь вводит код и выполняет обычный вход.
Для поиска не нужны адрес первой рамки, интернет и центральный сервер.
Web в объём этого плана не входит.

## Механизм обнаружения

Предлагается **mDNS вместе с DNS-SD**: рамка публикует объявление о себе,
клиент запрашивает устройства определённого типа и получает их адреса,
порт и короткие метаданные. Это семейство механизмов Bonjour и Avahi;
DNS-SD задаёт перечисление экземпляров через PTR, адрес сервиса через SRV
и метаданные через TXT. См. [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).

mDNS использует UDP 5353 и multicast-адреса `224.0.0.251` и `ff02::fb`.
Обычный поиск ограничен локальным сетевым сегментом; роутинг между VLAN
сам по себе не переносит эти объявления.
См. [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762).

| Вариант | Применение в проекте |
| --- | --- |
| mDNS и DNS-SD | Основной поиск без знания IP и без дополнительного сервера. |
| Перебор IP и TCP-портов | Не включать в первую реализацию: маска сети неизвестна, IPv6 не допускает такой перебор, результаты требуют отдельного распознавания. |
| Собственный UDP broadcast | Не вводить второй протокол с собственной обработкой конфликтов, кеша и платформенных ограничений. |
| MQTT или облачный реестр | Возможное отдельное решение для разных сетей; текущий MQTT требует заранее настроенного брокера. |

«Все рамки» здесь означает включённые рамки с новой поддержкой discovery,
разрешённой публикацией и доступным multicast. Старая прошивка, изоляция
Wi-Fi-клиентов, firewall, сон ОС и разные VLAN могут ограничить результат.
Пустой список означает отсутствие обнаруженных объявлений, а не доказанное
отсутствие устройств. Ручной ввод адреса остаётся доступным.

## Исходное состояние проекта

* В [config_app](../../config_app/README.md) есть runner для Linux и Web.
  Runner для Windows, macOS, Android и iOS предстоит добавить. До обещания
  поддержки проверить сборку клиента и его транзитивные зависимости на каждой
  из пяти целевых ОС, включая импорты backend, платформенные сервисы и видео.
* [LoginBloc](../../config_app/lib/features/login/presentation/bloc/login_bloc.dart)
  и [LoginForm](../../config_app/lib/features/login/presentation/widgets/login_form.dart)
  уже отделяют ввод адреса и авторизацию. Поиск станет источником выбора адреса.
* [WebService](../../backend/lib/src/web_server/web_service.dart) предоставляет
  HTTP и `/ws`, слушает IPv4 и запускается по требованию.
  [WebServerConfig](../../backend/lib/src/web_server/web_server_config.dart)
  задаёт порт 8080 и `alwaysEnabled=false` по умолчанию.
* [Web-isolate](../../backend/lib/web_server.dart) существует независимо от
  открытого HTTP listener. Здесь можно разместить владельца публикации,
  сохранив действующее включение и выключение доступа к настройкам.
* `MqttConfig.deviceId` имеет общий default `dslideshow`. Он не подходит
  как уникальный идентификатор рамки для нового протокола.

## Разделение компонентов

| Компонент | Ответственность |
| --- | --- |
| `common` | Freezed-модели идентичности и метаданных, версия протокола, enum состояний, разбор и валидация. |
| `backend` | Постоянный ID рамки, публикация и обновление объявления через Avahi, минимальный HTTP-ответ об идентичности. |
| `config_app` | Нативный адаптер discovery, разрешения ОС, ограниченный реестр найденных рамок, Bloc поиска на login и подключение. |
| Платформенные runner | Разрешения, подписи, entitlement и сетевые настройки сборки. |
| `deb_factory` | Зависимости Avahi/D-Bus для рамки и проверка упаковки. |

Для клиента основной кандидат — [Bonsoir](https://pub.dev/packages/bonsoir):
он заявляет поддержку всех пяти нужных ОС. Его нативный адаптер скрывается
за интерфейсом `FrameDiscoveryProvider`. Сначала проверить на небольшом
прототипе выдачу TXT, адресов, изменений и ошибок разрешений. Поддержка ОС
в описании пакета сама по себе не подтверждает работу нашего приложения.

Для backend использовать Avahi через D-Bus из Dart. Flutter-плагин клиента
не переносить в backend-isolate или flutter-pi. В API Avahi есть регистрация
через `EntryGroup`, обновление TXT и освобождение регистрации:
[описание интерфейса](https://github.com/avahi/avahi/blob/master/avahi-daemon/org.freedesktop.Avahi.EntryGroup.xml).
Статический XML-файл в `/etc/avahi/services` не отражает жизненный цикл
процесса и состояние доступа, поэтому основная публикация должна быть динамической.

## Контракт объявления и идентичности

Предлагаемый тип сервиса — `_dslideshow._tcp`, домен — `local.`.
Имя экземпляра по умолчанию — `DSlideshow <короткий ID>`; пользовательское
имя может повторяться, идентичность от него не зависит. Перед выпуском
проверить имя типа по реестру IANA и оформить регистрацию при необходимости.

| Поле | Предлагаемый контракт |
| --- | --- |
| `id` в TXT | UUID конкретной установки рамки, постоянный при рестарте, OTA и смене IP. |
| `name` в TXT | Короткое отображаемое имя с ограничением длины. |
| `proto` в TXT | Версия discovery-протокола, первая версия — `1`. |
| `web` в TXT | Enum: `disabled`, `starting`, `ready`, `failed`; неизвестное значение отображается как неизвестное состояние. |
| `fv`, `bv` в TXT | Версии frontend/backend из `ApplicationInfo`. |
| SRV | Hostname рамки и фактический порт HTTP listener при `ready`; при выключенном доступе — порт из действующей `WebServerConfig.port`. |
| A и AAAA | Разрешённые платформой адреса с учётом сетевого интерфейса. |

Объявление присутствия публикуется всё время работы рамки, в том числе
при `web=disabled`. В этом состоянии SRV содержит настроенный порт,
но TCP listener может отсутствовать. Это явный контракт нашего типа сервиса:
карточка показывает «Доступ к настройкам выключен» и предлагает открыть
экран настройки на самой рамке. Поиск никогда не включает HTTP и не меняет код.
`ready` публикуется после успешного bind; TXT остаётся заявленным состоянием,
фактическая доступность проверяется при подключении.

Новый ID создавать до первой публикации и сохранять атомарно в отдельном
постоянном файле `device_identity.json` внутри `externalStorage`. У файла один
владелец в web-isolate: не добавлять конкурентную запись в общий `storage.json`
из нескольких изолятов. Ошибка сохранения не должна порождать новый ID на
каждый запуск или останавливать слайдшоу. Образ для клонирования распространять
без этого файла; импорт конфигурации другой рамки не переносит её идентичность.

В конфигурации предусмотреть `discovery.enabled` с default `true` и
`discovery.name` с default пустой строкой, означающей имя по умолчанию.
При содержательном изменении существующих моделей конфигурации применить
Freezed и штатную JSON-генерацию по правилам репозитория.

TXT содержит только публичные метаданные. Коды доступа, токены, MAC,
machine-id и конфигурация в объявление не попадают. Ограничить размер TXT
и каждого поля; отсутствующий/невалидный ID не заменять hostname.
Неизвестные дополнительные поля игнорировать, несовместимый `proto`
показывать отдельным состоянием без автоматического подключения.

### Изменяемый web порт

Поиск обращается к стандартному mDNS-порту UDP 5353. HTTP/WebSocket-порт
каждой рамки приходит в SRV-ответе и может отличаться от 8080 и от портов
других рамок. Поэтому клиент сначала обнаруживает сервис, затем получает
его host и port и только после этого строит HTTP/WS URI. Например,
объявление адреса `192.168.1.20` и порта `9091` даёт
`ws://192.168.1.20:9091/ws`. Диапазон портов для подключения — 1–65535;
невалидный или отсутствующий порт не заменяется на 8080.

Порт читать из действующей конфигурации при запуске рамки и использовать
в объявлении этого запуска. После изменения порта пользователь перезагружает
рамку; новый процесс сразу публикует объявление с новым портом. Отслеживание
изменений конфигурации и горячая смена SRV-порта не нужны. При ошибке bind
публиковать состояние отказа. После перезагрузки пользователь нажимает
«Повторить» на login и выбирает заново найденную рамку.

Для mDNS должен проходить UDP 5353; для входа и медиа — настроенный TCP-порт
рамки. Это отдельные сетевые условия: обнаруженная рамка может быть
недоступна для подключения из-за firewall на её web-порту.

## Автоматический поиск на странице login

В существующей [LoginPage](../../config_app/lib/features/login/presentation/pages/login_page.dart)
добавить блок **«Фоторамки в сети»** над полем адреса, индикатор поиска,
список результатов и кнопку **«Повторить»**. Поиск запускается автоматически
один раз при создании сессии страницы. Rebuild, смена темы, локали и ввод
текста не запускают его снова. Отдельного экрана выбора и обязательной
кнопки первого запуска не требуется.

Если ОС требует разрешение LAN, при первом открытии login в foreground
объяснить назначение доступа и инициировать системный запрос. При уже
выданном разрешении поиск начинается сразу. Время системного диалога не
сокращает окно поиска. При подтверждённом отказе остановиться и показать
действия повтора или открытия системных настроек, без цикла запросов.

Результаты поступают постепенно. Карточка содержит имя, короткий ID,
адрес с портом, версии и состояние доступа. Нажатие на готовую рамку
выделяет её и заполняет поле подключения URI с портом из SRV на этой же
странице. Поля имени пользователя и кода сохраняются; поиск и выбор
не отправляют код и не выполняют вход автоматически. При выключенном
доступе карточка объясняет действие на рамке и позволяет повторить поиск.

Поле ручного адреса остаётся доступным с самого начала, в том числе при
пустом результате и ошибке discovery. Поступающие объявления и повтор
поиска не перезаписывают введённый вручную адрес. Адрес подключения заполняется
при явном выборе карточки; специальная синхронизация поля при смене порта
рамки не требуется. Текст поля, выбранная карточка и URI в LoginBloc должны
оставаться согласованными.

Кнопка «Повторить» завершает старую сессию поиска и начинает новую, сохраняя
введённые реквизиты. Во время активного поиска или отправки формы кнопка
неактивна; повторные события не создают параллельных поисков. Успешный вход
и уход со страницы отменяют discovery; новый вход на login создаёт новую
сессию с автоматическим запуском.

`FrameDiscoveryRepository` управляет подпиской на найденные, обновлённые
и потерянные сервисы. Сначала получать объявления нужного типа, затем
разрешать их адреса и TXT с ограниченной очередью. Начальные пределы для
реализации: окно поиска 5 секунд после завершения запроса разрешений,
не более 4 параллельных resolve, 256 записей в реестре и 8 адресов на рамку.
Лимиты централизовать; превышение показывать как неполный результат.
Ни один таймаут не означает, что найдены абсолютно все устройства.

Повторы одного объявления и интерфейсов объединять по ID. При одинаковом
ID у разных hostnames показывать конфликт идентичности, исключая тихий
выбор произвольной рамки. Одинаковые имена при разных ID допустимы.
Повторный поиск заменяет сессию; поздние callbacks прошлой сессии игнорируются.
Во время поиска учитывать события удаления из нативного кеша. После остановки
поиска список становится снимком с временем наблюдения: через 30 секунд
помечать его устаревшим, не выдавая сохранённую запись за проверенный online.
Срок жизни DNS-записей обрабатывает провайдер; возраст снимка — правило UI.
Закрытие экрана, logout, смена сети и уход приложения в background завершают
подписки и resolve; возврат требует обновления устаревшего результата.
Ошибки stop обрабатываются, cleanup остаётся идемпотентным.

Новый `FrameDiscoveryBloc` внутри LoginPage и `StatelessWidget` блока поиска
используют Freezed-состояние
и enum: ожидание, запрос разрешения, поиск, результат, пустой результат,
подтверждённый отказ разрешения, недоступный провайдер, ошибка.
Пустой список не превращать в «нет разрешения»: часть ОС не даёт надёжно
прочитать этот статус. UI сохраняет возможность повторить поиск или перейти
в системные настройки. Подписи — в ARB, обычные widget-тесты — на `en`.

Для подключения использовать уже разрешённые IP из нативного API, порт SRV
и фиксированный путь `/ws`; собирать `Uri` структурно. Текущий backend слушает
IPv4, поэтому первая версия выбирает IPv4 и явно сообщает об отсутствии
совместимого адреса. IPv6 не конкатенировать в строку и не обещать до добавления
listener и приёмки scope ID для link-local. `.local` можно показать пользователю,
но возможность его разрешения HTTP-клиентом проверяется отдельно.
При нескольких IPv4 выполнять ограниченные попытки по адресам выбранной
рамки с общим deadline, сверяя ID перед передачей кода на каждом адресе.

Перед отправкой кода получить минимальный `GET /api/device` с небольшим
таймаутом, лимитом ответа и запретом redirect; сверить продукт, ID и версию
протокола с выбранной карточкой. Старый backend без этого endpoint доступен
через существующий ручной вход. Такая сверка выявляет смену адреса и ошибочный
сервис, но не обеспечивает криптографическую подлинность устройства: mDNS
и текущий HTTP/WS не защищают от активного участника локальной сети.
Нельзя автоматически отправлять сохранённый код новой карточке только по имени.

При смене уже подключённой рамки использовать существующую защиту черновика,
завершить прежнюю realtime-сессию и очистить данные устройства. Не смешивать
конфигурацию, галерею и код двух рамок. Потеря mDNS-объявления сама по себе
не разрывает исправное авторизованное соединение.

## Подготовка пяти платформ

| Платформа | Что включить в реализацию и приёмку |
| --- | --- |
| Windows | Добавить runner, проверить системный DNS-SD API и правила firewall для частной сети в упакованном приложении. Не требовать установки Apple Bonjour без необходимости выбранного адаптера. |
| macOS | Добавить runner, `NSLocalNetworkUsageDescription`, `NSBonjourServices` с `_dslideshow._tcp`, нужные network entitlement для выбранной sandbox-конфигурации; проверить подписанную release-сборку. |
| Linux | Сохранить существующий runner, описать зависимость от Avahi и системной D-Bus, различать отсутствие службы и запрет доступа к ней; проверить ограничения формата упаковки. |
| Android | Добавить runner и `INTERNET`. При target SDK 37+ объявить и запросить `ACCESS_LOCAL_NETWORK` до поиска и соединения; при меньшем target SDK не запрашивать это разрешение. Проверить NSD и переходы разрешений на реальном устройстве. |
| iOS | Добавить runner, `NSLocalNetworkUsageDescription` и `NSBonjourServices` с конкретным типом; проверить отказ, повторное разрешение и foreground/background на реальном iPhone. |

Apple описывает требования local network privacy и различия Bonjour и прямого
multicast в [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
Для поиска конкретного объявленного типа через Bonjour не закладывать прямые
UDP-сокеты и специальный multicast entitlement без необходимости.
Правила Android зависят от target SDK:
[Local network permission](https://developer.android.com/privacy-and-security/local-network-permission).
Для собственного списка всех рамок нужен общий доступ к LAN при target SDK 37+;
системный picker выбора одного устройства — другой UX.

Системные зависимости Linux и нативные механизмы выбранного пакета сверить с
[инструкцией Bonsoir](https://bonsoir.skyost.eu/docs/). Минимальные версии ОС
зафиксировать после проверки совместимости Flutter SDK и всего приложения.
Для текущих HTTP/WS и загрузки медиа отдельно проверить Android network security
configuration и Apple ATS выбранного транспорта; разрешение discovery само
по себе не подтверждает возможность подключения или проигрывания медиа.
Не отключать сетевые ограничения глобально как способ исправить поиск.

## Последовательность реализации

1. **Подтвердить платформенную основу.** Создать недостающие runner, проверить
   сборку и запуск минимального клиентского пути на пяти ОС. Прототипировать
   Bonsoir ↔ Avahi, включая TXT и ошибки разрешений. Исправить необходимые
   платформенные импорты, определить поддерживаемые версии и зафиксировать
   выбор адаптера. Не начинать с полной переработки остальных экранов.
2. **Описать и проверить общий контракт.** Добавить модели `FrameIdentity`,
   `FrameAdvertisement`, `DiscoveredFrame` и состояния; генерацию, независимые
   примеры TXT/JSON и тесты отсутствующих, неизвестных и повреждённых полей.
3. **Научить рамку объявляться.** Реализовать постоянный ID, динамическую
   публикацию Avahi и `/api/device`. Связать TXT с фактическими переходами
   `WebService`, обработать конфликт имени, рестарт Avahi и завершение процесса.
   Изменение сети, отказ D-Bus и отключение discovery не нарушают слайдшоу.
4. **Реализовать поиск клиента.** Добавить provider, repository, разрешения,
   ограничение очередей, дедупликацию, отмену, обновление и обработку потери сети.
   HTTP-проверку выполнять для выбранной рамки, без опроса каждого адреса сети.
5. **Встроить поиск в login.** Создавать FrameDiscoveryBloc в LoginPage с
   событием первого запуска; добавить индикатор, список, выбор и «Повторить»
   в LoginForm. Связать выбор с LoginBloc и полем адреса, сохранить ручной
   ввод и безопасную смену рамки. Обновить локализации и проверить отсутствие
   автоматической отправки кода и переноса черновика между устройствами.
6. **Завершить поставку и приёмку.** Обновить DEB-зависимости и документацию
   установки клиентов. Провести локальные проверки, затем сетевую приёмку
   нативных release-сборок на пяти ОС. Материалы приёмки хранить отдельно
   от описания действующего контракта.

Этапы 1–5 образуют минимальный функциональный объём. Заявлять поддержку всех
пяти ОС можно после этапа 6. QR, облачный реестр, поиск через VLAN и удалённое
включение доступа остаются отдельными возможностями.

## Проверки и критерии завершения

Локально дополнять существующие тесты авторизации и жизненного цикла;
fake подменяет нативный provider/D-Bus, а тесты выполняют рабочие repository,
Bloc, сериализаторы и HTTP handler. Включить следующие контракты:

* ID сохраняется после перезапуска, смены IP и обновления; ошибка записи
  не публикует временный ID; клон с повторным ID обнаруживается как конфликт.
* Две и более рамки появляются отдельными карточками; повторы с Wi-Fi/Ethernet
  объединяются; одинаковые имена, нестандартный порт, повреждённый TXT,
  несовместимый протокол и неподдерживаемый адрес обрабатываются явно.
* Открытие login запускает ровно один поиск; rebuild и ввод в форму не
  запускают дополнительные. «Повторить» начинает новую сессию, старые
  callbacks игнорируются; уход со страницы и успешный вход отменяют поиск.
* Выбор рамки заполняет видимое поле и URI подключения её адресом и SRV-портом.
  Проверить рамки с разными портами, например 8080 и 9091, а также новый запуск
  рамки с изменённым портом и её выбор после «Повторить». Горячая смена порта
  в объём не входит. Повреждённый порт не подменяется default.
* Автопоиск и повтор сохраняют ручной адрес, имя пользователя и код;
  discovery не отправляет код и не выполняет вход. Результат поиска не
  блокирует существующий ручной вход.
* `disabled` виден в поиске, не вызывает включения HTTP и отправки кода;
  `ready` появляется после bind; отказ запуска и закрытие доступа обновляют TXT.
* Разрешение, отказ, неизвестный статус, отсутствие Avahi, частичный resolve,
  устаревание снимка, повтор, отмена, смена сети и поздний callback дают
  ожидаемое состояние и освобождают ресурсы. Время в тестах виртуальное,
  события управляемые.
* HTTP-проверка отклоняет иной ID, redirect, большой/повреждённый ответ;
  существующая авторизация и ручной вход продолжают работать.
* Переключение рамки соблюдает защиту несохранённых правок; предыдущие запросы
  и соединения не меняют состояние нового устройства.

Диагностические компоненты: `FrameIdentity`, `FrameAdvertisement`,
`FrameDiscoveryRepository`, `FrameDiscoveryBloc`. INFO содержит начало и итог
по `scanId`, сводные количества; WARNING — безопасный
тип отказа; штатная отмена — обычный итог. FINE допускает ограниченные подробности
resolve. Тестами проверить связь начала/итога, отмену, восстановление и отсутствие
кодов доступа, авторизованных URL, сырого TXT и потока INFO на каждый пакет.

Сетевая приёмка требует минимум двух рамок и реальных нативных клиентов:
первый запуск без известного IP, запрет/разрешение LAN, смена DHCP-адреса,
одинаковые имена, разные web-порты и смена порта после перезапуска,
рестарт рамки/Avahi, выключение доступа, отсутствие интернета,
изоляция Wi-Fi и возврат приложения из background. Для iOS/macOS проверить
системный диалог в установленной сборке; эмулятор и VM-тесты не подтверждают
мобильный multicast и поведение системных разрешений.

Команды анализатора и VM-тестов выполнять из затронутых пакетов по
[руководству тестирования](../testing.md). После содержательных правок Flutter
применить hot reload/restart в подходящем разрешённом нативном debug-приложении.
Проверку влияния постоянно работающей публикации на ресурсы рамки и слайдшоу
включить в аппаратную приёмку по [руководству стенда](../raspberry-pi-benchmarks.md)
с действующими ограничениями OpenGL и восстановлением службы.

Перед закрытием плана провести финальное ревью поведения, гонок, cleanup,
логов и покрытия. Текущий контракт перенести в [руководство config_app](../config-app.md)
и [README backend](../../backend/README.md), команды установки — в README клиентов
и [deb_factory](../../deb_factory/readme.md), результаты — в датированную историю.
После переноса уникальных сведений удалить выполненный план и обновить ссылки.
