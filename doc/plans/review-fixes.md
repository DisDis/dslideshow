# Исправления по ревью трёх приложений

Статус: **предложен, ожидает согласования реализации**.
Последняя содержательная сверка: **30.10.2026**.
Основание: [ревью и baseline coverage](../history/review-2026-10-30/README.md).
Приоритеты пользователя: оставшиеся P1 → P2 → дефект теста → приоритетное покрытие.
Проверки только локальные; незакоммиченные изменения сохраняются, исходники не копируются.

## Уже принятые решения

Пользователь 30.10.2026 прямо подтвердил намеренное поведение:

* **R1:** media upload может записывать вне каталога медиа. Ограничение пути,
  запрет traversal/симлинков и изменение правил назначения в эту работу не входят.
* **R2:** `WebService` выводит код доступа в INFO. Эти записи сохраняются.

Это принятые риски, а не незавершённые исправления. Исключение касается именно
этих двух случаев: оно не разрешает записывать пароль Wi-Fi, другие секреты
или сырые транспортные исключения. Изменения очереди должны сохранять
существующий серверный контракт. Исторический baseline не перезаписывается.

## Этап 1 — оставшиеся P1

### R3. Безопасная диагностика Wi-Fi

Убрать передачу исходного `ProcessException` и аргументов команды в logger.
Ввести минимальную подменяемую границу исполнения, сохраняя рабочий WiFiService
предметом тестов. Логировать действие, ID, безопасный тип/exit code и итог;
не логировать пароль, командную строку и сырой stdout/stderr.

Приёмка: отказ запуска и ненулевой exit code диагностируются; синтетический
пароль отсутствует во всех полях записи logger. Проверки не запускают настоящий
`sudo`/`nmcli`. На этом этапе ещё не менять семантику подтверждения RPC из R7.

### R4. Восстановление загрузки слайдшоу

Обработать отказ обеих storage-операций и выход из `loadingNext`. Сохранять
показанный слайд; при первом запуске оставить существующий загрузчик.
Предлагаемая политика повторов: 1, 2, 4, 8, 16, затем не чаще раза в 30 секунд.
При неизвестном результате `storageNext` сначала сверять текущий элемент,
**не повторять автоматически продвижение**. Ошибка чтения повторяет чтение.
Пауза/сон приостанавливают повторы, закрытие отменяет таймеры и влияние поздних
ответов; возобновление возвращает возможность загрузки. Предусмотреть связь
первой ошибки, повторов и успешного восстановления в безопасных логах.

Приёмка: отказ любой RPC не оставляет блокирующую фазу, текущий кадр не теряется,
нет горячего цикла/двойного продвижения/позднего изменения закрытого Bloc.
Проверки используют виртуальное время, управляемые ответы и рабочий renderer
там, где важно сохранение сессии. Новый UX пустой медиатеки в этап не входит.

## Этап 2 — P2

### R5. Очередь загрузок панели

Резервировать слот до первого await/progress; одна попытка имеет собственный ID
и единственный запуск. Слот освобождается после завершения транспорта/cleanup.
Определить remove/close как настоящую отмену текущей работы, игнорировать
запоздавшие события старой попытки, retry создавать явно, без скрытой пересылки
мутаций. Читать содержимое только активных задач, не всю web-очередь заранее;
перенести файловый обход из синхронного UI в ограниченную асинхронную работу.
Пути/URI собирать штатными средствами с сохранением серверного поведения R1.

Приёмка: повторное добавление до progress даёт ровно по одной отправке на файл,
одновременно активны не более двух задач до cleanup; отмена, частичный отказ,
retry и close не оставляют клиентов/подписок и не меняют новую попытку.
Тесты реального Bloc и HTTP-клиента с управляемым транспортом/loopback;
малая выборка проверяет границы очереди и ленивое чтение. Логи — сводки операций,
подробности отдельных файлов на FINE, без секретных URL.

### R6. Выбор и отправка OTA в панели

Перенести выбранный файл, код, валидацию и жизненный цикл отправки в Bloc;
экран сделать StatelessWidget. Убрать `filePath!` и controller из builder.
До допустимого выбора действие недоступно; отмена выбора, повторный выбор,
rebuild, reset и close имеют явное поведение. Код остаётся строкой.
Использовать источник файла/поток, подходящий общей форме, вместо зависимости
общего UI от нативного `File/path`; ресурсы и поздние ответы принадлежат попытке.
Доработать подменяемость OTAClient для реальных локальных HTTP-проверок.

Приёмка: нажатие без файла безопасно; rebuild сохраняет ввод; отмена picker
не отправляет старый файл; загрузка/ошибка/отмена и закрытие освобождают ресурсы.
VM-тесты проверяют Bloc, виджеты и HTTP-контракт, но не DOM, browser picker,
настоящую отправку из браузера или установку DEB. Существующий серверный
HTTP-контракт сохранять; отдельный сценарий рамки описан ниже.

### Дополнение пользователя: возврат к слайдшоу после ошибки OTA

Уточнение от 30.10.2026: после неудачного обновления рамка автоматически
возвращается к слайдшоу **через 30 секунд**. Проверить рабочий путь
OTAService → уведомления frontend → OtaBloc/RouteBloc → слайдшоу;
если требование не выполнено, реализовать его в рамках этого этапа.
Это отдельный контракт от OTA-формы панели и пятиминутного autostop HTTP-сервера.
Текущие 30 секунд `_initialCheck` относятся к проверке релиза, а не к возврату
после ошибки; автоматический возврат этим таймером не подтверждается.

Отсчёт начинается при окончательном отказе попытки обновления. Охватить ошибку
передачи/скачивания, отказ запуска установщика, ненулевой exit code и отказ
перезапуска после установки. До истечения срока доступны причина и журнал;
возврат не должен перезапускать приложение или устанавливать пакет повторно.
Сведения об ошибке сохраняются для диагностики после смены экрана.

Таймер принадлежит конкретной попытке и имеет одного владельца. Повторное
уведомление той же ошибки не отодвигает срок. Новая попытка отменяет старый
возврат; ручной выход/смена экрана и закрытие отменяют его действие. Поздний
таймер не уводит пользователя с другого экрана. Успешная установка и её штатный
перезапуск сохраняют свой жизненный цикл. Сторонний отклонённый HTTP-запрос
или ошибка чтения сведений не завершают действующую установку и не запускают
возврат вместо её текущего состояния. `alwaysEnabled` сервера не блокирует
возврат экрана к слайдшоу.

Приёмка на виртуальном времени:

* На 29,999 секунды после окончательной ошибки показан OTA; на 30 секундах
  происходит ровно один переход, и рабочий экран слайдшоу снова отображается.
* Для каждого существенного класса отказа нет перезапуска/повторной установки,
  поздние события не возвращают старый экран; причины/результаты диагностируются.
* Новая попытка до deadline, повторный failure, ручной выход, смена страницы,
  close, успешный путь и активная установка не получают ложного перехода.
* Проверяется фактический маршрут/экран, а не только наличие Timer или отправка
  fake-события. Backend использует подменяемый внешний installer и локальные
  потоки/HTTP; настоящий `apt`, служба, браузер и устройство не запускаются.

Дополнить существующие `backend/test/ota_upload_test.dart`,
`dslideshow_flutter/test/ota_bloc_test.dart` и подходящий app/widget-harness,
не создавая ещё одну полную матрицу OTA на каждом уровне. Логи связывают
ошибку, назначение/отмену возврата и итоговый переход с одной попыткой.

### R7. Завершение Wi-Fi RPC

Сделать изменяющие методы сервиса ожидаемыми и возвращать успех только после
успешного завершения команды; отказ передавать исходному RPC с его ID.
Не отправлять мутации автоматически повторно при disconnect/timeout.
Предлагаемые сроки: системная Wi-Fi-операция до 60 секунд с ограниченным cleanup,
ожидание соответствующего клиентского RPC — 65 секунд. Для остальных RPC
оставить текущие 15 секунд. Согласовать сроки всех участвующих слоёв без
изменения wire-схемы. При разрыве связи считать итог неизвестным; панель
не должна выдавать такой результат за подтверждённый успех.

Приёмка: ответ не приходит раньше завершения, отказ/timeout корректно передаются,
панель обновляет список после подтверждения; поздний ответ и закрытие безопасны.
Процессы, транспорт и часы управляемые, без изменения сети машины и без broker.

## Этап 3 — Q1, дефект теста

Исправить empty-connections сценарий `backend/test/wifi_service_test.dart`:
вызывать `parseConnectionsOutput`. Оставить отдельную проверку пустого scan;
проверять рабочие парсеры, не SDK и не заранее заданный результат fake.
Небольшая отрицательная/граничная проверка должна отличать два контракта.
Дополнять существующие тесты, не дублировать их матрицу.

## Этап 4 — приоритетные пробелы покрытия

Сначала регрессии R3–R7 и их диагностика закрываются в соответствующих этапах.
Далее последовательно добавить минимальные достаточные сценарии:

1. **FrontendService:** рабочий RPC-facade, результаты/ошибки storage и SystemInfo,
   доставка событий, конкурентные и поздние ответы на его собственных границах.
2. **MainMenuBloc:** кнопки, переход через границы списка, команды/отказы,
   отмена подписки и отсутствие действий после закрытия.
3. **Storage/WebServer-формы панели:** ввод, invalid input, действия добавления/
   удаления и сохранность общего черновика. Обычная локаль — en.
4. **MQTT:** настоящий MqttService с fake внешнего клиента/соединения;
   subscribe/payload/reconnect и владение подписками, без реального broker.
5. **AppStorage:** чтение `storage.json`, defaults/типы, повреждённый JSON,
   отложенная запись и ошибки I/O на временных файлах с виртуальным временем.
   Это key-value persistence, а не выбор медиахранилища: исходный отчёт
   неточно описал ответственность класса.

Допустимы небольшие точки внедрения внешних зависимостей. Новые контракты
закрытия и дополнительные обнаруженные дефекты фиксировать явно; не расширять
продуктовое поведение только ради процентов. Массовая миграция моделей/экранов,
вся матрица эффектов и нативная/browser-приёмка не входят в этот этап.

## Проверки, документация и завершение

* По каждому исправлению сначала воспроизведение, затем регрессия ожидаемого
  поведения, реализация, проверка логов/ресурсов и финальное ревью diff.
  Диагностические пробы ревью сохраняются как исторические свидетельства;
  штатные регрессии размещаются в пакетах, общие fake — в `test/support/`.
* Применять Bloc/StatelessWidget, enum, Freezed и штатную генерацию по правилам
  проекта. Не расширять согласованный объём миграцией незатронутых моделей.
  Локализации обновлять из ARB, документацию — в профильных руководствах,
  продуктовые изменения — в `Unreleased` без увеличения версий.
* После каждого этапа — целевые VM-тесты и анализ затронутых пакетов.
  В конце — один полный прогон трёх пакетов с coverage, который одновременно
  служит полным тестовым прогоном; не повторять его отдельно без причины.
  Python/shell проверять при изменении инструментов.
* Runtime-проверка возможна только в подходящем уже запущенном локальном
  нативном debug-приложении через DTD, с проверкой принадлежности workspace.
  Иначе указать отсутствие runtime и ограничиться VM. Браузер, устройство,
  benchmarks, реальные Wi-Fi-команды, установка пакетов и DEB исключены.
* Сохранить новый датированный coverage/manifest/сводки рядом с результатами,
  сравнить покрытие изменённых областей и неизвестные файлы с учётом изменений
  строк. Старый baseline неизменен. Пересечения тестов сравнивать только на
  одном снимке; разные ревизии не сливать в один LCOV.
* Критерий завершения: R3–R7 и Q1 имеют проверенные исправления, автоматический
  возврат после ошибки OTA через 30 секунд проверен и при необходимости исправлен, приоритетные
  области имеют перечисленные сценарии, проверки проходят, логи и lifecycle
  проверены, R1/R2 сохранены как решения пользователя. Аппаратная/браузерная
  приёмка и произвольный общий порог покрытия не объявляются достигнутыми.

После выполнения этапов переносить действующее поведение в руководства,
результаты — в датированный отчёт. Завершённый план удалить после переноса
уникальных сведений; открытые задачи других планов не объявлять выполненными
только по совпадению затронутых файлов.
