## Открытый объём

1. Пользователь просматривает файл решений; при необходимости корректируем
   выбранные варианты. Изменения папок **любого** подключённого аккаунта
   уже поддержаны общей семейной панелью.
2. Для живого OAuth владелец регистрирует приложение Яндекс OAuth с правами
   `cloud_api:disk.read` и `cloud_api:disk.info`, вводит Client ID и, если нужен,
   client secret в настройках Storage. Credentials реального приложения
   и аккаунтов в рабочем окружении отсутствовали.
3. При отдельно разрешённой браузерной проверке проверить вход с телефона
   кнопкой и с другого устройства через QR/код, фактический аккаунт, отказ,
   истечение кода, повторный вход и редактирование его папок другим членом семьи.
   Подстановка кода в QR не обещается: используется документированный Device Flow.
4. На небольшом наборе реального Диска подтвердить чтение выбранных обычных
   папок, оригиналы поддерживаемых фото/видео, refresh token и отзыв доступа.
   Контракты этих сценариев уже проверены локально с fake внешнего API.

Запуск браузера, изменение аккаунтов, установка на фоторамку и аппаратные
проверки не выполняются автоматически. Состав будущих живых проверок
определяется отдельным поручением пользователя.

После завершения живой приёмки можно начать отдельный
[общий этап генерации Cloud API из OpenAPI](cloud-storage-openapi.md).
Он отложен и не входит в текущую реализацию Яндекс Диска.

## Завершение плана

После утреннего ревью и разрешённой живой проверки записать её фактический
результат в датированный отчёт. Исправить найденные расхождения в коде
и руководствах, затем удалить этот план и убрать его из активной навигации.
Локальные тесты и сборки не считаются подтверждением реального OAuth,
браузерного перехода или нагрузки на физической рамке.
