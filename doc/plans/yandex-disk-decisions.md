# Решения реализации Яндекс Диска для утреннего ревью

Дата: **31.10.2026**. Пользователь разрешил продолжать реализацию без ожидания
ответов, фиксировать вопросы и выбирать рекомендуемый вариант. Аппаратные
проверки на фоторамке не выполняются. Согласованный объём —
[план Яндекс Диска и скрытых медиа](yandex-disk-sync.md).

Этот файл хранит решения, которые можно пересмотреть после утреннего ревью.
Статус: **реализация и локальные проверки завершены; ожидается ревью пользователя**.
Действующее поведение описано в [руководстве Яндекс Диска](../yandex-disk.md)
и [руководстве галереи](../gallery.md#скрытые-файлы).

| Вопрос | Принятое решение и причина |
| --- | --- |
| Где взять OAuth client ID для реального входа? | Добавить настройку приложения Яндекса в форме Storage. Владелец один раз вводит Client ID и, если нужен выбранному OAuth-приложению, client secret. Значения хранятся приватно в существующем AppStorage; секрет нельзя прочитать из панели или экспортировать в AppConfig. Не подставлять чужое OAuth-приложение. Для живого входа потребуется зарегистрированное приложение пользователя. |
| Можно ли обещать вход без ручного кода? | Использовать официальный Device Flow: кнопка, QR официальной страницы Яндекса и отдельный код с копированием. Не формировать недокументированную ссылку с кодом; автоматическую подстановку не обещать. |
| Нужен ли гостевой доступ для подключения родственника? | Нет. Все участники семьи используют обычный доступ config_app и могут менять папки любого подключённого аккаунта. |
| Когда сохраняются подключение и выбранные папки? | OAuth сохраняет credentials сразу в AppStorage. Папки, подписи и период входят в общий черновик/Save и применяются после штатного перезапуска. Отмена черновика не отключает уже подключённый аккаунт; явное отключение удаляет credentials и прекращает дальнейший импорт аккаунта. Текущий скачиваемый файл завершается, локальные файлы сохраняются. |
| Сколько подключений OAuth может идти одновременно? | Одна активная сессия на рамку, чтобы семейные действия не подменяли друг другу ожидаемый аккаунт. Явная отмена и истечение завершают сессию; поздний ответ её не восстанавливает. Лимит 32 относится к уже подключённым аккаунтам, а не одновременным экранам входа. |
| Как открыть Яндекс из мобильной версии? | Использовать официальный Flutter-плагин url_launcher и внешний браузер. QR отображать через уже используемый проектом qr_flutter; обе зависимости объявить непосредственно в config_app. |
| Как проверить без аккаунта и фоторамки? | Локальные unit/VM widget-тесты рабочих сервисов, Bloc и HTTP/RPC-контрактов с подменой внешнего Яндекса. Не выполнять живую авторизацию без пользовательских credentials; не запускать браузерные и аппаратные тесты. Эти границы явно указать в результате. |
| Выполнять ли hot reload? | DTD обнаружен и подключён, список приложений пуст. Подходящего работающего debug-приложения нет. Новое приложение ради проверки не запускается; используются анализатор и VM-тесты. URI подключения не публикуется. |
| От какого момента отсчитывать час синхронизации? | От завершения прохода. После перезапуска ждать только оставшееся время от последнего успешного прохода. Ошибка назначает повтор через полный период, без немедленного цикла попыток. Один одноразовый таймер исключает пропуск следующего часа из-за длительности загрузки. |
| Что делать, если последнее успешное время оказалось в будущем? | Ограничить ожидание следующим периодом. На рамке часы до синхронизации NTP могут отставать; одноразовый таймер не должен откладывать импорт на дни после восстановления времени. Дополнительного сохранённого состояния нет. |
| Когда начинает действовать «Продолжить»? | Пауза относится к текущей работе Storage и не сохраняется после перезапуска. Продолжение планирует следующий срок от последнего успешного прохода; если он уже наступил, начинает новый проход. Передача, оборванная ошибкой сети, с середины не возобновляется. |
| Нужно ли узнавать одинаковые фотографии из разных аккаунтов? | Нет. Используется согласованная пара «accountId + полный путь» и два файловых корня. Облачное переименование или другая папка могут дать отдельную копию; для удаления дублей есть общий поиск галереи. |
| Какие технические пределы выбраны? | До 32 подключённых аккаунтов, страницы API по 100 записей, до 64 уровней вложенности относительно выбранной папки, потоковые файлы и ограниченные JSON-ответы. Нового файлового реестра и полного списка облачных медиа в AppStorage нет. |
| Что делать с legacy Google Photos? | Сохранить существующую авторизацию и публичную ссылку запуска старого OAuth, адаптировать загрузчик к hidden и общей публикации. Убрать вывод refresh token и сырых исключений транспорта из затронутого пути. Доступ к новым Google Photos API остаётся отдельной задачей. |
| Где находится логика облачного провайдера после утреннего ревью? | По согласованию пользователя введены CloudStorage и ленивый StorageProviderRegistry. HardwareService маршрутизирует общие DriveCommand; YandexDriveStorage обрабатывает их и владеет OAuth-сервисом. Авторизация неактивного Storage доступна без запуска его медиатеки и расписания. Реестр освобождает все созданные экземпляры один раз. |
| Сохранять ли прежний RPC? | Пользователь уточнил, что код не публиковался и не использовался. Принят единый DriveCommand/DriveResult с явным provider и общими моделями Drive*. Панель и тесты переведены на него; прежние Yandex-команды и aliases удалены. |
| Как реестр создаёт провайдеры? | По решению пользователя GetIt регистрирует FactoryParam по аргументу StorageType. Реестр обращается к GetIt.instance, кеширует один экземпляр каждого типа и владеет их закрытием; GetIt не становится вторым владельцем. Единственный конструктор без аргументов, изоляция unit-тестов — через GetIt scopes. |
| Как передавать зависимости HardwareService? | Все зависимости стали обязательными именованными параметрами; неиспользуемый AppConfig удалён из конструктора. Это делает точку сборки и тестовые fixtures читаемыми. |
| Где хранится hidden и общая проверка двух корней? | В DiskStorage находятся final Directory hidden и mediaExists(relativePath). Яндекс и Google наследуют корень и проверку; необязателен только аргумент конструктора для переопределения default. |
| Где публикуются скачанные файлы? | По решению пользователя в CloudStorage: staging, проверка размера/checksum и локальное переименование. CloudMediaCommit, ManagedCloudPublication и RPC CommitImportedMediaCommand/Result удалены. Web-сервер не участвует в публикации облачных файлов. |
| Нужно ли прерывать скачиваемый файл при остановке импорта? | Нет, по решению пользователя начатое скачивание всегда доходит до проверки и локальной публикации либо реальной ошибки передачи/записи. Пауза, отключение аккаунта и release останавливают новые файлы, а release ждёт текущий перед закрытием ресурсов. В publishDownloadedMedia и YandexDriveApi.download нет параметра cancellation или фиктивного токена отмены. Правило общее для облачных Storage, включая Google Photos. |
| Нужен ли токен отмены для метаданных синхронизации? | Нет. Начатый запрос метаданных или обновления access token завершается; перед следующим запросом или файлом читаются существующие состояния паузы, подключения аккаунта и закрытия Storage. Быстрый pause/resume продолжает тот же запрос и проход. Отдельный токен остановки обхода и регистрации токенов по аккаунтам удалены; release ждёт начатые запросы и текущий файл перед закрытием API. |
| Нужен ли отдельный объект отмены OAuth? | Нет, по уточнению пользователя CloudStorageCancellation удалён полностью. Отмена, истечение срока и close выставляют терминальный статус сессии и останавливают её таймеры. Текущий HTTP-запрос завершается; статус, актуальность сессии и закрытие сервиса проверяются после ответа и в обработчике ошибки. Поздние данные не сохраняются, новый шаг не начинается. Close ждёт все начатые запросы, включая запросы прежних отменённых сессий. |
| Нужен ли commit RPC из-за скрытия во время первого скачивания? | Нет. Пользователь справедливо уточнил: новый файл ещё недоступен в галерее и показе. Скрывают уже опубликованный файл; от повторного импорта защищает проверка images/hidden. Первоначальное объяснение назначения RPC этим сценарием было неверным. |
| Нужно ли mediaExists проверять каждый сегмент в файловой системе? | Нет. Пользователь разрешил симлинки в пути. Используются максимум две проверки File.exists относительно images и hidden, включая ссылки на существующий файл. Лексическая проверка относительного пути остаётся в памяти; каталог и битая ссылка возвращают false. |
| Обновлять ли галерею при каждом облачном файле? | Нет. CloudStorage не вызывает markDirty и не отправляет события в панель; пользователь обновляет список кнопками. Существующий watcher backend-кеша не инициирует перерисовку UI. |
| Как вернуть прежние значения AppStorage после ошибки? | Обычным setValue по старым ключам. Опасный restoreValue, отменявший общий таймер, удалён. Посторонние pending-изменения сохраняются; фоновый отказ записи диагностируется без потери значений в памяти. |
| Генерировать ли Cloud API из OpenAPI? | Да, как отдельный общий этап после реализации и живой проверки Яндекс Диска. Пока только план; наличие официальной схемы Яндекса предстоит проверить. См. [отложенный план](cloud-storage-openapi.md). |

## Замечания и результаты

Реализован весь согласованный объём: YandexDriveStorage с несколькими аккаунтами
и выбором папок, общий семейный доступ к редактированию, Device Flow с кнопкой
и QR/кодом, скрытые медиа, Undo и поиск дублей в hidden. Google Photos учитывает
скрытые файлы. Отдельной базы облачных файлов нет.

Локально пройдены анализаторы затронутых пакетов, полный backend-прогон,
VM-тесты панели и общих моделей; собраны web/Wasm release и Android debug APK.
Точные команды, результаты и пределы покрытия — в
[датированном отчёте](../history/2026-10-31-yandex-disk-local-validation.md).

Для первого реального входа потребуется зарегистрировать OAuth-приложение
и ввести Client ID в настройках Storage. Реальный Яндекс, браузерный переход
и фоторамка не проверялись. Ничего на фоторамке не устанавливалось.
Отдельного решения, требующего остановить реализацию до утра, не осталось.
