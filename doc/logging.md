# Логирование ошибок

Во всех пакетах используется стандартный `package:logging`. Существующий logger
компонента получает краткий контекст действия, исходное исключение и исходный
стек отдельными аргументами:

```dart
try {
  await storage.init();
} catch (error, stack) {
  _log.warning('Storage initialization failed', error, stack);
  rethrow;
}
```

Тип исключения и код отказа могут дополнять сообщение. Они не заменяют текст
исключения и стек. Собственный формат исключений или обёртка над logger для
этого не нужны. Правила разработки закреплены в
[AGENTS.md](../AGENTS.md#ошибки-и-стек-трейсы).

## Где сохранять причину

Полную диагностику пишет обработчик, который знает действие и обрабатывает
отказ. Если он превращает исключение в прикладную RPC/HTTP-ошибку, запись
делается перед преобразованием. Формат ответа и локализованные сообщения
интерфейса сохраняются. Например, отказ импорта может вернуть короткий
`UploadFailure`, а журнал сохраняет исходный `FileSystemException` с путём.

Для межизолятного RPC исходное исключение и стек остаются в журнале того
isolate, где произошёл отказ. Получатель типизированного отказа видит свой
стек ожидания RPC. Компонент, тип команды и существующий ID запроса помогают
найти обе записи. Контракт надёжного межизолятного RPC и поведение сетевого
WebSocket не меняются из-за логирования.

В `catchError`, `Future.then(onError:)` и `Stream.listen(onError:)` принимайте
оба аргумента. Если ошибка передаётся вспомогательному методу, передавайте
ему и стек. Используйте `rethrow` внутри `catch`, а для отложенного выброса —
`Error.throwWithStackTrace(error, stack)`. Не заменяйте исходный стек на
`StackTrace.current`. Если API передаёт только текст ошибки, записывайте этот
текст без выдуманного стека.

Не повторяйте полный стек на каждом промежуточном уровне. Чистое
распространение ошибки может оставить запись конечному обработчику;
ошибка фоновой задачи должна быть наблюдаема там, где её обрабатывают.
Не добавляйте для логов счётчики, реестры дедупликации и отдельные operation ID.

## Уровни и объём

* INFO — значимые переходы, начало и итог операции, сводные количества.
* WARNING/SEVERE — отказ с причиной и стеком по его значимости.
* FINE/DEBUG — подробности, отдельные элементы и восстанавливаемые отказы
  согласно существующей политике компонента.

Обычная отмена — штатный итог. Ошибка освобождения ресурсов при отмене
является отдельным отказом и сохраняет свою причину. Для коллекций 50 000+
медиа INFO остаётся сводным: без записи на каждый файл, кадр или тик опроса.
Большие диагностические данные вычисляются лениво; полный полученный стек
исключения не обрезается этим ограничением.

По решению владельца проекта от 31.10.2026 чувствительные данные в логах
разрешены. Текст исходной ошибки, URL, пути, коды и реквизиты не маскируются
в debug/release, консоли и журнале службы. Это не требует отдельных дампов
конфигурации, содержимого файлов или всей коллекции.

## Консоль и получение логов

`common/lib/log.dart` выводит компонент, уровень, маркер isolate, сообщение,
`LogRecord.error` и `LogRecord.stackTrace`. `autover` сохраняет те же поля.
В `tools` оба входа — `bin/dslideshow_tools.dart` и `tool/grind.dart` — используют
`BuildConsole`: многострочные ошибки и все строки стека остаются в постоянном
выводе stderr, в том числе при активном прогрессе и с `--no-color`.
Терминальные управляющие последовательности продолжают обрабатываться renderer.
Benchmark renderer сохраняет поля ошибки и стека в своих событиях.

Уровень приложений задаётся существующими `log.main`, `log.hw_frame`,
`log.web` в конфигурации; изменение применяется после перезапуска.
Для подробностей включите `FINE` или `ALL` нужного isolate. Локальный
`flutter run` показывает журнал в терминале; для подключённого debug-приложения
доступен `flutter logs -d <device-id>`. На установленной рамке:

```sh
journalctl -u dslideshow.service -b --no-pager
```

Особенности компонентов описаны в руководствах
[backend](../backend/README.md), [панели](config-app.md),
[галереи](gallery.md#логи-управления-медиатекой) и [tools](../tools/README.md).

## Локальная проверка

Тесты рабочих сервисов и Bloc проверяют результат действия вместе с реальным
`LogRecord`: исходный объект ошибки, переданный стек, уровень и контекст.
Для потоков и Future можно передать заранее известный `StackTrace.fromString`,
чтобы обнаружить потерю или замену стека. Используются фиктивные реквизиты.
Проверки консольных обработчиков включают многострочный текст и длинный стек,
а для tools — режим с прогрессом и без цвета.

Базовые проверки выполняются из соответствующего пакета:

```sh
(cd common && dart test test/log_test.dart test/rpc_telemetry_test.dart)
(cd backend && dart test --concurrency=1 test/yandex_drive_storage_test.dart test/drive_rpc_test.dart)
(cd tools && dart test test/build/console_test.dart test/build/grinder_entrypoint_test.dart)
```

Остальные изменённые сервисы/Bloc проверяются своими VM-тестами и анализатором
по [руководству тестирования](testing.md). Эти проверки не подтверждают
вывод journal на физической рамке или работу внешних провайдеров.
