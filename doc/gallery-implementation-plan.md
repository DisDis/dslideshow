# План реализации миниатюр и управляемой загрузки галереи

Подготовлен 26 октября 2026 года по запросу пользователя. Это план реализации,
а не отчёт о готовом функционале. Основание — [исследование галереи](gallery-performance.md)
и [локальные пробы](../benchmarks/reports/gallery-local-2026-10-26/report.md).
Production-реализация и аппаратная проверка ещё не начаты.

## Результат и границы

Сетка получает серверные миниатюры нужного физического размера. Один клиентский
загрузчик фотографий обслуживает сетку и fullscreen: ограничивает активные
запросы, объединяет одинаковые, приоритизирует видимые элементы, удаляет
устаревшую работу и действительно отменяет ненужную передачу. Версии источников
и производных исключают смешивание старых и новых изображений в кеше.

Оригиналы сохраняются без уменьшения и перекодирования. Fullscreen/zoom и
фоторамка продолжают использовать оригиналы; миниатюра может служить только
временным preview при открытии. Форматы фото/GIF и существующее видео Web/Linux,
выбор элементов, обновление списка и обработка ошибок сохраняются.

Первый выпуск не включает полную фоновую обработку коллекции, video posters,
новую навигацию по папкам, замену shelf, proxy или общую переработку upload.
Пагинация — отдельное расширение при подтверждённой необходимости. Лимит
image loader относится к фото/миниатюрам галереи: browser/mpv видео, RPC,
upload и другие разделы панели имеют собственные transport paths.

## Зафиксированные архитектурные решения

| Компонент | Ответственность и время жизни |
| --- | --- |
| `GalleryCatalogService`, backend | Асинхронный снимок каталога, типы, стабильные ID и source revisions. Один выполняющийся scan; файловые события во время него требуют повторной сверки |
| `ThumbnailService`, backend | Ленивое создание, объединение одинаковых генераций, bounded workers/queue, атомарная публикация и уборка производных |
| HTTP file responder | Авторизация, validators/HEAD/Range/CORS, поток готового файла и permit до завершения его тела |
| Общие DTO в `common` | Каталог, capabilities, описание thumbnail variant и типизированные ошибки. `@JsonSerializable`, enum и штатная генерация |
| `GalleryRepository`, клиент | Чтение каталога, выбор поддерживаемого протокола, timeout/cancel списка; без байтов изображений |
| `GalleryBloc` | Immutable модель списка, первая загрузка/refresh/error и поколение запроса; без кеша картинок и плееров |
| `GalleryViewportController` | Видимые строки, направление, ограниченный prefetch и текущий набор потребностей страницы |
| `MediaImageLoader` | Один экземпляр на server/auth scope; single-flight, приоритетная очередь, abortable transport, encoded cache. Общий для сетки и fullscreen |
| Плитка/image provider | Освобождаемый consumer lease на результат; показ и decoded image lifecycle. Не создаёт независимую загрузку при каждом build |

Viewport lease не равен listener/keepAlive ImageCache. Внутренний pending listener
Flutter не считается потребителем, которому нужна сеть после ухода страницы.
Иначе scheduler пройдёт isolated-тесты, но реальная плитка не вызовет abort.
Provider/completer должны очищать отменённые pending записи и соблюдать внешний
lease lifecycle; это проверяется отдельной widget integration с настоящим ImageCache.

Загрузчик живёт дольше маршрута галереи, но страницы освобождают все свои leases.
Смена сервера/авторизации закрывает старый scope и его задачи. Под новым
scheduler не остаётся отдельная неконтролируемая FIFO CachedNetworkImage:
кеш подключается к управляемому transport, а не запускает второй transport.

## Последовательность работ

Каждый этап — отдельная проверяемая порция изменений с документацией, тестами
и ревью. Названия новых классов/файлов ниже — предлагаемые точки реализации.

| Этап | Изменения | Условие завершения |
| --- | --- | --- |
| 0. Baseline и стенд | Заморозить исходники/SDK/config/media. В `benchmarks/` подготовить управляемый HTTP server и повторяемый scroll-сценарий Web/Linux, счётчики тела/отмены/cache и системных ресурсов | Сценарий воспроизводится, сырые ошибки/отмены сохраняются; записаны исходные метрики и критерии сравнения |
| 1. Контракт и каталог | DTO/capabilities; асинхронный catalog service, revisions и инвалидация; additive v2 endpoints; legacy list — async + корректный JSON без служебных staging-файлов | Roundtrip/unknown values, concurrent scan/refresh, смена файлов, restart и совместимость старого клиента проверены |
| 2. Клиентский loader | Transport Web/Linux, leases, приоритеты, дедупликация, настоящая отмена, bounded caches, отдельный decode budget | Наблюдаемый cap до конца body; abort до headers/во время body; повторный acquire во время отмены; очередь и ресурсы не накапливаются |
| 3. Список и viewport | Typed model/BLoC, refresh lifecycle, стабильные ID, viewport demand, fullscreen через тот же loader; пока допустимы оригиналы | Промежуточный кандидат A: режим очереди проверяем на прежних оригиналах; у фото нет обхода scheduler, выбор/scroll/fullscreen/видео работают |
| 4. Генератор и кеш backend | Сначала прототип decoder на больших фото; затем thumbnail service, worker/stream budgets, coalescing, публикация, LRU, HTTP/CORS | Генератор не блокирует web-isolate, имеет измеренный peak memory; корректны cold miss/hit, revision race, ошибки, cleanup и cache invalidation |
| 5. Миниатюры в сетке | Thumbnail variants по размеру/DPR, versioned keys, ошибки/retry и переход к original; подключить серверные budgets | Кандидат B: сетка передаёт производные, fullscreen — оригинал; нет массового fallback на оригиналы; подтверждены Web/Linux и mixed-version случаи |
| 6. Приёмка и выпуск | Локальная матрица, финальное ревью, затем отдельно согласованный A/B на Pi/Wi-Fi; документация и выпуск | Пройдены функциональные/resource gates, сохранены сравнимые архивы и визуальная проверка; аппаратные выводы сделаны только по аппаратным данным |

После этапа 1 клиентские этапы 2–3 и прототип генератора этапа 4 могут идти
параллельно по одному согласованному контракту. Интеграция — после обоих.
Кандидат A сохраняется для отделения эффекта очереди от эффекта миниатюр.
На этом запросе выполняется только подготовка плана.

## 1. API, каталог и версии

Предлагаемые новые маршруты, с сохранением действующих `/list` и `/get`:

| Запрос | Контракт |
| --- | --- |
| `GET /cache/<code>/v2/catalog` | Снимок с `catalogRevision`, capabilities, параметрами thumbnail policy и typed entries; обычное чтение не запускает обработку всей фототеки |
| `POST /cache/<code>/v2/catalog/refresh` | Обновление с operation ID и enum `CatalogRefreshMode`: обычный scan либо явный forceInvalidate для внешних изменений с прежними stat-метаданными; возвращает новый снимок |
| `GET/HEAD /cache/<code>/v2/thumbnail/<mediaId>/<sourceRevision>/<policyVersion>/<bucket>` | Проверка текущего источника/revision, готовая производная либо bounded lazy generation; URL одного варианта не меняет содержимое |
| Прежний `GET/HEAD /cache/<code>/get/<itemPath>` | Оригинал с прежним назначением; новый клиент передаёт `?rev=<sourceRevision>`, новый backend проверяет его. Параметр необязателен для старого клиента. Mutable original URL не получает immutable cache policy |

Снимок содержит schema version, persistent server ID и catalog revision;
неподдерживаемая обязательная schema version даёт контролируемую ошибку.
У записи: `mediaId`, относительный путь/название, `kind`, `sourceRevision`,
original reference, thumbnail support/variants. `kind` различает изображение,
видео, каталог и неизвестный тип. `supported` у миниатюры означает возможность
получения, а не обязательное наличие готового файла. Внутри клиента — отдельно
`originalUri` и thumbnail URI; тип и выбор не выводятся из URL миниатюры.
Создание и eviction производных не меняют catalog revision: capabilities
описывают допустимые варианты, а не меняющийся статус каждой генерации.

ID — непрозрачная постоянная идентичность записи. Source revision — другой
непрозрачный persistent generation token, не timestamp и не номер элемента.
Замена меняет revision; удаление и обнаруженное повторное создание получают
новый ID. Выбор снимается для исчезнувших или изменивших revision записей,
чтобы не применить действие к другому содержимому. Rebuild/смена URL из-за
авторизации не меняют выбор неизменившегося источника.

Рекомендуемый контракт инвалидации без хеширования всей коллекции на каждом GET:

* Каждая завершённая управляемая публикация/замена меняет revision независимо
  от совпадения размера/времени. Диск каталога переживает restart; потеря или
  повреждение metadata создаёт новый namespace, не переиспользует старые tokens.
* Для внешних изменений — асинхронный scan/fingerprint и filesystem events как
  подсказка. Обычный Refresh выполняет scan и сохраняет revisions неизменных
  файлов. Явный forceInvalidate консервативно меняет revisions области проверки
  даже при совпавших метаданных: это цена гарантированной инвалидации таких замен.
  Обычное чтение каталога и повторный вход также сохраняют revisions.
  Смена общего content epoch позволяет инвалидировать область без отдельной
  записи метаданных на каждый файл; epoch входит в effective source revision.
* Между внешней правкой, не обнаруженной watcher/fingerprint, и forceInvalidate
  возможна старая миниатюра. Этот предел документируется. Автоматическое
  обнаружение любого same-metadata изменения потребует content verification
  и отдельного бюджета; `mtime+size` такой гарантии не даёт.
* Source revision не называется strong ETag. Strong ETag готовой производной
  получается из её байтов; политика исходника и производной различается.

ForceInvalidate намеренно делает ранее созданные производные области
устаревшими, но пересоздаёт только востребованные плитки. POST имеет operation ID
для дедупликации повторной отправки; scan/invalidation сериализуются.
Отмена клиентского ожидания не обещает отката уже применённой инвалидации.
Обычная кнопка Refresh использует scan. ForceInvalidate — явная сервисная операция
для внешнего импорта/замены с сохранёнными метаданными, с документированной командой
или отдельным локализованным действием; она не выполняется при каждом входе.

Точки публикации: WebService upload, GooglePhoto и внешняя сверка. Hook срабатывает
на каждый действительно опубликованный файл, в том числе при partial batch error.
До начала замены источник помечается dirty, после публикации/закрытия writer
меняет revision. Незавершённая операция после crash требует сверки до выдачи
производной. Ошибка обновления каталога оставляет источник dirty, не разрешает
старую миниатюру и не скрывает факт уже опубликованного upload.

У GooglePhoto сейчас запись идёт непосредственно в конечный файл и `pipe` не
ожидается всей цепочкой. Для корректного publication hook нужно ожидать закрытия
потока и не считать промежуточный файл готовым; ограниченная правка staging/
publication входит в этот этап, переработка синхронизации GooglePhoto — нет.
Staging размещается вне `images/` на том же filesystem либо переиспользует
штатный publication helper. Произвольный `.gphoto.part` внутри `images/` непригоден:
DiskStorage исключает только собственный формат `.upload-<32hex>.part`.
`HttpClient` закрывается и `_syncInProcess` сбрасывается в `finally`, включая ошибки.
Согласовать уведомление между storage и web isolates через существующий RPC
transport либо общий журнал публикаций; завершённость нельзя заменять таймером.

Каталог строится отдельно, публикуется целиком; ошибка сохраняет предыдущий снимок.
Зарезервированные staging-файлы/служебные производные не попадают в API;
предикат общедоступных файлов согласован с DiskStorage/upload, без случайного
исключения пользовательских имён. Папки сохраняются как typed entries,
правила навигации не меняются. JSON генерируется штатной сериализацией.
Пагинация добавляется, только если baseline 1k/10k/50k показывает недостаточную
первую загрузку/память после async list. Тогда отдельный этап: общий snapshot,
стабильный порядок, cursor + catalog revision, bound памяти/TTL и invalid-cursor
retry; повторного полного scan на каждую страницу быть не должно.

## 2. Очередь, отмена и кеш клиента

Приоритеты enum: fullscreen original → видимые плитки → разрешённый prefetch.
Внутри класса — расстояние до viewport и возраст, чтобы исключить starvation.
Prefetch не занимает весь transport budget: остаётся резерв для интерактивного
спроса. Устаревшая speculative-загрузка без видимых consumers может отменяться
ради нового приоритетного запроса; повторный запуск не обходит общий cap.
Обновление demand объединяется в один проход на кадр. Диапазон видимых строк
вычисляется по реальной геометрии SliverGrid, padding и app bar; resize/DPR/смена
числа колонок пересчитывают его. Не обходить всю коллекцию на каждом scroll tick.

Состояния задачи enum: queued, fetching, cancelling, ready, failed. Decoder
имеет отдельные состояния/permit. Ключ включает server/auth scope, media ID,
source revision, variant/bucket/policy. На ключ — один transport и любое конечное
число leases, соответствующее действующим потребителям.

Обязательные инварианты:

1. `active <= configuredMax` учитывает запрос до конца body/error/подтверждённого
   abort, включая cancelling. Headers и `Future<Response>` слот не освобождают.
2. Уход одного consumer не отменяет остальных. Последний consumer удаляет queued
   job либо прерывает HTTP и чтение body. Reacquire во время cancelling ждёт его
   завершения; старый и новый transport одного ключа не перекрываются.
3. Очередь ограничена актуальным demand, состоящим из viewport и bounded prefetch;
   history scroll, retries, completers и служебные maps не растут бесконечно.
4. Поздний результат прежнего scope/revision/attempt не публикуется. Decode не
   запускается для уже ненужного результата. Невозможность прервать работающий
   decoder не выдаётся за успешную отмену CPU-работы.
5. Скрытый маршрут снимает свою demand, включая fullscreen push поверх сетки;
   pop восстанавливает её по геометрии. Dispose снимает все leases. Запущенное
   плиточное видео учитывает видимость маршрута отдельно от image scheduler.
6. Timeout/error освобождает ресурсы и допускает явный retry. Автоматические
   повторы конечны, соблюдают Retry-After и не возвращают устаревшие задачи.

Использовать управляемые IOClient/BrowserClient с AbortableRequest имеющегося
`http`; проверить фактический обрыв переданного тела на обеих платформах.
Полученные bytes/файл передаются image provider напрямую: последующий
`Image.network`/CachedNetworkImage не должен повторно обратиться к URL в обход
loader. Fullscreen фотографии подключаются к нему же, сохраняя полное разрешение.
Видео остаётся на штатном video_player/mpv, без автоматического старта плиток.

Encoded memory/disk cache и decoded ImageCache имеют отдельные бюджеты.
Отдельно учитываются bytes выполняющихся загрузок и ожидающих decode результатов;
одного ограничения количества запросов недостаточно для памяти. Native original
можно потоково записывать в файл. Для Web больших originals нужен проверенный
режим ограниченного одновременного буферирования, без уменьшения исходного файла.
Большой активный fullscreen original учитывается отдельно от evictable кеша,
не вытесняя десятки необработанных ответов в неограниченный backlog.
На Linux — atomic temp→cache file, byte/object LRU, metadata и cleanup startup.
На Web — HTTP-кеш браузера и bounded memory cache; отдельный IndexedDB-кеш
в первом выпуске не нужен. Blob/object URLs при использовании освобождаются.
Не держать без необходимости несколько копий bytes/Blob/decoded одного варианта.
Бюджет evictable cache не является строгим пределом всего RSS: live images,
fullscreen original и выполняющийся decoder измеряются отдельно.

Loader хранит кеш по server/auth scope; logout запрещает позднюю публикацию
старой задачи. Дисковый thumbnail cache сервера не зависит от auth-code, но
авторизация проверяется на каждом HTTP-запросе до cache hit/304. Повторный вход
не обещает отзыва уже скачанных клиентских копий — это иной контракт доступа.

## 3. Генерация и HTTP backend

Размер выбирается по фактической ширине плитки × DPR и округляется вверх в
фиксированный набор buckets. Конкретный набор, format/quality и предел DPR
фиксируются после прототипа/визуальной проверки; произвольные width/quality
из запроса не создают неограниченное число вариантов. Для исходно маленького
фото не требуется бессмысленное увеличение. В `policyVersion` входят все
параметры, влияющие на пиксели, включая orientation/кадрирование/формат.

Прототип сравнивает JPEG и поддерживаемые альтернативы на фото 48 Мп, портретах
с EXIF и прозрачности. Он должен воспроизвести нынешний `BoxFit.cover`/alignment
плиток без дополнительной потери детализации. GIF grid derivative допускается
как статический первый кадр с явным контрактом; fullscreen остаётся анимированным.
Для видео первого выпуска — существующая кнопка без server poster extraction.

Выбор decoder — отдельный gate этапа 4: проверить server/Linux ARM64 packaging,
decoder-level downsampling, EXIF/цвет/alpha, время и peak memory. Только после
этого принять необходимую библиотеку/runtime dependency; случайный `pub upgrade`
или установка системных компонентов не входят в проверку. Прототип/телеметрия
находятся в `benchmarks/`, production decoder имеет самостоятельный сервисный API.

Производные лежат вне `images/`, в отдельном каталоге рядом с persistent metadata.
Ключ диска: media ID + source revision + bucket + policyVersion. Lazy miss
объединяется с другими запросами этого ключа. Один согласованный открытый source
используется для генерации; после неё revision/identity проверяются снова.
Заменённый/удалённый источник не может опубликовать запоздалую производную.
Перед cache hit проверяется текущий fingerprint асинхронно; stale запись каталога
не позволяет выдать старое поколение после уже наблюдаемой замены источника.

Worker pool выполняет decode/encode вне web-isolate. Его предел, backlog и byte
budget независимы от выдачи файлов. Истечение server waiter deadline, закрытие
сервиса и известная отмена снимают waiter; отсутствие waiters удаляет queued job.
Выполняющаяся неотменяемая операция ограничена timeout/ресурсным budget и не
публикуется после закрытия. Single-flight завершается для всех waiters при
успехе, ошибке, отмене или закрытии сервиса.

До возврата Response текущий shelf handler не получает надёжного disconnect token.
Поэтому клиентский abort во время lazy generation не приравнивается к мгновенному
снятию server waiter. Консервативная гарантия первого выпуска — конечный срок
ожидания, backlog и общий worker budget, с cleanup по deadline. На прототипе
проверить возможность bridge из native HTTP lifecycle в Request.context;
если он вводится, добавить настоящий disconnect-before-headers тест и только
после него обещать немедленное снятие waiter. Замена HTTP-сервера ради этого
не подразумевается. После начала передачи действуют проверяемые body cancel/FD
гарантии; эти два случая измеряются отдельно.

Одного `Future.timeout` недостаточно для остановки decoder. Если выбранный
native decoder не допускает надёжного прерывания, использовать управляемый
процесс с проверяемым завершением/cleanup; не оставлять зависшую работу вечно.
Краткий ограниченный negative cache привязан к revision и не запускает заново
повреждённое фото при каждом появлении плитки; явный retry имеет конечный budget.

Готовый результат публикуется атомарно. LRU ограничивает bytes и object count,
не удаляет используемый источник передачи; временные/битые записи убираются
при restart. Ошибка диска/decoder не меняет оригинал. Отдельные server limits
ограничивают workers, ожидающие jobs и активные file streams от всех клиентов.
Ожидание генерации не занимает file-stream permit. Permit выдачи удерживается
до done/error/cancel body; управление/RPC не ставится в media FIFO.

HTTP-контракт проверяется до подключения UI:

* 200/304/HEAD с согласованными headers/body; ETag и Last-Modified. Versioned
  производная получает длительный private TTL только при неизменном содержимом
  URL; TTL и auth scope не подменяют source revision.
  Новый original URL с `rev` также обходит старую недельную запись по прежнему
  URL; одни новые заголовки не отзывают уже свежую копию у старого клиента.
* 400 для неизвестного bucket/policy, 403 для auth, 404 для исчезнувшего источника,
  409 для устаревшей revision, 415 для неподдерживаемой производной, 429 с
  Retry-After при заполнении бюджета, 503 для временной недоступности сервиса.
  В typed error response нет секретных URL/кодов доступа.
* Thumbnail HEAD проходит ту же проверку и при необходимости bounded generation,
  но не передаёт тело. Проверка валидатора готового кеша не запускает новый decode.
* Original GET/HEAD/Range/If-Range/416 сохраняют видео/seek. Исправить уже
  воспроизведённые Range/conditional ошибки, согласовать stat/open при замене.
  Несколько диапазонов допустимо явно игнорировать с полным 200.
* Для Web — same-origin и cross-origin, OPTIONS/preflight, Allow-Headers для
  фактически используемых validators/Range и Expose-Headers для ETag/Content-Range.
  Это проверяется также на error/304/206 ответах настоящим браузером.

Pinned desktop cache manager не соблюдает все ожидаемые варианты TTL. Новый
loader не полагается на `max-age=0` как единственную инвалидацию: revision key
и тесты реального cache hit/revalidation обязательны.

## 4. Интеграция и совместимость

В модели галереи stable media ID отделяется от URI и revision. Refresh сохраняет
успешный список/scroll до получения нового снимка, показывает ошибку с retry без
потери доступа к старому. `RefreshIndicator` ждёт сам refresh. Повторный refresh
замещает старый; его поздний ответ не выигрывает. Невалидные данные не приводятся
молча к строкам; неизвестные enum values имеют документированный fallback.

Ошибка миниатюры показывает локализованный placeholder/retry. Она не запускает
оригиналы автоматически для всех плиток. Явное открытие fullscreen запрашивает
original variant с высшим приоритетом. Смена revision отменяет старые leases;
409 вызывает одну объединённую сверку каталога, а не retry loop каждого элемента.

Сначала выпускается backend с additive API и legacy routes, потом клиент.
Новый клиент определяет поддержку по capabilities v2; fallback на legacy
допускается при отсутствии протокола (404/405 catalog route), а не при произвольной
сетевой ошибке/403/ошибке отдельной миниатюры. Legacy mode использует original
через тот же bounded loader и не обещает новой revision-инвалидации. Без надёжной
revision безопасно сбрасывать selection/cache freshness при явном refresh.
Rollback клиента не затрагивает оригиналы; производные можно удалить и создать
заново. Старый backend не требует понимания новых DTO.

## Проверки, бюджеты и критерии приёмки

Числа `maxActiveImages`, prefetch rows, decode workers, worker backlog,
encoded/decoded/disk bytes, stream limits, timeouts и TTL — параметры эксперимента,
не заранее объявленная мощность shelf/Pi. После baseline записать выбранные
значения и основания в отчёт **до** A/B; defaults/валидацию оформить типизированной
policy/config без benchmark-переключателей в production. Не вводить UI-настройки
для каждого внутреннего лимита без пользовательской необходимости.

| Проверка | Критерий |
| --- | --- |
| Controlled transport: два consumers, reacquire при abort, задержанные headers/body | На ключ один transport, peak active не превышает cap до окончания body, отмена видна серверу |
| Настоящий widget + ImageCache: удаление всех внешних leases до headers/во время body | Внутренний pending listener не удерживает сеть; transport отменён, pending запись очищена, повторный показ работает |
| Fling/reverse/resize/fullscreen/dispose и многократные циклы | Demand/queue ограничены текущим viewport+prefetch, видимые задачи не голодают; tasks/FD/memory после прогрева выходят на plateau |
| Одновременный cold miss одного варианта | Одна генерация и корректные ответы всех waiters; ошибочная генерация не отравляет кеш |
| Клиентский abort до ответа, пока server job ждёт worker | Client slot освобождён после abort; server waiter/job убраны в пределах собственного deadline, либо раньше по отдельно проверенному lifecycle bridge |
| Замена во время hash/decode/stream, удаление, partial upload, crash/restart | Новая revision, отсутствие старой публикации, освобождённые ресурсы и согласованный HTTP-контракт |
| Cold/warm cache, force refresh, смена сервера/auth, same-metadata external edit | Наблюдаемые hits и инвалидация по выбранному контракту; область авторизации не смешивается |
| Фото/GIF/EXIF/alpha, fullscreen/zoom, mixed video/seek/close | Качество производной проверено, original не заменён thumbnail, гарантии видео из README сохранены |
| Web/Linux, same/cross-origin, old/new client/backend | Одинаковый смысл queue/revision/errors; CORS и legacy fallback работают без storm |
| Один/несколько клиентов + конфигурация/RPC | Конечная нагрузка backend, корректные 429/retry и сохранённая отзывчивость управления |

Матрица baseline/A/B: 1k/10k/50k flat/nested, большие **реальные неизменённые**
фото и встроенные fixtures, DPR/окно, cold/warm cache, медленный/быстрый/обратный
scroll, смешанные видео и Wi-Fi. Собирать запросы/сек и активные/queued,
фактические байты, cache tiers, TTFB/body p50/p95/p99, ошибки/отмены; CPU/RSS/HWM,
FD/threads/I/O backend/workers, память/frame time клиента и задержку RPC.
Нет нулей вместо отсутствующих измерений; handler bytes не называются wire bytes.

Приёмка требует уменьшения bytes для одинаковой последовательности просмотра,
подтверждённого cap/abort/bounds, отсутствия UX/resource регрессий и улучшения
наблюдаемой отзывчивости по заранее записанным порогам. Нельзя объявлять победу
только по среднему RPS или меньшему числу фото, успевших загрузиться.

Релевантные команды при реализации, из каталогов соответствующих пакетов:

/home/dis/bin/flutter/bin/cache/dart-sdk/bin/dart --suppress-analytics test

Аппаратная часть — отдельное согласованное окно по
[руководству RaPi5](raspberry-pi-benchmarks.md), без автоматического запуска или
расписания. Зафиксировать release baseline/candidate, медиа, SDK/engine и один
runtime; не менять ОС/драйверы/firmware/flutter-pi. Изолированный GPU-стенд только
OpenGL, с остановкой и гарантированным восстановлением службы через supervisor.
Проверка конкуренции с работающей фоторамкой требует отдельного сценария и
согласования. Vulkan и 24-часовой прогон не входят в план. Если устройства нет,
сохранить команды будущего прогона и оставить аппаратную приёмку открытой.

## Файлы и управление изменениями

Основные области: `common/lib/src/gallery/` (новые DTO),
`backend/lib/src/service/gallery/` (новые catalog/thumbnail services),
`backend/lib/src/web_server/`, publication hooks в storage/upload,
`config_app/lib/features/gallery/` и `config_app/lib/src/` (loader/transport/cache).
Unit/widget/integration проверки — в пакетах, измерительный стенд и телеметрия —
только `benchmarks/`. Новый production API не зависит от benchmark entry points.

Перед каждой реализационной порцией перечитать status и сохранить чужие изменения:
в общей рабочей копии параллельно меняются frame/backend, версии и i18n.
Не использовать текущий HEAD как baseline без проверки его состава. Документацию
обновлять по фактически готовым этапам; Unreleased — при подготовке изменения
к выпуску. Версии/lock-файлы/генерируемые файлы менять только по необходимости
и штатными генераторами. После исправлений повторять затронутые проверки и
финальное ревью, включая гонки, освобождение ресурсов и достаточность тестов.
