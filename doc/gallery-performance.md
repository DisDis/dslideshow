# Галерея config_app: нагрузка и план решения

Исследование от 26 октября 2026 года. Это анализ и предложение для обсуждения:
production-код не изменён, кандидат ещё не реализован. RaPi5, служба фоторамки,
runtime и сеть устройства не затрагивались. Воспроизводимые локальные пробы и
сырые результаты описаны в [отчёте](../benchmarks/reports/gallery-local-2026-10-26/report.md).
Точка входа — [README панели](../config_app/README.md); общий
[план улучшений](config-app-improvements.md), этапы 6–7, остаётся актуальным.
Подробная последовательность работ и выбранные контракты вынесены в
[план реализации](gallery-implementation-plan.md).

## Что установлено

| Участок | Фактическое поведение | Значение для проблемы |
| --- | --- | --- |
| Сетка | `SliverGrid` лениво строит ячейки шириной до 200 logical px, включая область вокруг viewport | Виртуализация уже есть. Построение плитки не означает, что она сейчас видима |
| Фото | `ImageGridItem` запрашивает тот же оригинальный URL, что полноэкранный просмотр | Маленькая плитка загружает большой файл; серверного thumbnail API нет |
| Linux | `flutter_cache_manager` уже имеет FIFO, single-flight по ключу и предел 10 активных image fetch на default manager | Нельзя утверждать, что параллельность совсем не ограничена. Очередь не учитывает viewport и не удаляет устаревшие задачи |
| Web | Default `HtmlImage` идёт через `ui_web.createImageCodecFromUrl`, обходя файловый CacheManager | Linux-лимит 10 и его дисковый кеш здесь не действуют. Остаются Flutter ImageCache и HTTP-кеш браузера |
| Исчезновение фото | Текущая цепочка CachedNetworkImage не предоставляет реального abort запроса при dispose плитки | Ушедшие с экрана оригиналы могут продолжать загружаться и занимать очередь |
| Rebuild | Ключи image provider сравниваются по URL/cacheKey, scale и размерам; ImageCache объединяет pending/completed загрузки | Создание `GalleryItem` при build само по себе не доказывает повторный HTTP |
| GET файла | `existsSync`, два `statSync`, затем поток `File.openRead` | Сервер передаёт оригинал без уменьшения; целиком в RAM backend его не буферизует |
| HTTP-кеш | Уже есть `Last-Modified` и `Cache-Control: public, max-age=604800`; нет ETag и обработки условных запросов | Свежие копии могут не обращаться к серверу, но revalidation сейчас возвращает полное тело |
| Замена файла | Upload атомарно публикует новый файл по прежнему пути; URL остаётся тем же | Свежий недельный кеш может показывать старый файл |
| Список | HTTP `/list` использует рекурсивный `listSync` и ручную сборку всего JSON | Он блокирует web-isolate; ранее ускоренный `DiskStorage` — другой путь |
| Видео | Плитка создаёт плеер только по нажатию; fullscreen — автоматически | Просто появление новых видеоплиток сейчас не создаёт загрузку видео. Активные плееры используют отдельный сетевой путь |

Дополнительные воспроизведённые ошибки HTTP-пути: список включает каталоги и
`.part`, имя с кавычкой ломает JSON; `bytes=99-` для файла из десяти байтов
возвращает полное тело вместо 416; `If-Range` игнорируется. Это реальные
пограничные ошибки, но их вклад в наблюдаемое торможение не измерен.
Несколько диапазонов сейчас игнорируются с полным 200 — это отдельное
зафиксированное поведение, а не доказательство перегрузки.

Список клиента загружается целиком без timeout/отмены/pagination. `GalleryBloc`
пока не переводит исключение загрузки в имеющийся `ErrorGalleryState` и не
защищает результат от более позднего refresh. Повторные load-события могут
выполняться конкурентно. Это необходимо учесть при изменении lifecycle.

## Что подтверждают локальные пробы

Использованы настоящие `WebService.handler`, Dart 3.13.5, локальный Linux x64,
без аппаратных сервисов. Список измерялся в AOT, без HTTP-транспорта, на пустых
файлах с расширением JPG после создания fixtures: файловый кеш ОС не очищался.
Для каждого размера три последовательных повтора в одном процессе.

| Файлов | Handler, медиана | Диапазон | Опоздание таймера, назначенного через 1 мс |
| --- | ---: | ---: | ---: |
| 1 000 | 4,28 мс | 3,83–5,32 мс | 2,94–4,47 мс |
| 10 000 | 40,57 мс | 40,41–41,68 мс | 39,72–40,81 мс |
| 50 000 | 241,19 мс | 229,10–327,32 мс | 228,84–327,28 мс |

Обработка списка задерживает выполнение других событий того же isolate.
Это не замер WebSocket/RPC на устройстве и не p95/p99. Ускорение обхода списка
само по себе не уменьшит тела фото при прокрутке уже открытой галереи.

GET `photo_large.jpg` из встроенных медиа вернул все **10 192 467 байт** исходника
8000×6000. Это подсчёт тела handler, а не замер фактических браузерных байтов:
browser cache hit может вообще исключить передачу. `If-Modified-Since` с текущей
датой и `If-None-Match: *` на тестовом файле вернули 200 и полное тело.

Отдельно проверен настоящий локальный TCP-разрыв: клиент закрыл соединение
после первого chunk ответа на файл 64 МиБ. В финальном AOT-прогоне backend
прочёл 192 КиБ (в предыдущих — 256 КиБ), подписка
на источник была отменена, открытых FD этого файла после отмены не осталось.
Следовательно, текущий shelf/Dart IO путь способен остановить чтение при
реальном разрыве. Эта проверка не подтверждает, что Flutter-плитка вызывает
такой разрыв, и не заменяет проверку на Pi.

Фиксированного ограничения shelf в запросах/сек не обнаружено. `backlog: 32`
в запуске сервера — очередь ещё не принятых соединений ОС, не лимит RPS.
По коду shelf запросы обрабатываются конкурентно, тело передаётся `addStream`.

## Причины и оставшиеся гипотезы

Самый обоснованный первый объект оптимизации — большие оригиналы для плиток
в сочетании с работой, устаревшей после прокрутки. Это следует из кода и
контрактных проб, но доминирующую причину на RaPi5 ещё предстоит измерить.
Возможны одновременно несколько ограничений:

* Wi-Fi и суммарные байты, медленный накопитель, конкуренция чтений и FD;
* синхронные metadata/list операции и доступность web-isolate для RPC;
* декодирование и память клиента. Один RGBA-буфер 8000×6000 занимает около
  183 МиБ, до дополнительных копий и кешей; это расчёт, не измеренный RSS;
* возврат к уже просмотренным плиткам после eviction и повторная загрузка
  после изменения auth-code/URL;
* активное видео, refresh списка и несколько клиентов одновременно.

Пока не сняты реальные RPS/параллельность, браузерные cache hits/повторы,
CPU/I/O/FD backend и клиентский frame time. Поэтому конкретный «безопасный
лимит запросов» и обещание плавной прокрутки сейчас были бы предположением.

## Сравнение вариантов

| Вариант | Состав | Плюсы | Ограничения |
| --- | --- | --- | --- |
| A: управление текущими оригиналами | Общая очередь с приоритетом viewport, реальный abort, дедупликация, ограниченный prefetch; исправление HTTP-кеша и асинхронного списка | Быстрее ограничивает лишнюю работу; нет серверного декодирования | Каждый холодный полезный запрос всё ещё передаёт большой оригинал и требует декодирования на клиенте |
| B: очередь и ленивые миниатюры **(рекомендуется)** | A + versioned thumbnail API, конечная очередь генерации, single-flight, дисковый LRU с бюджетом | Уменьшает полезные сетевые тела и клиентский decode; готовит только нужную часть коллекции | Холодный miss требует тяжёлого decode на Pi; нужны отдельные worker/лимиты, инвалидация и обработка ошибок |
| C: предварительная подготовка | B + подготовка миниатюр при ingest и низкоприоритетный проход существующей коллекции | После подготовки мало холодных thumbnail miss, предсказуемее скролл | Стоимость всей коллекции по CPU/I/O/диску, миграция/прерывание/resume. Нельзя делать полный eager-проход при каждом открытии галереи |

Начать с B, а фоновую подготовку C добавлять по результатам холодных прогонов.
Новые uploads можно ставить в ту же низкоприоритетную очередь после публикации,
не задерживая успешный upload декодированием. Для существующей библиотеки —
lazy first; явный фоновый проход обсуждать отдельно с учётом работы фоторамки.

Reverse proxy/static server не уменьшит оригиналы и не устранит устаревшую
клиентскую очередь. Рассматривать его только если после B профиль покажет
издержки Dart-передачи готовых файлов при прочих равных. Установку nginx или
смену сервера сейчас ничто не обосновывает. Транзитивный `shelf_static` можно
сравнить как HTTP-helper, но он также не решает revision, авторизацию, общие
лимиты, `If-Range` и согласованность stat/open автоматически.

## Предлагаемая архитектура B

### Клиентская загрузка

Один loader на сессию/сервер и область авторизации, общий для Web и Linux.
Он владеет транспортом, bounded очередью и кешами; плитки получают подписки
на результат, а не создают независимые HTTP-клиенты. Для Web нужен
контролируемый запрос байтов с последующим показом уже полученного результата;
оставленный `Image.network`/default HtmlImage снова обойдёт scheduler.
Имеющийся `http 1.6.0` поддерживает `AbortableRequest` в IOClient/BrowserClient:
обновление зависимости для этого не требуется.

* Ключ запроса: server identity + auth scope + media identity/revision + variant.
  Один in-flight на ключ, несколько потребителей. Размер и формат входят в ключ.
* Высший приоритет у текущего viewport; небольшой ограниченный prefetch вокруг
  него ниже. Близость к viewport пересчитывается при смене направления.
  Число построенных Sliver-детей не считать точным признаком видимости.
* При уходе плитки удалить её queued-задачу или снять consumer активной.
  При отсутствии consumers отменить транспорт/чтение тела. Освобождать слот
  только после завершения или подтверждённой отмены. Одного generation check
  перед `setState` недостаточно.
* Очередь содержит только текущий viewport и разрешённый prefetch, а не все
  когда-либо увиденные элементы. На смене каталога/сессии и dispose удалить
  старые задачи; поздние ответы не публикуются. Обработка частых разворотов
  не должна создавать бесконечные cancel/restart и starvation видимых плиток.
* Stable widget keys и media identity сохраняют выбор/результат через rebuild.
  Возврат к просмотренному использует memory/disk/HTTP cache. Не удерживать
  все оригиналы или Blob в RAM; Web object URLs и subscriptions освобождать.
* Ошибки и таймауты завершают задачу, освобождают слот, дают явный retry.
  Устаревшие задачи не повторять автоматически; retries конечны и учитывают
  429/Retry-After. Refresh не публикует поздний результат предыдущего списка.

Точные лимиты загрузки, длины prefetch, decode и кеша выбрать после замеров;
начальные экспериментальные значения должны быть подписаны как параметры
кандидата, а не как подтверждённая пропускная способность Pi.

### Миниатюры

Оригинальный `GalleryItem.uri`/ID сохранить для выбора, типа медиа и fullscreen.
Добавить отдельный thumbnail variant. Подмена `uri` миниатюрой ломает общую
идентичность и переход к оригиналу. Ошибка миниатюры не должна автоматически
загружать оригиналы всей сетки: показать retry/placeholder, оригинал открывается
явным действием пользователя. Ошибка одного файла не блокирует очередь.

Целевой размер определяется фактической шириной плитки × DPR с округлением
в небольшой фиксированный набор размеров; произвольный размер из запроса не
должен порождать бесконечно много файлов. Для обсуждения: 200 logical px
при DPR 1/2/3 требуют порядка 200/400/600 физических px. Конкретные buckets,
ограничение DPR, формат и качество закрепить визуальной проверкой и замером.
Сохранять aspect ratio, EXIF orientation и достаточную площадь для `BoxFit.cover`.
JPEG для непрозрачных фото — простой кандидат; WebP сравнить по цене encode/
decode и поддержке обеих платформ, а не выбирать без измерения. Прозрачность
сохранять подходящим форматом. GIF в сетке может получить статический первый
кадр по явному контракту; fullscreen сохраняет оригинальную анимацию.
Video poster extraction — отдельная тяжёлая возможность; для первого этапа
оставить текущую кнопку видео без автоматической загрузки видеопотока.

Сервис производных расположен **вне каталога originals/images**, иначе список
и показ рамки увидят его файлы. Ключ диска: canonical media ID + source revision +
size bucket + версия формата/качества. Auth-code не входит в дисковый ключ,
чтобы смена кода не запускала повторное создание одних и тех же производных.

Генерация выполняется отдельно от web-isolate, с конечной очередью и ограничением
одновременных decode/encode по памяти и CPU, single-flight для одинакового ключа.
Не выбирать библиотеку декодирования/новый системный компонент до отдельного
локального прототипа: полный decode 48 Мп на Pi сам может стать bottleneck;
нужно сравнить decoder-level downsampling и фактический peak memory.
Синхронный image decode в HTTP handler неприемлем для этого плана.
Лимит генерации отделён от лимита активных выдач готовых файлов; ожидание worker
не занимает file-stream permit. На переполнение — ограниченный Retry-After,
а не бесконечная очередь. Длительно ожидающий клиент может уйти; последняя
отписка удаляет ещё не начатую генерацию. Если выполняющийся decoder нельзя
прервать, это явно учитывается как остаточная работа, без ложного отчёта abort.

Публиковать через временный файл и atomic rename, проверять source revision
после генерации и не публиковать результат для заменённого/удалённого источника.
Старые поколения очищать. LRU ограничить байтами и количеством записей;
отдельно ограничить память/число открытых файлов и уборку после перезапуска.
Не использовать upload `.part` как готовый оригинал.

### Версии, HTTP-кеш и передача

Manifest должен сообщать revision и доступные производные, чтобы клиент получал
стабильные versioned URL. Для управляемых публикаций revision меняется на каждый
реально опубликованный файл, включая частично успешный batch. Учитывать
GooglePhoto, внешние удаления/замены и повторную индексацию. Watcher — подсказка:
Linux recursive watch не гарантирует обнаружение вложенных изменений.

`mtime+size` не является безусловной идентичностью содержимого. До реализации
нужно выбрать контракт: persistent generation для управляемых изменений плюс
явная внешняя переиндексация/инвалидация, либо digest при ingest/обнаружении
изменения. Если обещается корректность внешней same-size замены с сохранёнными
timestamps, необходима проверка содержимого; это нельзя доказать одним stat.
Не хешировать целую коллекцию на каждом `/list` или GET. Не называть stat ETag
strong и не давать immutable URL, если его содержимое может измениться.

Versioned производным с действительно фиксированным содержимым можно дать
долгий TTL и ETag; изменяемым URL — проверяемую политику revalidation.
Авторизация выполняется перед выдачей тела, cache hit и 304. Клиентские ключи
включают server/auth scope; смена сессии не смешивает источники. Общий proxy
cache для авторизованных медиа не включать без явного контракта. TTL локального
кеша и прекращение доступа после logout — отдельные свойства; текущий код
авторизации в URL уже не отзывает скачанную копию.

У pinned desktop cache manager есть особенность: `max-age=0` не обнуляет default
семь дней, `no-store` отдельно не обрабатывается; `no-cache` распознаётся.
Поэтому revision keys и интеграционные cache-тесты обязательны. Заголовков,
которые просто выглядят корректными, недостаточно.

Условные GET/HEAD, ETag/Last-Modified, корректный `If-Range`/416 и согласованные
headers/body при replace/delete покрыть регрессиями. Активный file permit
держать до done/error/cancel тела, не только до возврата `Future<Response>`.
Не читать файл целиком в память. Проверить лимиты нескольких клиентов и
сохранение отзывчивости `/info`, авторизации и WebSocket/RPC. Плееры mpv и
video_player имеют собственный transport: image scheduler сам по себе не
ограничивает все video/Range-запросы; общий server budget нужно измерять отдельно,
не ломая seek и инициализацию.

Web bytes loader проверить как same-origin, так и cross-origin (включая запуск
панели с другого dev host/port). Ручные validators/Range могут потребовать
preflight и конкретных `Access-Control-Allow-Headers`; чтение ETag/Content-Range —
`Access-Control-Expose-Headers`. Текущие CORS headers этого полного контракта
не обеспечивают. Проверить OPTIONS и error/304/206 ответы в настоящем браузере;
не считать успешный native HTTP-тест доказательством работоспособности Web.

### Большие списки

Первый шаг — асинхронный обход, корректная JSON-сериализация, исключение временных
файлов и конечное время/отмена клиентского списка. Для новой модели каталога —
`JsonSerializable`, фиксированные типы/варианты — enum. Пагинация полезна для
больших коллекций, но не решает большой payload отдельных изображений.

Если вводить страницы, нужен настоящий индекс/снимок каталога: стабильный порядок,
cursor и catalog revision, обработка изменения/устаревания cursor, дедупликация
страниц. Нельзя заново рекурсивно сканировать все N файлов для каждой страницы.
Поскольку сейчас папки приходят как элементы списка, сначала явно сохранить
контракт папок/выбора и проверить поведение UI; не удалять их из API вслепую.
Окончательную необходимость страниц оценить по времени первой загрузки,
клиентскому JSON decode и памяти на 1k/10k/50k реальных путей.

## План реализации

Этапы, зависимости, предлагаемые API и условия завершения описаны в
[отдельном плане](gallery-implementation-plan.md). Сначала фиксируются baseline
и контракты, затем независимо готовятся управляемый клиентский pipeline и
серверная генерация; кандидат A сохраняется до подключения миниатюр в B.

Каждый шаг требует документации, тестов наблюдаемого поведения и ревью.
Не менять версии, lock-файлы и зависимости как побочный эффект проверок.
Новые подписи — в i18n. Изменение image pipeline не считается аппаратно принятым
после desktop-тестов. Ограничения видео из README панели сохраняются.

## Матрица измерений и приёмки

В baseline и каждом кандидате одинаковы release mode, SDK/engine, media manifest
с хешами, разрешение/DPR/размер окна, renderer, клиентская машина, Pi/runtime,
Wi-Fi и последовательность scroll. Сохранять сборки, конфиг, исходники и архивы.
Разделять холодный кеш приложения/производных/браузера и прогретый кеш ОС:
очистка browser storage не означает холодный диск Pi. Удалять только кеш стенда.

| Сценарий | Что выясняет |
| --- | --- |
| Первая загрузка 1k/10k/50k, flat/nested | List/JSON, память, задержка до первых плиток |
| Большие реальные фото, включая 48 Мп; DPR 1/2/3 | Сетевые байты, decode, детализация и пик памяти |
| Медленный scroll, быстрый fling, резкий разворот и возврат | Приоритеты, stale очередь, cache hits и повторная передача |
| Несколько проходов туда-обратно и закрытие во время загрузки | Отсутствие накопления tasks/consumers/Blob/FD/плееров |
| Холодные/тёплые HTTP-, disk- и thumbnail cache | Стоимость генерации и повторных посещений |
| Фото/GIF/видео, tile play и fullscreen/seek/close | Thumbnail→original, Range, lifecycle и сохранность видео |
| Замена/удаление, same-name upload, внешний импорт | Инвалидация и отсутствие старой картинки/поздней публикации |
| Timeout, 404/403/429/500, disconnect, смена сессии/каталога | Освобождение слотов и возможность повторить действие |
| Web same-origin и cross-origin, preflight/validators/Range | Доступность headers и bytes loader в браузере |
| Один и несколько клиентов при запросах конфигурации/RPC | Общий budget, доступность управления и справедливость |

Собирать по слоям: начатые/активные/queued запросы и RPS, фактические байты,
cache tier/hit, TTFB и полный body p50/p95/p99, ошибки/отмены отдельно от успешных
ответов; CPU/RSS/HWM/FD/threads и I/O backend, отдельно decoder workers;
client memory/декодированные изображения, scroll frame time/длинные кадры,
задержку конфигурации/WebSocket/RPC под нагрузкой. Для Web использовать Network
и Performance, Resource Timing при доступности; для Linux считать transport
в стенде. Счётчик handler не видит браузерные hits и не равен wire bytes.
Нельзя подставлять нули вместо ошибок/отсутствующих измерений или выводить
устойчивый p99 из трёх повторов.

Обязательные автоматические проверки: peak active ≤ выбранного лимита **до
конца body**, дедупликация двух consumers и отмена только последнего, смена
приоритета/направления, bound очереди и отсутствие starvation; dispose/cancel
до headers и во время body, FD/memory plateau после повторных циклов;
thumbnail single-flight/revision race/atomic publish/LRU и ошибки decoder;
browser/Linux cache hit и инвалидация, HEAD/304/Range/If-Range/416; сохранение
выбора и original URI, fullscreen/GIF/video, retry и ошибки списка.

RaPi5-нагрузка и deployment в этом исследовании не запускались и автоматически
не планируются. Перед аппаратной проверкой согласовать окно и архивы;
следовать [руководству](raspberry-pi-benchmarks.md), не обновлять ОС/драйверы/
firmware/flutter-pi. Для изолированного стенда предусмотреть остановку и
гарантированное восстановление службы через supervisor; конкурентный тест
с работающей фоторамкой требует отдельного согласования. GPU-проверки только
OpenGL, Vulkan и 24-часовой прогон в этот план не входят.

## Первичные источники по зависимостям

Проверены локальные pinned исходники: Flutter 3.47.7 / Dart 3.13.5,
cached_network_image 4.0.5, cached_network_image_web 2.0.3,
flutter_cache_manager 3.4.5, http 1.6.0, shelf 1.4.3. Поведение будущих версий
нужно проверять заново. Официальные пояснения:

* [Image.network](https://api.flutter.dev/flutter/widgets/Image/Image.network.html):
  decode/cacheWidth и ограничения Web; это не серверное уменьшение файла.
* [ImageCache](https://api.flutter.dev/flutter/painting/ImageCache-class.html):
  pending/completed/live изображения и кеш декодированных данных.
* [ImageCacheManager](https://pub.dev/packages/flutter_cache_manager/versions/3.4.5#imagecachemanager):
  локальное изменение размера, сохранение оригинала.
* [CachedNetworkImage](https://pub.dev/packages/cached_network_image):
  ограничения кеширования Web; они не отменяют HTTP-кеш браузера.
* [HttpGetResponse.validTill](https://pub.dev/documentation/flutter_cache_manager/latest/flutter_cache_manager/HttpGetResponse/validTill.html):
  разбор TTL; выводы выше проверены по установленной 3.4.5.
* [http: отмена запроса](https://pub.dev/packages/http#abort-request):
  AbortableRequest и поддерживающие clients.
* [File.openRead](https://api.dart.dev/dart-io/File/openRead.html):
  подписку нужно дочитать или отменить для освобождения ресурсов.
