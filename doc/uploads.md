# Загрузка медиа, OTA и конфигурации

Точка входа — [разработка проекта](../readme.md#разработка).

Актуальность: сверено с кодом 30.10.2026. Здесь описаны очередь config_app,
HTTP-приём медиа, формы OTA и импорт/экспорт конфигурации.

По прямому решению пользователя от 30.10.2026 существующая возможность media
upload записывать вне каталога медиа и вывод кода доступа `WebService` в INFO
сохранены намеренно (R1/R2 [ревью](https://github.com/DisDis/dslideshow/blob/v16.0.0/doc/history/review-2026-10-30/README.md)). Они
исключены из исправлений; это узкое решение не распространяется на пароль
Wi-Fi, другие секреты и сырые транспортные исключения. Прежние правила имён,
URI-декодирования, вложенности и симлинков не пересматривались.
Сохранено повторное `Uri.decodeFull`
для имени медиа: не-ASCII имена и некорректные percent-последовательности могут
отклоняться. Это известное ограничение, не исправленное потоковой загрузкой.

## Очередь медиа в config_app

Очередь резервирует до двух слотов до первого асинхронного чтения. Слот занят
до завершения HTTP и очистки источника, в том числе при отмене. Файлы ожидающих
задач представлены дескрипторами: размер и поток читаются только активной
попыткой, без предварительного `readAsBytes` для всей коллекции. Папка
обходится асинхронно, порциями по 128 поддерживаемых файлов; обычное следование
симлинкам и прежние относительные имена сохранены. Web-файлы без нативного пути
используют имя picker. Назначение собирается через `path`, код в HTTP URI —
как отдельный экранированный сегмент; `wss`-соединение использует `https`.
Серверные правила пути R1 при этом сохраняются.
Если API picker уже начал неотменяемое чтение размера, отмена ждёт его
завершения и до этого удерживает слот; поздний размер не запускает отправку.

Удаление активной задачи отменяет транспорт и подписку на содержимое. Другой
файл занимает слот после cleanup, а не сразу после скрытия строки. Закрытие
Bloc отменяет обход и активные операции и ждёт их освобождения. Удаление
ожидающей задачи не открывает её файл. Ошибочная задача допускает только явный
повтор; новая попытка имеет отдельный ID, запоздавшие progress/result старой
попытки игнорируются. Неизвестный исход отправки предлагает проверить рамку
перед повтором: отмена клиента не гарантирует, что сервер не успел опубликовать
файл. История успешных задач ограничена 100 записями.

На Android выбор файлов/папки запускает Bloc. Файлы выбираются стандартным
picker; у пустой очереди рядом с файлами есть отдельная кнопка «Загрузить папку».
После добавления файлов выбор папки также доступен через меню «+».
На Android папка выбирается через `ACTION_OPEN_DOCUMENT_TREE`: доступ даётся к выбранному дереву,
общие разрешения на всё хранилище не запрашиваются. Подпапки обходятся через
ContentResolver, страницы содержат до 128 записей; курсоры закрываются при
завершении, ошибке и отмене. Сохраняется префикс выбранной папки и вложенные пути.
Два активных файла читаются блоками до 64 КиБ, остальные представлены метаданными.
Неизвестный размер остаётся отдельной ошибкой источника. Закрытие очереди ждёт
начатого чтения и освобождения ресурсов, не открывая следующие файлы.
После окончания процесса очередь не восстанавливается; постоянные SAF-grants
для неё не сохраняются. Ограничения Android на выбор корня Download и Android/data
сохраняются; обычная подпапка выбирается отдельно.
Отмена picker пишет INFO, отказ — WARNING и локализованное сообщение. В логах
нет document URI и имён выбранных файлов.
У отдельных Android-файлов используется исходное имя: служебные каталоги кеша picker
не становятся подпапками на рамке. При выборе дерева сохраняются его вложенные пути.

Прогресс хранится отдельно для двух активных задач и обновляет только видимые
строки; на каждом progress очередь не копируется и не разворачивается целиком.
Категория `UploadQueueBloc` на INFO сообщает начало/итог пакета с `batchId`,
числом успехов, отказов и отмен. Связь отдельной попытки с
пакетом и `attemptId` доступна на FINE; имена файлов, код и секретные URL
в сообщения не включаются. HTTP-ошибки показываются локализованными причинами.

VM-проверки рабочего Bloc, picker-виджета и HTTP-клиента:

```sh
# Из config_app/
flutter test --no-pub test/upload_queue_bloc_test.dart test/upload_picker_test.dart test/web_client_test.dart
flutter test --no-pub test/android_documents_test.dart test/upload_selection_test.dart
```

Они используют управляемые источники и loopback HTTP; настоящие browser picker,
BrowserClient/CORS и web bundle этим не проверяются.
Android NSD и системные диалоги дополнительно проверяются на подключённом телефоне;
VM-тесты проверяют рабочие Dart-адаптеры с подменой платформенного канала.

## Приём и сохранение

`POST /upload/<code>/` принимает multipart/form-data с одной или несколькими
частями `file`. Каждая часть получает собственный временный `.part` в каталоге
конечного файла (для обычных медиапутей — в `images` или его подкаталоге).
Файлы записываются последовательно, с ожиданием записи, flush и close, без накопления всего тела
в памяти. Поддержка относительных подпапок существующей панели сохранена.

Публикация начинается после успешного разбора всего multipart. Переименование
в конечное имя атомарно для одного файла и заменяет прежнюю готовую копию.
Несколько файлов не образуют файловую транзакцию: если последующее
переименование не удалось, JSON ошибки содержит `published` с именами уже
опубликованных файлов. Непубликованные `.part` удаляются. Повтор одного пути
внутри запроса и параллельная загрузка того же пути отклоняются с 409.
HTTP 200 возвращается после публикации всех файлов; прежний текст успеха
`File uploaded` сохранён.

Для обычных медиапутей `.part` находятся внутри `images` по согласованному
решению. Последующий
[этап производительности backend](backend-performance.md) исключает служебные
временные файлы загрузки из индекса `DiskStorage`; само переименование
конечного имени остаётся атомарным для одного файла.
Очистка при обрыве процесса или отключении питания не гарантируется:
автоматическое удаление оставшихся после аварии файлов в этот этап не входит.

## Пределы

| Параметр | По умолчанию |
| --- | --- |
| Полное тело media/OTA-запроса | 200 МиБ (209715200 байт) |
| Полное тело загрузки конфигурации | 20 МиБ (20971520 байт) |
| Файлы в media-запросе | 100 |
| Файлы OTA/конфигурации | 1 |
| Части multipart | 128 для медиа, 2 для OTA/конфигурации (код и файл) |
| Текстовое поле | 1024 байта |
| Заголовки одной части | 16 КиБ |
| Активные media-запросы | 2 |
| Активные OTA-операции | 1 |
| Простой передачи | 120 секунд |
| Общая длительность приёма | 30 минут |

Предел тела учитывает фактически полученные байты, включая multipart-обвязку,
до разбора частей. Заявленный Content-Length позволяет отказать раньше,
но не заменяет счётчик. Отсутствующий Content-Length допустим.
Параметры задаются в конструкторах приёмника/сервисов; новых настроек JSON
и полей веб-панели в этом этапе нет. Исчерпание media-слотов возвращает 429
с `Retry-After: 1`; очередь тел запросов на сервере не создаётся.

При ошибке или отмене освобождаются собственные ресурсы и резервирования,
удаляются непубликованные файлы. Ошибки очистки логируются отдельно.
Недостаток места/квоты при записи или закрытии возвращает 507.
Отмена прерывает ожидание зависшей записи/открытия/закрытия. Уже начатая
операция ОС остаётся под наблюдением: закрытие выполняется после неё, а
поздно созданный временный файл повторно удаляется после завершения открытия.
Успешный ответ всегда требует завершённого закрытия; при отмене физическое
закрытие занятого файлового дескриптора может завершиться позже ответа.

## OTA

### Панель config_app

Выбранный дескриптор файла, текстовый код, проверка расширения/размера и состояние
отправки принадлежат `OtaBloc`; страница — `StatelessWidget`. До выбора непустого
`.deb` и кода кнопка отправки недоступна. Перестроение сохраняет ввод, а новый
picker сначала сбрасывает прежний выбор: отмена диалога не отправит старый файл.
Reset и закрытие отменяют попытку, освобождают HTTP/источник и отбрасывают
поздние ответы. Прошивка передаётся потоком, без зависимости общего экрана
от `File/path`; код остаётся строкой с исходными пробелами и ведущими нулями.
Начатое чтение размера через API picker не поддерживает принудительную отмену:
reset/close ждёт его завершения, прежде чем освободить попытку.

`OTAClient` использует `GET /ota_start?format=json` и multipart `POST /ota_upload`,
с полем `code` перед `file`. HTTP 200 означает приём, а не успешную установку.
Ответ ограничен 64 КиБ; время отправки по умолчанию — 30 минут, инициализация
и простой чтения ответа — 60 секунд (либо меньший заданный timeout). У клиента
каждого действия свой HTTP transport, закрываемый при результате или отмене.
`OtaBloc` пишет начало/итог/ошибку/отмену с названием действия,
`OTAClient` — безопасный тип отказа и ограниченную диагностику
HTTP на FINE. Содержимое ответа, код и URL в логи не передаются.

```sh
# Из config_app/
flutter test --no-pub test/ota_panel_bloc_test.dart test/ota_panel_widget_test.dart test/ota_client_test.dart test/media_device_ui_test.dart
```

Сценарии рамки, включая автоматический возврат через 30 секунд после
подтверждённой ошибки, описаны в [руководстве стадий OTA](ota-update-stages.md).
VM/widget и loopback-проверки не подтверждают отправку из браузера и настоящую
установку пакета; физическое устройство в этой работе не используется.

### Страницы и действия

`GET /ota_start` показывает версию рамки и три действия: обновить прошивку,
скачать `config.json`, загрузить `config.json`. Формы вынесены в отдельные
Dart-файлы в `backend/lib/src/service/ota/`; общий модуль содержит встроенные
стили и тексты. Стандартная отправка форм работает без JavaScript, внешних
ресурсов и панели настройки. Язык выбирается по `Accept-Language` из русского
и английского с английским по умолчанию. Формы работают и на узком экране,
поддерживают светлую/тёмную тему браузера и явные подписи полей. Общий заголовок
DSlideshow сохраняет подписи `frontend` и `backend` в обоих языках; номера версий
показаны крупным красным жирным шрифтом.

Только страница прошивки содержит небольшой необязательный встроенный скрипт:
при отправке он блокирует кнопку «Загрузить и установить» и показывает «Загрузка…»
(`Uploading…` на английском). Отключённая кнопка серая в обеих темах, включая
наведение. Используется обычный POST формы; скрипт не
перехватывает передачу и не меняет поля. Его инициализация и обработчики защищены
от исключений, поэтому при отключённом JavaScript или ошибке сохраняется
стандартная отправка. При возврате назад кнопка восстанавливается через `pageshow`.
CSP разрешает только этот фиксированный скрипт по SHA-256; внешних ресурсов
и новых зависимостей нет.

Код доступа — произвольный текст. Он сравнивается точно, без удаления пробелов,
изменения регистра, числового преобразования или ограничения пятью цифрами
в интерфейсе. Текущая генерация кода на рамке не меняется.

Кнопка «Отменить и вернуться к слайдшоу» переходит на `GET /ota_stop`.
Она отправляет команду возврата экрана рамки к слайдшоу, но не отменяет уже
начатую передачу файла или установку. Возврат к слайдшоу доступен также
со страниц конфигурации; на них есть ссылка обратно к странице OTA.

Обычные браузерные формы получают HTML-страницы результата и ошибок при
`Accept: text/html`. Для клиентов без этого заголовка сохраняются текстовые
ответы. `GET /ota_start?format=json` сохраняет прежний машинный ответ с версиями
и состоянием OTA. Страницы и конфигурация отдаются с `Cache-Control: no-store`.

OTA работает в том же процессе Flutter, хотя имеет собственный isolate.
Риск недоступности при падении процесса или ошибке до запуска OTA принят:
отдельная recovery-служба и независимый запуск в эту работу не входят.

### Передача прошивки

`POST /ota_upload` сохраняет существующий контракт: поле `code` перед
единственным `file`, расширение `.deb`, HTTP 200 после полного сохранения
и принятия установки. Старые клиенты и встроенная HTML-форма уже отправляют
код перед файлом. Неверный код проверяется сразу; файл до кода отклоняется
до открытия временного файла. Служебное поле также ограничено по размеру.

### Отказ во время HTTP-загрузки

При отказе во время потокового разбора multipart на настоящем HTTP-сервере OTA
остаток тела запроса дочитывается с отбрасыванием байтов. Это
позволяет вернуть страницу ошибки, например HTTP 403 при неверном коде,
без сброса соединения из-за непрочитанного файла. Остаток тела не разбирается
как multipart и не записывается на диск. Браузеру приходится закончить отправку
выбранного файла до показа ответа.

Для прошивки код проверяется перед файлом: при неверном коде временный пакет
не создаётся и установка не запускается. Импорт конфигурации также допускает
`file` перед `code`; если файл уже записан во временный, при отказе он
удаляется и прежняя конфигурация не заменяется.

Дочитывание ограничено теми же общим размером тела, временем простоя, общей
длительностью и отменой. Если клиент оборвал передачу, завис или превысил предел,
соединение может завершиться без HTML-страницы ошибки. Приёмник по умолчанию
прерывает чтение при отказе; дочитывание включается на границе HTTP-сервера OTA.

### Сохранение и установка

Временный пакет хранится в `firmwares`, закрывается и переименовывается до
передачи установщику. Автоматическое скачивание релиза использует тот же
поток сохранения, ограничения размера и неизвестной длины. HTTP-клиент
скачивания закрывается при любом результате.

Ручная загрузка, проверка/скачивание автоматического обновления, установка и
ожидание перезапуска принадлежат одной операции. Второй ручной запрос
получает 409; автоматическая проверка при занятости пропускается. Ошибочный
параллельный запрос не сбрасывает состояние действующей операции.

HTTP 200 не означает успешную установку: итог передаётся штатным `OTAInfo`.
Сохранены wire-имена enum, включая историческое `instaling`. При новой
операции очищаются прежние ошибки и exitCode. Ошибки загрузки, старта
установщика, ненулевой exitCode и ошибки перезапуска отражаются в состоянии.
Прогресс ограничен четырьмя обновлениями в секунду; переходы состояния и
финальные 100% передаются сразу. При неизвестной длине — 0% до сохранения,
затем 100%, без бесконечности и NaN.

Для ответа frontend, получения сведений о релизе, соединения и HTTP-заголовков
скачивания действует отдельный таймаут 60 секунд. При молчащем frontend
автоматическая OTA завершается ошибкой и освобождает свою блокировку.
Одновременно ожидается не более одного RPC уведомления: состояние объединяется
до последнего значения, очередь вывода установщика ограничена 64 КиБ UTF-8.
Превышающий её вывод обрезается с отдельной записью в серверный лог.
После восстановления ответов передаётся последнее ожидающее состояние.

`close()` отменяет приём, закрывает HTTP-клиенты и сервер, очищает временные
файлы и таймеры. Уже запущенный пакетный менеджер не прерывается; после
закрытия сервиса он не инициирует отложенный перезапуск службы.

### Терминал на экране рамки

Начальный экран показывает большой QR-код для `/ota_start`, крупный жирный
код доступа и текущую версию красным. До получения сведений видна версия и
сообщение подготовки; при ошибке определения сети QR с непригодным адресом
не показывается. Открытие OTA во время действующей операции сохраняет её этап;
поздний ответ инициализации не возвращает экран подключения поверх установки.

После начала обновления статус расположен над журналом, терминал занимает
всю ширину и использует шрифт 32 logical px. Процент и определённая полоса
показывают только загрузку файла; установка имеет индикатор активности.
Три шага «Получение → Установка → Перезапуск» поясняют оставшуюся работу;
100% завершает только передачу. Иконки получения, установки и перезапуска
различаются. Карточка статуса и положение журнала сохраняются при смене этапа;
процент не переносится при переходе к 100%. До первого видимого вывода область
журнала показывает пояснение ожидания. [Все этапы обновления со скриншотами](ota-update-stages.md).
Новые строки видны автоматически, ручной уход в историю приостанавливает
автоскролл. «К последней строке» либо ручной возврат вниз возобновляют его.
Ошибка и завершение оставляют журнал доступным; завершение установки и
перезапуск приложения имеют разные подписи.

В журнале установки Linux `LF` начинает новую строку с первого столбца, поэтому
вывод `apt` не смещается вправо ступеньками. `CRLF` остаётся одним переносом,
а отдельный `CR` позволяет переписывать прогресс в текущей строке. Это режим
терминала во frontend; исходные фрагменты вывода и ANSI-последовательности
передаются без замены переносов. [Поведение и локальная проверка](../dslideshow_flutter/README.md#терминал-ota).

Из `dslideshow_flutter/`:

```sh
flutter test --no-pub test/terminal_backend_test.dart
DSLIDESHOW_EMBEDDED=true flutter test --no-pub test/ota_bloc_test.dart \
  test/ota_view_test.dart test/ota_terminal_panel_test.dart \
  test/ota_ready_paint_test.dart
```

Проверяются содержимое буфера, реальные состояния Bloc, компоновка и прокрутка
TerminalView. Тесты не выполняют установку через `apt`; native-вывод и
FrameTiming проверяются отдельно [стендом OTA](../benchmarks/ota-harness.md)
с искусственным потоком логов, без запуска установщика.

## Конфигурация через OTA

`GET /ota_download_config` открывает форму с кодом; `POST /ota_download_config`
принимает прежнее поле `code` и возвращает файл-вложение с именем `config.json`.
Скачивание не разбирает JSON и сохраняет исходные байты: повреждённый файл тоже
можно получить для исправления. Ответ не кешируется браузером.

`GET /ota_upload_config` открывает форму импорта с рекомендацией сначала скачать
резервную копию. `POST /ota_upload_config` принимает `multipart/form-data` с одним
полем `code` и одним `file`; их порядок, в отличие от прошивки, может быть любым.
Имена маршрутов и полей сохранены для существующих клиентов.

Приём использует потоковую запись во временный файл рядом с текущим конфигом,
пределы тела/частей/служебных данных и таймауты из таблицы выше. Перед заменой
проверяются код, UTF-8, корректный JSON-объект и возможность его разбора рабочей
моделью `AppConfig`. Это не полная проверка диапазонов всех настроек:
например, ограничения редактора эффектов остаются в config_app.
Только после успешных проверок, flush и close временный файл атомарно
переименовывается в файл конфигурации. Записываются исходные байты, без повторной
сериализации: неизвестные поля и форматирование сохраняются. При ошибке
авторизации, разбора, лимита или записи прежняя конфигурация сохраняется,
неопубликованный временный файл удаляется.

Временный файл создаётся с обычными правами процесса и файловой системы
(`umask` на POSIX); после переименования эти права остаются у итогового файла.
Режим доступа прежнего файла отдельно не переносится. Дополнительных системных
команд и новых Dart-пакетов для импорта нет.

Импорт меняет файл на диске. Работающие сервисы продолжают использовать прежнюю
конфигурацию до следующего перезапуска приложения; автоматического перезапуска
после импорта нет. Атомарная замена не является гарантией сохранности при
аварийном отключении питания. Как и при других загрузках, после аварийного
завершения процесса временный файл может остаться на диске.

## HTTP-ответы

| Код | Значение |
| --- | --- |
| 200 | Медиа опубликованы / OTA сохранена и принята в установку / конфигурация передана или сохранена |
| 400 | Некорректный multipart, отсутствующий файл или неверная структура |
| 403 | Неверный код доступа или файл OTA перед авторизацией |
| 408 | Таймаут или отмена приёма |
| 409 | Конфликт пути или занятая OTA |
| 413 | Превышен предел тела, числа частей/файлов или размера служебных данных |
| 415 | Неподдерживаемый формат прошивки |
| 429 | Заняты слоты загрузки медиа |
| 500 | Ошибка сохранения или публикации |
| 503 | Закрытый сервис |
| 507 | Недостаточно места или дисковой квоты |

## Локальная проверка

Из `backend`, без обновления зависимостей:

```sh
dart analyze
dart test --concurrency=1 test/ota_test.dart test/ota_upload_test.dart test/ota_config_transfer_test.dart test/streaming_upload_test.dart
dart test --concurrency=1
```

Регрессии используют временные каталоги, управляемые потоки и writer с
задержкой/ошибками, а также локальный HTTP-сервер для обрыва соединения.
Проверка частоты прогресса учитывает фактическую длительность записи на диск:
не более четырёх промежуточных уведомлений в секунду плюс первое и финальное.
Отдельная синхронная проверка подтверждает объединение быстрых обновлений и
обязательную доставку итогового числа байтов без зависимости от скорости диска.
Установщик и restart подменяются fake: тесты не выполняют настоящие
`apt-get`, установку DEB, reboot или перезапуск службы. Проверяются
независимость файлов, завершение close до ответа/установки, размеры и
chunked-передача, ошибки и cleanup, слоты и конкурентные OTA-операции,
состояния, прогресс и освобождение ресурсов.

OTA-регрессии дополнительно проверяют ответы встроенных страниц, выбор языка,
контракт HTML/CSP для необязательного скрипта, точное сравнение текстового кода,
переход к слайдшоу, запуск после отказа открытия порта и работу HTTP при молчащем
frontend. Реальные локальные HTTP-запросы проверяют получение ответа на ранний
отказ с ещё не переданным файлом, без сохранения и установки. Тесты приёмника
проверяют ограничения байтов, времени и отмены при отбрасывании тела; это
не браузерные проверки. Конфигурационные тесты
проверяют исходные байты повреждённого файла при скачивании, оба порядка частей,
проверку `AppConfig`, атомарное сохранение, ограничения, ошибки и очистку.

Эти проверки подтверждают контракт приёма и установки с подменённым
исполнителем. Реальная установка пакета и поведение накопителя при
аварийном отключении питания ими не проверяются. Браузерные и аппаратные
прогоны для обновления страниц не выполняются: HTTP-тесты не подтверждают
фактический вид страницы, выполнение скрипта, отправку HTML-форм и CSS в браузере.
