# План автоматизации Google Photos клиента и перехода миниатюр на FFmpeg

Подготовлен 27.10.2026. Автоматизация googleapis остаётся на согласовании.
По указанию пользователя переход миниатюр на FFmpeg реализован отдельно;
локальное A/B описывает [итоговый JPEG-конвейер и команды](../benchmarks/reports/thumbnail-jpeg-local-2026-10-27/report.md).
По отдельному указанию пользователя создана
[локальная проба Ambient API](../tools/README.md); backend она не меняет.
Уточнение пользователя учтено: **при каждом запуске подготовки скачивается
свежий discovery-файл**. Проверки этого этапа выполняются локально; устройство,
ОС и рабочая служба не изменяются.

После отдельного разрешения пользователя 27.10.2026 выполнена SSH-диагностика
FFmpeg 5.1.9 на RaPi: найден SIGSEGV RGBA drawbox и проверен исправленный RGB-фон
на тестовом PNG и реальном фото 256/512/1024. [Отчёт](../benchmarks/reports/gallery-ffmpeg51-diagnostics-2026-10-27/report.md).
Это целевая функциональная проверка CLI; приёмка UI под нагрузкой остаётся отложенной.

Дополнительное требование: фоторамка должна читать содержимое выбранного
альбома и скачивать из него фото и видео. Разовый ручной импорт выбранных
медиа не считается равнозначной заменой. Пользователь не проходил партнёрское
подключение, но включил Google Photos Ambient API в Google Console.
В живой локальной проверке 27.10.2026 OAuth прошёл успешно, но `devices.create`
вернул `403 PERMISSION_DENIED` с прямым указанием на partner program. Выбор
альбома и скачивание медиа не достигнуты. Поэтому техническая автоматизация генерации
клиента и функциональная приёмка Google Photos — разные результаты;
способ доступа к обычному пользовательскому альбому пока не согласован.

Отложенная проверка полноты контрактов записана отдельно в
[плане RPC-анализатора](rpc-contract-coverage-plan.md).

## Исходное состояние до реализации

* Backend импортирует только `package:googleapis/photoslibrary/v1.dart`.
  Path-зависимость указывает вне проекта:
  `../../googleapis/discoveryapis_generator/googleapis`.
  Соседний пакет сгенерирован целиком и занимает около 127 MiB; он уже находится
  вне Git этого проекта. Его checkout и незакоммиченные файлы не удаляем.
* [Ручная инструкция](../backend/lib/src/service/googlephoto/readme.md)
  использует копирование JSON и генерацию всех Google API. Репозиторный
  `photoslibrary__v1.json` имеет revision `20180508`.
* 27.10.2026 официальный
  [discovery endpoint](https://photoslibrary.googleapis.com/$discovery/rest?version=v1)
  отдаёт revision `20261022`. Это наблюдение, а не закрепление версии для будущих
  запусков: новая подготовка всегда получает документ с сервера заново.
* `IsolateThumbnailWorker` запускает отдельный isolate на работу, читает источник,
  декодирует через Dart `image`, учитывает EXIF, делает центральный квадрат,
  уменьшает его и кодирует JPEG/PNG. `ThumbnailService` отдельно владеет очередью,
  дедупликацией, кешем и жизненным циклом запросов.
* На локальной машине установлены `ffmpeg` и `ffprobe` 8.0.1. В DEB-зависимостях
  пакета `ffmpeg` сейчас нет: `gstreamer1.0-libav` не предоставляет CLI FFmpeg.

## Этап 1: подготовка локального googleapis

Этот этап автоматизирует техническую подготовку существующего клиента.
Он не считается выполнением требования чтения обычного альбома; решение
о доступном API описано ниже. Bootstrap и фиксация свежего discovery должны
позволять подключить клиент выбранного Photos API после решения вопроса доступа.

1. Добавить одну команду подготовки, независимую от `pub get` backend:
   предполагаемая точка входа — `tools/prepare_googleapis.py`.
   Инструментарий генератора хранить отдельно в `tools/googleapis_codegen/`:
   официальный генератор из Git на закреплённом commit, его dependency lock
   и небольшой entry point. Не использовать
   [discontinued pub-версию 1.0.0](https://pub.dev/packages/discoveryapis_generator)
   и не загружать изменяемый HEAD при каждой сборке.
2. На каждый вызов команды выполнять HTTPS GET свежего discovery с
   `Cache-Control: no-cache`, deadline,
   ограничением размера, проверкой статуса и JSON. Проверять `name=photoslibrary`,
   `version=v1`, ожидаемый API endpoint и используемые ресурсы/методы.
   Не использовать старый локальный документ как молчаливый fallback при ошибке.
   Сетевая ошибка останавливает подготовку и сборку с понятным сообщением.
3. Скачанный вход хранить в игнорируемом
   `generated/googleapis-discovery/photoslibrary__v1.json`, выход — в
   `generated/googleapis/`. Генерировать **только Photos Library v1** с именем
   пакета `googleapis`, сохраняя существующий import. Эти пути и кеш инструмента
   исключить из Git. Старый JSON 2018 года убрать из рабочего рецепта и tracked
   исходников после подключения новой подготовки; результат не должен загрязнять
   Git при каждом скачивании.
4. После успешного скачивания сравнивать SHA-256 содержимого и параметры
   генерации с manifest. При неизменном документе, генераторе, lock и валидном
   выходе повторную генерацию можно пропустить. Свежий GET всё равно обязателен.
   При изменении входов генерировать во временный каталог, проверять результат
   и только затем заменять готовый пакет. Удерживать lock против параллельной
   подготовки; не оставлять полуперезаписанный пакет при сбое.
5. Сохранять manifest: URL, время загрузки UTC, revision, SHA-256 исходных байтов,
   commit генератора, hash lock, SDK, параметры и сведения о сгенерированном
   результате. Снимок JSON и manifest сохранять в артефактах проверяемой сборки:
   разные дни могут давать разные клиенты при неизменном commit приложения.
6. Backend переключить на `../generated/googleapis`; обновить только необходимые
   path-записи lock-файлов backend, frontend, config_app, benchmarks и
   system_metrics_widget без побочного upgrade остальных зависимостей.
   Подготовку встроить перед зависимыми тестами/`pub get`/сборками в штатные
   entry points: DEB preflight, Linux/Web и flutter-pi build, генерация моделей,
   сборка benchmarks. Один pipeline использует один загруженный снимок схемы.
   Обычный прямой `dart/flutter pub get` сам скрипт не запускает: для ручного
   запуска описать команду подготовки и добавить понятную проверку prerequisites.
7. Обновить GooglePhoto README, инструкции сборки приложений, DEB и стенда,
   корневой README и Unreleased. Подготовка не меняет версии прошивки и не
   требует установки Dart-клиента на устройстве: он входит в сборку приложения.

Проверки: запуск из чистого checkout без соседнего googleapis; без SSH GitHub;
повторный GET при попадании в кеш; новая revision; одинаковый JSON;
недоступность endpoint; HTML вместо JSON; неверный API; повреждённый manifest
или неполный выход; параллельные запуски; ошибка генератора с сохранением
прежнего пакета. Проверить совместимость свежего клиента с используемыми
`albums.list`, `mediaItems.search`, DTO и `googleapis_auth`, затем анализатор
и тесты backend и зависимых пакетов. Тесты загрузчика использовать с управляемым
HTTP-сервером; живой endpoint проверять отдельным smoke, не делать unit-тесты
зависимыми от Google.

## Граница между генерацией и доступом к Google Photos

Photos API существует. Однако текущая интеграция запрашивает
`photoslibrary.readonly` и ищет существующий альбом по имени. Согласно
[официальным изменениям API](https://developers.google.com/photos/support/updates),
с 31.03.2025 этот scope удалён; Library API читает контент, созданный приложением.
Для выбора пользователем существующих фото доступен
[Picker API](https://developers.google.com/photos/overview/about).
Текущий [`albums.list`](https://developers.google.com/photos/library/reference/rest/v1/albums/list)
документирован для app-created альбомов.

Даже свежий discovery может содержать legacy scopes. Наличие описания метода
или scope не доказывает доступность прежних прав на сервере.
Успешная генерация, компиляция и mock HTTP-тест не подтверждают работу с живой
учётной записью. Обновление JSON не восстановит автоматический доступ к
произвольному прежнему альбому.

Предлагаемый объём этого этапа — автоматизация сборки клиента и проверка
компиляционной/HTTP-совместимости. Сценарий доступа к личной библиотеке является
обязательным функциональным требованием, но пока не имеет согласованной
реализации. Он не подменяется неявно обновлением схемы или Picker-импортом.

### Решение о доступе к выбранному альбому

Для обычных существующих альбомов наиболее близкий официальный вариант —
[Ambient API для фоторамок](https://developers.google.com/photos/ambient/guides/get-started):
пользователь подключает устройство и выбирает источники-альбомы в Google Photos.
Устройство получает `deviceId`, а выбранные источники доступны как `mediaSources`
с устойчивыми идентификаторами. Запрос
[`mediaItems.list`](https://developers.google.com/photos/ambient/reference/rest/v1/mediaItems/list)
может ограничиваться конкретным `mediaSourceId` и возвращать страницы медиа.
Для Ambient требуется принятие в
[партнёрскую программу](https://developers.google.com/photos/partner-program/overview).
Пользователь включил Ambient API в Console. Локальная проба подтвердила OAuth,
но запрос создания устройства отклонён с указанием на партнёрскую программу;
партнёрского подключения пока нет. Включения сервиса для проверенного проекта
оказалось недостаточно. Заявки и обращения от имени пользователя не отправлять.

[Инструкция настройки Ambient](https://developers.google.com/photos/ambient/guides/configure-your-app)
описывает включение API, OAuth client типа TVs and Limited Input devices
и тестирование с предупреждением Unverified app до проверки публичного приложения.
Это не отменяет требования партнёрской страницы и не доказывает отдельного
исключения для тестовых проектов. Минимальная
[локальная проверка](../tools/README.md) реализована: OAuth со scope `photosambient.mediaitems`, `devices.create`,
выбор альбома через `settingsUri`, чтение источника и скачивание контрольных фото
и видео. После получения допуска нужно повторить её до конца. Успех подтверждает проверенный сценарий данного проекта, а не разрешение
публичного распространения. При отказе разбирать код и причину ошибки, а не
приписывать любой 403 отсутствию партнёрства.

После получения доступа понадобится отдельная реализация: авторизация устройства,
выбор и сохранение источника по ID, обновление токенов, обход страниц с учётом
лимитов и семантики Ambient, получение свежих URL и загрузка обоих видов медиа.
Точное соответствие выдачи полному содержимому альбома нужно проверить: Ambient
документирует curated-выдачу и content filtering. Нельзя удалять локальные медиа
на основании неполной страницы или считать её отсутствие доказательством удаления.

Скачивание должно работать по актуальным `baseUrl`; не сохранять их как вечные
ссылки. Параметры скачивания и необходимые HTTP-заголовки проверить для выбранного
API, включая истечение URL и готовность видео. Согласно
[руководству Ambient](https://developers.google.com/photos/ambient/guides/media-items),
параметр `dv` даёт транскодированную версию видео, а не гарантию побайтового
оригинала. Сохранить атомарную публикацию и отмену текущего GPhotoStorage;
незавершённая загрузка не должна попадать в фототеку. Реальная приёмка требует
доступного проекта Google и контрольного альбома с фото и видео.

Публичный
[Picker API](https://developers.google.com/photos/picker/guides/get-started-picker)
подходит для импорта явно выбранных пользователем медиа в сессии, а не для
автоматического перечитывания содержимого произвольного альбома. Это может быть
отдельным согласованным режимом импорта; требование пользователя о выбранном
альбоме таким режимом не закрывается. Library API достаточен только для доступного
ему app-created контента, что не следует предполагать для существующей фототеки.

Перед функциональной переработкой GooglePhoto требуется выбрать доступный путь:
получение Ambient-доступа с проверкой семантики альбома либо явно согласованное
изменение источника/сценария. Сейчас это открытый вопрос плана. Генерацию клиента
и замену миниатюр можно выполнить независимыми порциями после согласования.

## Этап 2: FFmpeg вместо isolate-декодера миниатюр

Реализован 27.10.2026; затем уточнён пользователем: один FFmpeg без ffprobe,
всегда JPEG, общий путь для фото/анимаций/видео, выбор кадра через `thumbnail`
и отдельная конфигурация `gallery`. Первоначальные предложения PNG/первого
кадра/probe заменены следующими требованиями.

1. Одна генерация запускает один `Process.start` без shell и новых Dart isolates.
   FFmpeg сам определяет формат локального файла. Прямое чтение с seek нужно
   контейнерам видео; разрешены протоколы `file,pipe`, сеть запрещена.
2. EXIF → центральный квадрат → уменьшение без upscale → непрозрачный фон →
   `thumbnail` по начальным N уменьшенным кадрам → JPEG. По умолчанию N=30,
   качество=60, фон `#202020`, decoder/filter/encoder threads=1.
3. `gallery.thumbnail` задаёт набор вариантов существующего `GalleryThumbnailSize`
   (`small`/`medium`/`large`), качество, фон, группу кадров, очередь, параллелизм,
   дисковый бюджет и timeout. `maxWorkers=4`; `gallery.maxConcurrentMediaStreams`
   ограничивает выдачу файлов. Изменения действуют после перезапуска.
4. Сохранить single-flight, публикацию с проверкой версии источника, LRU, ошибки,
   отмену и удержание слота до cleanup TERM→KILL/exit/pipes. Источник проверяется
   stat до/после FFmpeg, decoder ограничен `max_pixels`, вывод — 8 MiB и дисковым
   бюджетом. Stat не ограничивает реально прочитанные байты растущего файла,
   а pixel limit не является пределом RSS. JPEG lowres без probe не выбирается.
5. Удалить isolate worker, ffprobe, определение demuxer и промежуточный RGBA в
   Dart. `image` остаётся только dev-зависимостью для fixtures/независимых проверок.
   Основные backend/web/OTA isolates сохранены.
6. Ввести policy 4 и hash параметров рендера в URL/ключи серверного и клиентского
   кешей. MD5 готового JPEG служит content ETag и checksum при восстановлении.
   Устаревший policy URL возвращает 409; миграции старых производных нет,
   прежние файлы с SHA-256 digest удаляются при восстановлении кеша.
7. Подключить JPEG-постеры видео к общему загрузчику галереи. Исходное видео
   запускается прежним плеером; оригиналы/fullscreen/фоторамка не перекодируются.
8. Требуется только CLI `ffmpeg` (DEB Depends). При отсутствии executable
   миниатюры недоступны (503), оригиналы доступны; Dart fallback отсутствует.
   Не устанавливать системные пакеты автоматически.
9. Сохранить локальный frozen AOT baseline/candidate в `benchmarks/`, проверить
   функциональность, ресурсы и качество. [Текущий отчёт](../benchmarks/reports/thumbnail-jpeg-local-2026-10-27/report.md),
   первый промежуточный отчёт удалён при очистке 29.10.2026 как заменённый
   итоговым JPEG-сравнением.

Фактические параметры и JSON: [галерея](gallery.md), [backend](../backend/README.md).
Шкалы JPEG quality Dart и FFmpeg не равны: 1..100 отображается в qscale 31..2.
Официальные описания: [FFmpeg](https://ffmpeg.org/ffmpeg.html),
[фильтр thumbnail](https://ffmpeg.org/ffmpeg-filters.html#thumbnail).
Аппаратная приёмка отложена пользователем, текущие проверки только локальные.

## Приёмка и порядок

Порядок изменён пользователем: этап FFmpeg выполнен первым и независимо
от googleapis; подготовка Photos-клиента остаётся отдельной порцией. До начала функциональной миграции Photos/OAuth отдельно
согласовать доступный способ чтения альбома и проверить фактический Ambient-доступ;
успешная генерация Library-клиента не подтверждает работу с альбомом.

Для FFmpeg: unit-тесты аргументов и ошибок; настоящие локальные процессы для
cancel/timeout/kill, лимитов вывода и отсутствующих executable; изображения
JPEG/PNG/GIF/WebP/видео, EXIF rotations/mirrors, наложение alpha на фон, odd/small
размеры, повреждённые и слишком большие файлы, смена источника, cache hit/miss,
HEAD/ETag/Range, coalescing и shutdown. Реальные codec-тесты в обязательном
preflight не должны молча пропускаться при отсутствии FFmpeg.

После этого — анализатор и backend unit/HTTP/WebSocket-тесты, проверки зависимых
Flutter-пакетов и Web-сборки при затронутых зависимостях/контракте, Python-тесты
bootstrap/упаковки, синтаксис изменённых shell entry points и финальное ревью.
Не собирать финальный DEB ради проверки шаблонов и не увеличивать версии.

Локальное A/B в release: одинаковые большие фото, размеры 256/512/1024,
ориентация/прозрачность, холодные генерации и тёплый кеш; полная задержка задачи
включает Process.start/decode/выбор кадра/encode/cleanup. Измерять p50/p95, CPU, RSS backend
и subprocess, FD/threads/processes, event-loop gap и RPC latency под нагрузкой,
качество и объём результата. Все инструменты и отчёты — только `benchmarks/`.

По действующему указанию пользователя аппаратные проверки сейчас не проводятся.
Локальные результаты не объявлять подтверждённым ускорением на RaPi5.
Автоматических запусков или установок на устройство этот план не предусматривает.
