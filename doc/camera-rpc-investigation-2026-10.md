# Недоступная камера и timeout RPC/MQTT — исследование 26.10.2026

Исходный симптом: при специальном экране камер URL не отвечает или камера
выключена, после чего управление через RPC и MQTT выглядит зависшим.
Исследование не меняет приложение, настройки, службу или native runtime.
Инструменты находятся в `benchmarks/tool/`, результаты — в
[каталоге отчёта](../benchmarks/reports/camera-rpc-2026-10-26/).

## Установленные факты

1. Прямой общей очереди между загрузкой камеры и RPC/MQTT в коде нет.
   `CameraSnapshotClient` делает HTTP-запрос из frontend isolate; MQTT работает
   в backend isolate, WebSocket — в третьем isolate. `Service.processing`
   запускает async-обработчики конкурентно. Подготовка спецэкрана не удерживает
   обработчик статуса или RPC-команды frontend.
2. Четыре неотвечающие камеры в `sequence` могут задержать подготовку до
   примерно 40 секунд при дефолтном таймауте 10 секунд. Камеры проверяются
   последовательно до первого успешного снимка. Эта задержка сама по себе
   не объясняет недоступность RPC или MQTT.
3. Реальный локальный HTTP, который не присылает заголовки либо не завершает
   тело, не воспроизвёл многосекундную блокировку RPC. Использованы production
   `CameraSnapshotClient`, межизолятный `RemoteServiceImpl` и `EchoCommand`,
   а не `MockClient`. Ограничения: localhost, обычная Dart VM, без Flutter engine,
   физической сети, DNS и MQTT-брокера. SYN blackhole этой пробой не моделируется.
4. В RPC-транспорте подтверждено удержание слотов после внешнего
   `Future.timeout`. Дефолтный пул содержит пять слотов. Пока ответ не получен,
   слот не освобождается; при заполнении пула следующие команды ждут. Поздний
   ответ восстанавливает очередь. Это доказанный механизм усиления потерянных
   ответов, но его срабатывание при отказе камеры пока отдельно не установлено.
5. На работающей RaPi5 читающая проба поймала один timeout состояния после
   6 секунд. В том же окне были задержки WebSocket Echo до 5,46 секунды и
   backend Echo до 5,64 секунды. Следовательно, наблюдённая задержка затрагивает
   и путь, который вообще не ждёт frontend или снимок камеры. Сеть либо
   web/process scheduling требуют отдельного различения; считать причиной
   только `await` камеры оснований пока нет.

## Почему камера не должна останавливать управление

Основные места в коде:

| Путь | Поведение |
| --- | --- |
| `dslideshow_flutter/lib/src/service/camera_snapshot_client.dart` | Запрос ограничен по времени, размеру и concurrency; backend не используется. Таймаут начинается при запуске запроса, ожидание очереди в него не входит. |
| `dslideshow_flutter/lib/features/slideshow/presentation/sessions/cameras_screen_session.dart` | `prepare()` последовательно перебирает камеры в `sequence`, `grid` использует ограниченную очередь; ошибки заменяются состоянием недоступности. Ошибка HTTP не логируется с подробной причиной. |
| `dslideshow_flutter/lib/features/slideshow/presentation/pages/slideshow_page.dart` | Асинхронная подготовка спецэкрана отделена от listener и управления паузой/сном. |
| `dslideshow_flutter/lib/src/service/frontend.dart` | Старый MQTT action подтверждается после постановки события; состояние читается без ожидания камеры. |
| `backend/lib/src/service/mqtt/mqtt_service.dart` | Получение команды немедленно публикует state и добавляет событие. Этот state — не доказательство фактического выполнения действия UI. |
| `common/lib/src/rpc/service.dart` | Конкурентные async listeners. Ошибка обработки/сериализации повторно выбрасывается без ответа отправителю. |
| `common/lib/src/rpc/remote_service.dart` | Ожидание `result.next` не имеет внутреннего deadline; нет наблюдения смерти дочернего isolate. Внешний timeout не завершает исходный запрос. |

`GetFrameState` в текущем backend ограничивает ожидание frontend и объединяет
повторные незавершённые запросы. Поэтому единичный недоступный frontend не
должен заполнять все слоты именно опросами состояния. Для команд управления
внешний timeout всё равно не отменяет транспортное ожидание.

Простое добавление `.timeout()` и немедленное повторное использование того же
result port небезопасно: поздний ответ может попасть следующему запросу.
Исправлению транспорта нужны корреляция ответов, обработка поздних сообщений,
завершение при смерти isolate и проверка освобождения ресурсов.

### Четырёхминутная RPC-проба 19:46:17–19:50:17 МСК

Параллельно раз в секунду отправлены три читающих запроса по одному WebSocket.
Из-за ожидания самого медленного запроса цикл замедляется при задержке;
получилось по 218 попыток каждого типа. Это намеренно не нагрузочный тест.

| Запрос | Успешных / попыток | p50 успешных, мс | p99 успешных, мс | max успешных, мс |
| --- | ---: | ---: | ---: | ---: |
| WebSocket Echo, только web isolate | 218 / 218 | 6,403 | 1121,585 | 5455,628 |
| backend Echo, web→backend RPC | 218 / 218 | 6,562 | 1812,920 | 5638,413 |
| состояние, web→backend→frontend | 217 / 218 | 6,942 | 1616,765 | 5638,374 |

Одна попытка состояния в 19:48:16,645 МСК завершилась внешним timeout
через 6001,894 мс. Её длительность исключена из квантилей успешных ответов;
реальное время позднего ответа не измерено. Во всех 217 полученных состояниях
frontend присутствовал. Всплеск прошёл самостоятельно; последующие запросы
снова отвечали примерно за 7 мс.

Одновременно собрано 255 снимков `/proc` за 19:46:19–19:50:33 МСК.
В 84 замерах были `SYN_SENT` камер, MQTT TCP оставался `ESTABLISHED` во всех
255, FD 47–48, потоки 10–16. Ближайший снимок к timeout состояния содержит
SYN_SENT четвёртой камеры. Калибровка часов двух машин отдельно не проводилась,
поэтому сопоставление с точностью до долей секунды приблизительное.

В серверном журнале frontend-запросы во время всплеска имеют `duration: 0ms`.
Это измеряет выполнение handler после его запуска, а не время доставки,
ожидание result port или планировщик. Например, после отправки состояния
в 19:48:32,905 обработчик зарегистрирован в 19:48:38,278; на клиенте одновременно
задержались все три типа ответа. Одного такого совпадения недостаточно, чтобы
отличить задержку Wi-Fi от планирования web/process.

Сырые [RPC](../benchmarks/reports/camera-rpc-2026-10-26/device-rpc.json),
[сокеты](../benchmarks/reports/camera-rpc-2026-10-26/device-sockets-rpc.jsonl)
и [сводка](../benchmarks/reports/camera-rpc-2026-10-26/device-summary.json)
сохранены. Во время наблюдения служба оставалась активной, её состояние и
конфигурация не менялись. Отключение MQTT на уровне протокола не воспроизведено.

ограниченного числа пропусков. Успешные warmup/tail запросы не могут скрыть

а не аппаратный benchmark или подтверждение производительности RaPi5.

### Сеть и loopback HTTP на RaPi5

Дополнительно одновременно запущены 120-секундные пробы `/info`: с рабочей
машины через сеть и на самой RaPi5 через `127.0.0.1`. Оба клиента используют
одинаковый stdlib HTTP-инструмент, свежий TCP на каждый запрос и читают только
заголовки. Ответ `/info` статический и проверяет web isolate, а не RPC/frontend.

| Путь | Запросы / HTTP 200 | p50, мс | p99, мс | max, мс |
| --- | ---: | ---: | ---: | ---: |
| Рабочая машина → Wi-Fi → RaPi5 | 119 / 119 | 8,538 | 133,908 | 1821,619 |
| RaPi5 → собственный loopback | 120 / 120 | 1,103 | 1,574 | 139,095 |

Окна 19:54:08–19:56:08 и 19:54:12–19:56:12 МСК пересекались примерно
115,8 секунды. Самая большая сетевая задержка случилась до начала loopback;
это не синхронная пара для данного максимума. После первого запроса максимум
loopback был 1,574 мс, сети — 133,908 мс. Все замеры, включая первые, сохранены
в [сетевом](../benchmarks/reports/camera-rpc-2026-10-26/http-network.json) и
[loopback JSON](../benchmarks/reports/camera-rpc-2026-10-26/http-loopback.json).
Новых задержек по 5–6 секунд это окно не поймало, поэтому оно не доказывает
причину предыдущего RPC timeout. Сетевой путь остаётся приоритетной гипотезой;
длительное зависание web isolate этой короткой проверкой не подтверждено.

## Как повторить локальные пробы

Нужны уже установленные зависимости; `pub get`, обновление версий и генерация
моделей для этих инструментов не требуются. Из корня репозитория:

```sh
/home/dis/bin/flutter/bin/cache/dart-sdk/bin/dart \
  --packages=benchmarks/.dart_tool/package_config.json \
  benchmarks/tool/camera_rpc_probe.dart > /tmp/camera-rpc.json
/home/dis/bin/flutter/bin/cache/dart-sdk/bin/dart \
  --packages=backend/.dart_tool/package_config.json \
  benchmarks/tool/rpc_timeout_probe.dart > /tmp/rpc-timeout.json
```

Первая проба по умолчанию выполняет по восемь снимков с четырьмя слотами и
таймаутом 10000 мс: отказ до заголовков, зависшее тело, отказ TCP-подключения.
Во время снимков измеряются задержки Timer и Echo RPC. Параметры
`--timeout-ms=N --requests=N` предназначены для отдельной диагностики;
короткий прогон не подтверждает длительную отзывчивость.
Вторая проба намеренно занимает два RPC-слота, проверяет внешний timeout,
поздние ответы, исходные ID и штатное завершение worker.

## Читающая проверка на работающей фоторамке

Эти два инструмента не запускают Flutter/GPU-стенд и не требуют остановки
службы. `camera_device_probe.dart` активно отправляет только `WSEcho`,
backend Echo и `GetFrameState` раз в секунду; он не посылает команды управления
или MQTT publish. Текущий код веб-авторизации передаётся одной строкой через
stdin и не попадает в результат. Извлечение кода из журнала для этого запуска
отдельно разрешено пользователем.

```sh
# После запуска введите текущий код веб-авторизации и Enter.
/home/dis/bin/flutter/bin/cache/dart-sdk/bin/dart \
  benchmarks/tool/camera_device_probe.dart 192.168.50.143 240 \
  > /tmp/camera-device-rpc.json

# В другом терминале: PID нужно заново проверить, он меняется при рестарте.
ssh -o BatchMode=yes -o ConnectTimeout=120 \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=10 pi@192.168.50.143 \
  'python3 - /home/pi/dslideshow/config.json 76463 255' \
  < benchmarks/tool/camera_socket_probe.py > /tmp/camera-sockets.jsonl
```

Socket probe читает только IPv4 `/proc/net/tcp` и FD указанного процесса.
Ключ `camera_tcp_states` — `индекс:TCP-state`; индексы начинаются с нуля.
Если несколько URL имеют один IP/порт, он выводит группу индексов через
запятую: по TCP нельзя различить пути одного HTTP endpoint. DNS-имена, IPv6,
отдельные network namespaces и MQTT TLS/нестандартный порт этой пробой не
покрываются. Установка зависимостей на RaPi5 не нужна.

Для отдельного сравнения сети и web isolate, запустите эти две команды
параллельно; авторизация не требуется:

```sh
python3 benchmarks/tool/camera_http_probe.py 192.168.50.143:8080 120 \
  > /tmp/camera-http-network.json
ssh -o BatchMode=yes -o ConnectTimeout=120 \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=10 pi@192.168.50.143 \
  'python3 - 127.0.0.1:8080 120' \
  < benchmarks/tool/camera_http_probe.py > /tmp/camera-http-loopback.json
```

HTTP-инструмент требует Linux/POSIX `SIGALRM`; общий deadline ограничивает
также медленный DNS и получение заголовков. Тело не загружается.

## Как различить причины по результатам

| Наблюдение во время подтверждённого отказа камеры | Следующее направление |
| --- | --- |
| Web Echo отвечает; backend Echo перестал отвечать | backend isolate, заполнение web→backend RPC-пула, ошибки обработки/завершение isolate |
| Backend Echo отвечает; frontend отсутствует в состоянии | backend→frontend RPC, состояние UI isolate/engine; измерять отдельно очередь и время выполнения |
| Web Echo, backend Echo и состояние отвечают; действие UI не происходит | прохождение action через status/slideshow, подтверждение фактического выполнения, отображение устаревшего state |
| Все уровни недоступны, SSH работает | состояние процесса/потоков, native backtrace при зависании, ресурсы; SYN_SENT сам по себе недостаточен |
| Одновременно недоступны SSH/HTTP/MQTT | физическая сеть, маршрутизация и брокер; сравнить время события на обеих сторонах |
| Брокер пишет keepalive timeout именно клиента рамки | нужны его PINGREQ/PINGRESP и логи backend; живое чужое подключение к брокеру это не заменяет |

Уменьшение таймаута камеры может уменьшить время подготовки, но не считается
исправлением зависания управления. Увеличение RPC-пула, автоматический рестарт
и скрытие native-ошибок также не устанавливают причину.

## Оставшаяся проверка и область исправлений

Точная первопричина пользовательского сбоя считается установленной только
после одновременного наблюдения отказа камеры и задержки конкретного уровня
управления. Текущая архитектура и локальные пробы не подтверждают гипотезу
«любой HTTP await блокирует RPC/MQTT».

Следующий воспроизводимый сценарий: без изменения штатной конфигурации
сопоставить читающие RPC с SYN_SENT четырёх камер и точным временем
пользовательской команды/записями брокера. Для дальнейшего контролируемого A/B
нужны отдельно отвечающий URL, connection refused и SYN blackhole,
одинаковые приложение/runtime/медиа и OpenGL. Проверки с отдельным GPU-стендом
следует выполнять через [supervisor](raspberry-pi-benchmarks.md), с остановкой
и восстановлением службы. Длительный 24-часовой прогон не требуется.

Независимо от результата камеры, для отдельного исправления RPC обоснованы
контролируемый lifecycle запросов, корреляция поздних ответов, обработка смерти
isolate и ответа об ошибке. Регрессионные тесты должны воспроизводить заполнение
всех слотов, поздний ответ после deadline, ошибку handler/serializer и завершение
isolate; тестировать только обёртку `.timeout()` недостаточно.
