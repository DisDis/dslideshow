# Переход сборки и инструментов на Grinder/Dart — 30.10.2026

Проверяется рабочее дерево поверх `d4ef320d`, Flutter 3.47.7 / Dart 3.13.5,
Linux x64, 12 доступных CPU. Ниже раздельно сохранены первоначальная локальная
приёмка без production DEB и последующая полная сборка после уточнения состава
тестов. Установка на рамку, браузер, Google API, GPU и настоящая tracefs
на обоих этапах не запускались.
Рабочие команды и требования находятся в [tools](../../tools/README.md),
[выпуске](../releasing.md) и [README стенда](../../benchmarks/README.md).

## Решения и объём

* Сборка управляется закреплённым Grinder в самостоятельном пакете `tools`.
  Pub Workspaces и Melos не вводились; lock-файлы production-пакетов сохранены.
* Подготовка версии выполняется один раз на попытку, перед параллельными
  анализаторами, тестами, AOT и web. Повтор увеличивает build-номер снова;
  отказ не откатывает номер. Отдельные analyze/tests версии не меняют.
* DEB публикуется после полного успеха текущего запуска. Подготовленная версия,
  ApplicationInfo, native runtime и metadata проверяются; checkout блокируется
  до завершения cleanup. Частичный пакет не получает итоговое имя, существующий
  итоговый файл не заменяется даже при конкурирующей публикации.
* Действующие Python-тесты/CLI и inline Python в launchers перенесены на Dart.
  Исторические аппаратные эксперименты, source/raw/release-архивы и сторонние
  исходники не переписывались и не удалялись.
* По уточнению пользователя **тесты установщика Czkawka во временном DPKG_ROOT
  удалены без переноса**. Сам установщик и его вызов при настройке DEB сохранены.
  Установочные/runtime-скрипты на рамке остаются shell/Bash; шаблон DEB не изменён.

Grinder используется через программный `Grinder.start()`: CLI-обёртка библиотеки
сама вызывает `exit(1)` при ошибке, что обходило бы teardown и коды 130/143.
Своя тонкая точка входа сохраняет исключение, останавливает последующие
запрошенные задачи, освобождает очередь/потоки и возвращает корректный код.

Supervisor использует отдельные POSIX-группы и короткий фиксированный host-side
shell handshake перед `exec` буквальных argv. Он нужен для получения верных
идентичностей pipe после перенаправления stdio. Владелец отслеживает PID/start-time,
обычных и отделившихся потомков, завершает TERM/KILL и ждёт прекращения работы.
Выход leader с незакрытыми stdout/stderr не блокирует ошибку/отмену навсегда.
Обычный ненулевой результат отдельной coverage-suite не отменяет остальные suites.
Это код машины разработки/диагностического CLI, не замена установочных Bash-скриптов.

## Независимость проверок и исправления ревью

Comparator сохраняет 87 входов/ожидаемых результатов, снятых до удаления старой
реализации; отчёты/resume — отдельные прежние состояния. Native analyzer имеет
свои сохранённые входы/ожидания. Их происхождение и нормализация описаны в
[benchmark fixtures](../../tools/test/benchmarks/fixtures/README.md) и
[native fixtures](../../tools/test/benchmarks/native_pipeline/fixtures/README.md).
Ожидания не строятся из новой Dart-реализации.

На первом этапе process-тесты доказывали перекрытие четырёх ветвей через readiness/gates,
проверяли отказ каждой ветви, TERM-resistant и detached потомков, гонку старта,
реальные сигналы entrypoint, lock и no-clobber публикацию настоящего маленького DEB.
Позднейшее исключение тестов release-конвейера описано в конце этой записи.
Существующие media/визуальные эталоны не перегенерировались.

Ревью также закрыло сохранность прав существующего Ambient output-parent,
отмену посреди HTTP body с кодами 130/143, короткий HTTP timeout также для body, source/AOT
fingerprint coverage и canonical root через symlink. Успешный HTTP headers-тест
использует рабочую одиночную операцию, не короткое случайное окно sampling.

Первый общий прогон выявил уже имевшийся в `HEAD` пропуск `@ota_file_selected`
в русской ARB. Добавлены только совпадающие metadata placeholder `name`,
перевод/подпись не изменены. Выполнена штатная `flutter gen-l10n`; её вывод
использует текущую ширину форматирования 120. Существующие три i18n-регрессии прошли.

## Пределы вывода

Параллельность доказана функционально; одна пара измерений wall time не
подтверждает стабильный коэффициент ускорения или p95. Состав tooling tests
расширился относительно прежнего обязательного DEB-прогона, поэтому старое
общее время выпуска нельзя непосредственно сравнивать с новым.

ARM64 CLI был cross-compiled и проверен как AArch64 ELF с обычными glibc
зависимостями; x64 CLI и AOT fingerprint проверены локально. Это не аппаратная
приёмка launcher, tracefs, sudo, службы или GPIO на Pi. CPU/FPS диагностического
нового harness нельзя смешивать с прежними Python-запусками как один A/B.
Сохранённые отчёты относятся к своим сборкам; их raw/hash/числа не изменены.
Новый генератор media может давать другие JPEG/GIF-байты: новый seed/размер
не заменяет совпадение hashes входных медиа и условий baseline/candidate.

Тесты установки Czkawka исключены пользователем: работа предустановленного
CLI проверяется backend-сценариями, а установка/обновление DEB на устройстве
остаётся отдельной эксплуатационной проверкой.

## Три слота, Flutter concurrency 4 и группировка тестов

Следующий согласованный эксперимент сохраняет backend concurrency 1,
увеличивает общий лимит пакетных команд с 2 до 3 и явно задаёт Flutter
`--concurrency=4`. В прежнем запуске использовался штатный Flutter-лимит 6
для 12 логических CPU. Очередь и порядок команд не перестраивались, Wasm/JS,
AOT, сжатие и состав существующих assertions сохранены.

Добавлены `elapsedMs`, queued/dequeued и `queueWaitMs` от готовности всей
ветви; длительности фаз и дополнительный штатный JSON file-reporter каждого
пакета. Новый каталог выделяет основной контракт каждого suite в одну группу.
Выбор группы разрешён отдельной задаче `tests`; выпуск выполняет полный набор.
Автоматический выбор по изменённым файлам не включён.

На входе этой работы оба pubspec уже содержали `16.0.0+6`; этот номер не
откатывался. Первая попытка `16.0.0+7` завершилась отказом за **142,52 с**:
короткий startup guard двух gallery lifecycle-проверок и повторная компиляция
CLI в тесте неправильных аргументов не выдержали дополнительной нагрузки.
DEB не опубликован. Сохранённый JSON-профиль корректно показывает неполноту
и неуспех; повторное построение возвратило 1, структурных ошибок JSON — 0.

Для этих проверок введена одна компиляция настоящей точки входа в kernel на
файл тестов. Сценарии используют тот же код CLI/сервиса; проверки exit codes,
сигналов и освобождения ресурсов сохранены. Процесс и socket получают cleanup
сразу после запуска/получения. Компиляция ограничена 50 с, bootstrap — 60 с;
CLI-сценарии сохраняют 30 с, gallery readiness — 30 с, после сигнала — 8 с.
Это изменение тестовой инфраструктуры также входит в последующий замер.

Это суммы перекрывающихся интервалов, **не wall time группы и не CPU time**.
В `effects` 28 suites, из них 18 frontend. Нельзя вычесть эти суммы из полной
сборки или объявить условный пропуск безопасным по одному имени группы.

Кандидаты на последующий разбор, по длительности отдельного теста этого запуска:

Suite interval включает загрузку, подготовку и планирование. Например,
`terminal_backend_test` имеет всего 89 мс суммарных интервалов тестов при
22,221 с интервала suite; `camera_snapshot_client_test` — 137 мс при 22,468 с.
Это кандидаты на анализ стоимости запуска/уровня harness, а не доказательство
дорогих assertions. JSON-часы начинаются внутри runner: работа Flutter до
reporter не включена. Служебные загрузки и hooks показаны отдельно.

Группы не означают, что тест проверяет правильное свойство. Первичный просмотр
сохраняет два кандидата на усиление в
[открытых работах по эффектам](../plans/effects-work.md): проверки геометрии
`effect_rotation_coverage` / `effect_perspective_bounds` могут не выполнять
цикл assertions при отсутствии найденных объектов. Предпросмотр проверяет
wiring/смену/disposal и не заменяет frontend pixel tests. Автоматический
условный запуск потребует карты моделей, renderer/sessions, подготовки фото,
preview, shaders/assets, SDK/locks, test helpers и известного проверенного baseline.
