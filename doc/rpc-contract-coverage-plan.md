# Отложенный план проверки полноты RPC-контрактов

Записан 27.10.2026. Реализация отложена по решению пользователя; описанные ниже
проверки и `@RpcPayload()` пока не добавлены. Текущий builder и команды его
запуска описаны в [README генератора](../rpc_serializers_generator/README.md).

## Проблема

Builder проверяет корректность типов, перечисленных в `@RpcSerializers`.
Round-trip тесты закрепляют поведение существующих 57 регистраций. Если новый
класс забыли одновременно в аннотации и тестовых примерах, эти проверки
останутся зелёными. Число типов само по себе также не доказывает полноту.

Список регистрации остаётся один. Ожидаемый охват выводится из объявлений
контрактов, а не из второго списка имён.

## Уровень 1: обязательная регистрация команд и ответов

Статический анализатор просматривает все исходные библиотеки `backend/lib`
и `common/lib`, включая файлы, которые не экспортированы и нигде не импортированы.
Область задаётся пакетами с контрактами, не каталогом импортов реестра.
При появлении нового пакета с контрактами область явно расширяется.

Обязательные типы находятся по семантическому наследованию от `RpcResult`
и `WebSocketResult`. `RpcCommand` уже реализует `RpcResult`, а WebSocket-команды
входят в иерархию `WebSocketResult`. Промежуточные error-интерфейсы также
учитываются. Проверка сравнивает найденные типы с `@RpcSerializers` и сообщает
все отсутствующие регистрации вместе с исходным файлом и строкой.

Идентичность класса определяется библиотекой и объявлением; одинокая строка
имени недостаточна. Префиксы импорта, реэкспорты и косвенное наследование
не должны влиять на результат.

Сгенерированные реализации Freezed не считаются самостоятельными контрактами.
Нельзя исключать все `abstract`/`sealed` классы: публичные Freezed-модели тоже
имеют эти модификаторы. Базовые интерфейсы протокола исключаются явно;
для новых промежуточных баз нужен явный признак роли, а не эвристика по отсутствию
`fromJson`/`toJson`. Отсутствующий JSON-метод у payload должен давать ошибку.

Пример диагностики:

```text
Missing RPC serializer: NewCommand
backend/lib/src/command/new_command.dart:12
Add NewCommand to @RpcSerializers.
```

## Уровень 2: самостоятельно передаваемые DTO

`SystemInfo`, `CpuInfo`, `WiFiNetworkInfo` и некоторые другие текущие регистрации
не реализуют RPC-интерфейсы. По одному наличию `toJson` нельзя отличить такой
payload от модели, которая всегда передаётся внутри другого объекта.
При внедрении размечаются и все нынешние самостоятельно передаваемые DTO.

Предлагаемый явный маркер:

```dart
@RpcPayload()
class SomeInfo {
  // fromJson / toJson
}
```

Маркер объявляется в common рядом с `RpcSerializers` и требуется только для DTO,
передаваемых самостоятельно. Команды и ответы обнаруживаются через интерфейсы
без дополнительной аннотации. Обязательное множество уровня 1 объединяется
с множеством помеченных DTO; любой пропуск в реестре является ошибкой.
Вложенные модели не обязаны иметь собственный wire tag.

Проверка не может угадать намерение передавать обычный DTO самостоятельно,
если разработчик не обозначил его ни интерфейсом, ни маркером. Это ограничение
должно быть явно описано в правилах добавления контракта.

## Уровень 3: полнота тестовых примеров

Для каждого зарегистрированного типа нужен явно типизированный пример с
ожидаемым wire tag. Проверка сравнивает множества объявленных типов примеров
и регистраций, а не их размеры. Нельзя определять тип примера через
`runtimeType`: Freezed возвращает приватную реализацию.

Сопоставление реализуется через analyzer по явно указанным типам fixtures
либо через минимальный генерируемый каталог типов для тестов. При реализации
выбрать один способ и не создавать второй ручной реестр контрактов.

Для каждого примера выполняется:

```text
объект → serialize → JSON encode/decode → deserialize → serialize
```

Отдельно сохраняются проверки ожидаемых строковых тегов и важных JSON-полей.
Симметричный round-trip не обнаруживает согласованное переименование тега
в encode/decode. Проверяются также вложенные payload, неизвестные типы и ошибки.
Полнота fixtures не заменяет предметные проверки значений и совместимости JSON.

## Размещение и включение в проверки

Общий код проверки разместить в `rpc_serializers_generator`, а обязательный
интеграционный тест — в `backend/test/rpc_contract_coverage_test.dart`.
Тогда обычный backend `dart test` и существующий `deb_factory/run_tests.sh`
проверяют реальную полноту автоматически. Плагин IDE можно добавить позже;
он не является условием первого этапа.

Проверка охвата должна работать независимо от наличия новых импортов в реестре.
Не ограничивать её текущим `GeneratorForAnnotation`: поиск
[`BuildStep.findAssets`](https://pub.dev/documentation/build/latest/build/BuildStep-class.html)
ограничен текущим пакетом. Межпакетный обход реализовать отдельным analyzer check
с корректным разрешением package URI и конфигураций обоих пакетов.

В CI сначала генерировать код, затем проверять анализатор и тесты, а также
отсутствие изменений и новых незакоммиченных generated-файлов после генерации.

## Приёмка будущей реализации

Регрессионные сценарии: новый контракт в неимпортированном файле; косвенное
наследование; abstract/sealed Freezed API и приватная generated-реализация;
помеченный DTO и обычная вложенная модель; отсутствующий JSON-метод;
дубли имён из разных библиотек; пропущенный fixture при наличии регистрации;
переименование wire tag; контракт в common; исключение test/tool-классов.

Диагностика должна перечислять все нарушения, а не останавливаться на первом.
Сейчас этот документ фиксирует будущую работу и не меняет поведение backend.
