# Backend фоторамки

Backend предоставляет сервисы устройства, медиатеки, настройки, HTTP/WebSocket
и OTA. Локальные зависимости и общие команды сборки описаны в
[руководстве приложения](../dslideshow_flutter/README.md).

## Сервисы и изоляты

Сервис — обычный объект Dart; выделение класса или файла не создаёт isolate.
Существующие точки входа остаются прежними:

* `hw_frame.serviceMain` — backend-isolate с GPIO, MQTT, экраном, хранилищем,
  Wi-Fi и SystemInfo; он запускает web-isolate.
* `web_server.serviceMain` — HTTP/WebSocket и галерея.
* `ota.serviceMain` — обновления, запускается frontend отдельно от backend.

Worker миниатюр сохраняет существующий механизм выполнения. Рефакторинг
подписок и WebSocket-сессии не добавляет изолятов, таймеров, очередей событий
или сетевых клиентов.

## Границы ответственности

| Класс | Ответственность и владелец |
| --- | --- |
| `HardwareService` | RPC-обработчики, готовность сервисов, отправка команд во frontend и последовательная очередь уведомлений экрана. Создаёт и освобождает `DeviceEventBindings`. |
| `DeviceEventBindings` | Подписки на кнопки/присутствие GPIO, подготовку видимости экрана и команды MQTT. Живёт в том же backend-isolate; вызывает переданные обработчики и существующий `ScreenService`. |
| `WebService` | HTTP-сервер, маршруты, сервисы галереи и список активных WebSocket-пользователей. Создаёт `WebSocketUser` на каждое соединение. |
| `WebSocketUser` | Авторизация, кодирование сообщений, config-команды, RPC proxy и ожидающие ответы одного соединения. Реализация находится в `lib/src/web_server/web_socket_user.dart`. |

`DeviceEventBindings` подключает потоки в прежнем порядке: кнопки GPIO,
подготовка экрана, присутствие GPIO, MQTT pause, screen и menu. Значения pause
и menu передаются без преобразования; screen сохраняет инверсию значения,
которую ожидает frontend-действие `SlideshowAction.toggleScreen`. Поля кнопки
передаются без изменений. Категория и сообщения логирования сохранены.

`HardwareService.dispose()` ожидает отмену всех этих подписок перед освобождением
`ApplicationStateService`, экрана, GPIO, Storage и SystemInfo. Повторный вызов
возвращает то же завершение. Сам `DeviceEventBindings` владеет только подписками:
он не закрывает внедрённые сервисы и не ожидает уже отправленные RPC.
Состояние и переходы экрана остаются в `ScreenService`, current/next — в Storage.
Подробнее: [сон экрана и присутствие](../doc/screen-presence.md).

Для совместимости `web_service.dart` повторно экспортирует `WebSocketUser` и
`WebSocketUserStatus`. Новый код может импортировать файл сессии напрямую.
Wire-формат, задержка авторизации, обработка ошибок, config/RPC-команды и
отключение пользователей при остановке HTTP-сервера сохраняются. Перенос
не меняет существующую политику таймаутов и очистки WebSocket pending-запросов.

## Локальные проверки

Из каталога `backend/`, без обновления зависимостей:

```bash
dart analyze
dart test
dart test test/device_event_bindings_test.dart test/hardware_screen_test.dart \
  test/frame_state_test.dart test/web_socket_user_test.dart \
  test/web_socket_config_test.dart
```

Для HTTP-регрессий нужны разрешённые локальные сокеты. Тесты подписок используют
управляемые потоки и подменяемое питание: проверяют передачу кнопок/MQTT,
присутствие, порядок уведомлений, отмену ожидающих событий и завершение cleanup.
WebSocket-тесты проверяют авторизацию, echo, proxy RPC, config, корреляцию ответов
и явное отключение через существующий сериализатор. Дополнительно настоящий
локальный HTTP/WebSocket проверяет подключение через маршрут `WebService` и
отключение сессии при закрытии сервера. Физические GPIO, MQTT broker, DPMS
и питание экрана локально не проверяются.

Проверка выделения классов 27.10.2026 по решению пользователя ограничена локальным
окружением. Полный backend-прогон: 316 тестов; анализатор и форматирование прошли.
Синтетическая AOT-проба в порядке ABBAABBA проверила по 300 000 входных событий
и 50 000 WebSocket echo-сообщений в каждом процессе; число FD осталось 8→8.
Исходники baseline/candidate, бинарники и сырые результаты сохранены в
`benchmarks/reports/backend-extraction-2026-10-27/`; там же находится README
с командами повтора. Это проверка локальных CPU-путей и cleanup с подменяемыми
источниками событий, без заявления об ускорении или аппаратной приёмке.

Правила аппаратных запусков и восстановления службы — в
[руководстве RaPi5](../doc/raspberry-pi-benchmarks.md), инструменты измерений —
только в [benchmarks](../benchmarks/README.md). Сам перенос классов не является
подтверждённой оптимизацией производительности.
