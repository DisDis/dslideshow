# Backend фоторамки

Backend предоставляет сервисы устройства, медиатеки, настройки, HTTP/WebSocket
и OTA. Локальные зависимости и общие команды сборки описаны в
[руководстве приложения](../dslideshow_flutter/README.md).

## Руководства и конфигурация

* [Язык фоторамки](../doc/language.md): корневой `language`, значения по умолчанию
  и применение после перезапуска.
* [Настройки эффектов](../doc/effect-settings.md): `slideshow.effects`, хранение
  карты `EffectType`, удаление defaults, Fade для пустого набора; диапазоны
  и сочетания проверяет config_app, backend сохраняет разобранную модель.
* [Специальные экраны](../doc/special-screens.md): типы, расписания, JSON,
  обработка неизвестных экранов и правила компактной сериализации.
* [Галерея](../doc/gallery.md): FFmpeg/JPEG, API, publication/revision,
  budgets, cache policy, конфигурация и диагностика.
* [Медиа и OTA](../doc/uploads.md): потоковый приём, серверные HTML-формы,
  импорт/экспорт `config.json`, ограничения и ошибки. OTA работает в процессе
  Flutter; отдельной recovery-службы нет. HTTP 200 означает приём пакета,
  итог установки передаётся отдельно. Настройки применяются после перезапуска.
* [Google Photos](../doc/plans/google-photos-plan.md): открытые вопросы доступа
  к альбому и автоматизации внешнего googleapis.

Подтверждение запуска/остановки `WebServerControlCommand` ждёт реального
HTTP bind/close; ошибка возвращается через обычный RPC-отказ. `alwaysEnabled`
сохраняет приоритет. [Экран доступа, диагностика и регрессии](../doc/config-page-states.md).
По указанию пользователя код выводится на INFO при обновлении, настройке
постоянного кода и старте web-сервера для отладки рамки.

## Сервисы и изоляты

Сервис — обычный объект Dart; выделение класса или файла не создаёт isolate.
Существующие точки входа остаются прежними:

* `hw_frame.serviceMain` — backend-isolate с GPIO, MQTT, экраном, хранилищем,
  Wi-Fi и SystemInfo; он запускает web-isolate.
* `web_server.serviceMain` — HTTP/WebSocket и галерея.
* `ota.serviceMain` — обновления, запускается frontend отдельно от backend.

Каждая генерация миниатюры запускает один процесс FFmpeg без новых Dart-isolates.
Выделение подписок, WebSocket-сессии и сборщика состояния не добавляет изолятов, таймеров, очередей
событий или сетевых клиентов.

## Локальные зависимости миниатюр

В PATH должен быть `ffmpeg` (Debian/Ubuntu: пакет `ffmpeg`).
Проверены FFmpeg 5.1.9 (Debian 12 и команда на RaPi arm64) и 8.0.1 (Linux x64).
Для другой сборки сначала выполните обязательные codec-тесты: набор демультиплексоров/кодеков и EXIF может отличаться.
Установка пакетов скриптами проекта не выполняется.

```sh
ffmpeg -version
# Из backend/; Python 3 нужен для процессных регрессионных тестов.
dart test test/ffmpeg_thumbnail_worker_test.dart test/thumbnail_service_test.dart test/gallery_http_test.dart test/gallery_config_test.dart --concurrency=1
```

Linux-проверки освобождения исходных файлов обходят `/proc/self/fd` без
следования по ссылкам: дескриптор может закрыться между перечислением и чтением
его ссылки. Ошибки чтения отдельной ссылки не срывают проверку; ошибка самого
обхода не превращается в пустой результат. Проверки timeout, завершения
дочернего процесса и отсутствия оставшихся открытых исходников сохраняются.

`FfmpegThumbnailWorker` запускает один FFmpeg на задачу, без новых Dart-isolates.
Для миниатюр `ffmpeg` обязателен, `ffprobe` не нужен; при отсутствии executable миниатюры дают
503, оригиналы остаются доступны. Слот удерживается до cleanup дочернего процесса.

Все размеры, качество, бюджеты и JSON заданы в едином
[руководстве галереи](../doc/gallery.md#настройки-gallery).
Подробное логирование web-isolate включается через `log.web = "ALL"` после
перезапуска; [категории и сбор лога](../doc/gallery.md#диагностика-на-рамке).
Несовместимость RGBA drawbox с FFmpeg 5.1 и проверка RGB-фона сохранены в
[отчёте](../benchmarks/reports/gallery-ffmpeg51-diagnostics-2026-10-27/report.md).

## Инструменты управления медиатекой

Индекс каталога строится и хранится в памяти. ID — SHA-256 относительного пути,
версия — хеш stat-полей и общей метки инвалидации. `serverId` отсутствует.
На диске остаётся только `catalog.epoch` размером 32 байта: обычный scan его
не меняет, `forceInvalidate` заменяет. `catalog.json` не используется.
ID и версии неизменённых файлов сохраняются после перезапуска; список файлов
не сериализуется на диск. Последние 64 ID обновлений помнятся только в памяти.

Версии оригиналов основаны на типе, размере, `mtime` и `ctime`. После загрузки,
поворота, переноса в корзину или восстановления web-isolate вызывает
`GalleryCatalogService.markDirty()`. Уведомление хранится только в памяти;
оно не теряется при завершении уже начатого scan. `GalleryPublication` и
`publication.version` удалены. Неизменённые файлы сохраняют свои миниатюры.
Внешние изменения обнаруживаются watcher/периодической stat-сверкой; Google
Photos в схеме уведомлений не учитывается. При совпадении всех stat-полей
нужна явная инвалидация кеша;
подробности — в [руководстве версий](../doc/gallery.md#api-и-инвалидация).

Коллекция фоторамки может содержать **50 000+ медиафайлов**; это штатный объём
для проектирования сервисов. Индексы каталога, ограниченные очереди и ленивые
миниатюры описаны в [руководстве больших коллекций](../doc/gallery.md#большие-коллекции-50-000-медиафайлов).
Лимиты кандидатов Czkawka, размера JSON каталога корзины и числа файлов в команде
считаются отдельно от общего размера библиотеки.
Диагностические сводки и безопасные ID — часть приёмки;
[категории и уровни логов управления](../doc/gallery.md#логи-управления-медиатекой).

Настроенный каталог `images` может быть симлинком, в том числе цепочкой
относительных ссылок для `bin/web_server_test.dart`. Файловые операции фиксируют
его канонический корень и проверяют дочерние пути внутри него; симлинки медиа
и вложенных папок по-прежнему отклоняются. После перенастройки ссылки корня
нужен новый экземпляр сервиса: прежний возвращает `revisionMismatch`
с безопасной диагностикой `reason=rootChanged`. Корзина находится в
`<gallery state>/trash` (обычно `images.gallery/trash`), а не рядом с целью
симлинка оригиналов.
Пересечение её физического дерева с оригиналами и перенос между разделами
не допускаются. Причины отказа вроде `symlinkSegment` и `rootOverlap`
попадают в ограниченные сводки без раскрытия реальных путей.

Корзина — обычное дерево с исходными относительными путями:
`images/album/photo.jpg` → `images.gallery/trash/album/photo.jpg`.
Соседние `thumbnails/` и `duplicates/` принадлежат своим сервисам; очистка
миниатюр не удаляет корзину. Удалять весь `images.gallery` как кеш нельзя.
Manifest, sidecar-файлы и результаты операций в ней не сохраняются.
Список и версии строятся из файловой системы. Перенос использует `File.rename`
без FFI: занятый при проверке путь возвращает конфликт. Проверка и перенос
выполняются отдельно; создание целевого файла внешним процессом между ними
может привести к его замене. Требования и ограничения — в
[руководстве корзины](../doc/gallery.md#корзина).

Сведения и физический поворот выполняются на backend, поиск дубликатов —
отдельным headless-процессом. При установке DEB `postinst` скачивает Czkawka CLI
12.0.2 ARM64 с проверкой SHA-256 и запуска; остальные инструменты задаются
зависимостями DEB. Для локальной разработки их нужно установить отдельно.
Нужные executable должны быть доступны службе через PATH:

| Назначение | Executable | Пакет Debian/Ubuntu |
| --- | --- | --- |
| Миниатюры и сведения о видео | `ffmpeg`, `ffprobe` | `ffmpeg` |
| Поворот JPEG без повторного сжатия | `jpegtran` | `libjpeg-progs` или `libjpeg-turbo-progs` |
| Сохранение прав доступа результата поворота | `chmod` | `coreutils`, базовый Essential-пакет Debian |
| Точные копии и похожие фотографии | `czkawka_cli` | ARM64 release 12.0.2 из `postinst`; для разработки — совместимый `czkawka-cli` или release binary |

DEB создаёт `/usr/local/bin/czkawka_cli`; служба systemd получает явный PATH
с `/opt/dslideshow/bin` первым. Интернет при установке, офлайн-повтор,
системные зависимости, отказ установки и диагностика описаны в
[README упаковки](../deb_factory/readme.md#установка-czkawka-cli-на-фоторамке).

Адаптер JSON явно принимает ветки Czkawka CLI **8.x и 12.x**. Неизвестная ветка
возвращает типизированный отказ `unsupported`; совпадение имени executable
само по себе не подтверждает контракт. Оба режима ожидают итоговый JSON после
завершения CLI. Для 8.x используются общие аргументы; вывод результатов
в stdout считывается и отбрасывается, служебный кеш изолирован во временном
каталоге задачи. Для 12.x дополнительно отключается кеш и печать результатов.
stderr и время процесса ограничены. JSON результата читается целиком через
`readAsString()` после завершения CLI и разбирается в worker-isolate;
лимиты `maxResultBytes` и `maxStateBytes` удалены. Временные JSON/кеш/конфигурация
удаляются после cleanup процесса. При отсутствии executable API возвращает
HTTP 503 с `GalleryErrorCode.unavailable`; для асинхронного поиска этот код
сохраняется в состоянии `failed` задачи.

Одинаковые наборы участников из точного и похожего режимов сводятся к одной
группе с приоритетом «Точных копий». Более широкие похожие группы сохраняются
отдельно. Нормализация применяется также при чтении `job.json`, без его
перезаписи; новые результаты сохраняются уже без повторных групп.

В похожем поиске явно передаётся `--image-filter Lanczos3`, чтобы уменьшение
до перцептивного хеша было устойчивее к исходному разрешению. Порог, размер
и алгоритм хеша остаются штатными параметрами CLI; точный режим не меняется.
В сводке запуска похожего режима виден безопасный `imageFilter=Lanczos3`.
Изменение применяется только к новым поискам после обновления backend;
сохранённый `job.json` не пересчитывается. Это не гарантия обнаружения любых
вариантов кадра: в Czkawka 12.0.1 две группы с несколькими одинаковыми копиями
разных перцептивных хешей могут оставаться раздельными. Подробнее — в
[руководстве поиска](../doc/gallery.md#поиск-и-сравнение-дубликатов).

Локальные реальные codec/CLI-регрессии проверяют Czkawka 8.0.0, 12.0.1 и 12.0.2,
FFmpeg 8.1.2, Dart `exif` 3.3.0 / `image` 4.12.0,
JPEG IJG 9f и libjpeg-turbo 3.1.3 на Linux x64.
Оба варианта `jpegtran` допустимы: проверка `jpegtran -version` не используется,
поскольку IJG 9f не поддерживает этот аргумент. Наличие команды и поддержка
`-perfect`, преобразований и `-copy all` проверяются настоящим поворотом.
Новая комбинация версий требует тех же проверок качества, EXIF/ICC и cleanup.

```sh
command -v ffmpeg ffprobe jpegtran chmod czkawka_cli
czkawka_cli --version
# Из backend/; Python 3 нужен для управляемых процессных отказов.
dart test --concurrency=1 test/gallery_tool_runner_test.dart \
  test/gallery_media_tools_test.dart test/gallery_duplicate_cli_test.dart
# Только real CLI-тест допускает отдельный абсолютный путь для проверки адаптера:
CZKAWKA_CLI=/absolute/path/to/czkawka_cli dart test test/gallery_duplicate_cli_test.dart
```

EXIF и сведения изображений читаются в Dart пакетом `exif`; разрешение
берётся из заголовков JPEG/PNG/WebP/GIF, ICC — из контейнера. PNG поворачивается
пакетом `image` в отдельном worker-isolate с обновлением EXIF Orientation
и размеров. ExifTool не входит в runtime-зависимости. Политика сохранения
метаданных JPEG/PNG различается: JPEG оставляет результат `jpegtran -copy all`,
а изменение прочитанных пакетом `exif` тегов даёт безопасный WARNING без
возврата исходных EXIF-блоков. Проверки формата/геометрии/ICC остаются.
Подробности — в
[руководстве поворота](../doc/gallery.md#поворот-оригинала).

Отсутствие инструмента в настоящем codec/CLI-тесте — явная ошибка prerequisite,
а не пропущенный сценарий. VM-тесты проверяют локальные файлы и процессы;
они не подтверждают ARM64 ABI, нагрузку слайдшоу или производительность RaPi.
Установщик DEB проверяет запуск закреплённой ARM64-сборки на текущей ОС рамки;
это не заменяет проверку поиска на устройстве. Подключать unstable-репозиторий
или обновлять ОС ради утилиты не требуется. Политика Depends и загрузки
описана в [README упаковки](../deb_factory/readme.md).

## Границы ответственности

| Класс | Ответственность и владелец |
| --- | --- |
| `HardwareService` | RPC-обработчики, готовность сервисов, отправка команд во frontend и последовательная очередь уведомлений экрана. Создаёт `DeviceEventBindings` и `FrameStateReader`, владеет ожиданиями frontend и освобождением сервисов. |
| `DeviceEventBindings` | Подписки на кнопки/присутствие GPIO, подготовку видимости экрана и команды MQTT. Живёт в том же backend-isolate; вызывает переданные обработчики и существующий `ScreenService`. |
| `FrameStateReader` | Сбор `FrameState` из frontend, наблюдений `ApplicationStateService` и текущего состояния `ScreenService`; объединение запросов frontend-состояния. Использует механизм ожидания и проверку жизненного цикла, переданные `HardwareService`. |
| `WebService` | HTTP-сервер, маршруты, сервисы галереи и список активных WebSocket-пользователей. Создаёт `WebSocketUser` на каждое соединение. |
| `WebSocketUser` | Авторизация, кодирование сообщений, config-команды, RPC proxy и ожидающие ответы одного соединения. Реализация находится в `lib/src/web_server/web_socket_user.dart`. |

`DeviceEventBindings` подключает потоки в прежнем порядке: кнопки GPIO,
подготовка экрана, присутствие GPIO, MQTT pause, screen и menu. Значения pause
и menu передаются без преобразования; screen сохраняет инверсию значения,
которую ожидает frontend-действие `SlideshowAction.toggleScreen`. Поля кнопки
передаются без изменений. Категория и сообщения логирования сохранены.

`HardwareService.dispose()` ожидает отмену всех этих подписок перед освобождением
`ApplicationStateService`, экрана, GPIO, Storage и SystemInfo. Повторный вызов
возвращает то же завершение. Сам `DeviceEventBindings` владеет только подписками:
он не закрывает внедрённые сервисы и не ожидает уже отправленные RPC.
Состояние и переходы экрана остаются в `ScreenService`, current/next — в Storage.
Подробнее: [сон экрана и присутствие](../doc/screen-presence.md).

### Снимок состояния рамки

`FrameStateReader` находится в `lib/src/service/hardware/src/frame_state_reader.dart`
и работает в существующем backend-isolate. `HardwareService` делегирует ему сбор
снимка для `GetFrameStateCommand` и после подтверждения `SetFrameControlCommand`.
RPC id, формирование ответов/ошибок и выполнение команд остаются в фасаде.
Поля присутствия, питания, блокировки и фазы экрана читаются после ожидания
frontend; время снимка задаётся в UTC. Системные метрики остаются в SystemInfo.

Одновременные чтения используют один запрос состояния frontend. Готовые снимки
между чтениями не кешируются. Предел ожидания остаётся 3 секунды; timeout
возвращает снимок с `frontend: null`, сохраняя сведения backend. Пока исходный
RPC после timeout не завершился, повторные чтения используют тот же результат
ожидания и не занимают новые transport slots. Позднее завершение позволяет
следующему чтению запросить frontend заново.

После подтверждения команды управления фасад вызывает
`invalidateFrontendRequest()` и читает новый снимок: опрос до подтверждения мог
содержать старое намерение. Уже начатые чтения завершаются со своим результатом;
позднее завершение старого запроса не сбрасывает более новый незавершённый запрос.

Таймеры ожидания и их отмена при закрытии остаются в `HardwareService`, общими
для чтения и управления. Reader проверяет переданный `ensureActive` перед
запросом и после ожидания. У него нет собственного `dispose()`, подписок,
таймеров или транспорта: он не меняет правила закрытия и текст прежних ошибок.
Категория логирования также передаётся фасадом и сохраняется.

### WebSocket-сессии

Для совместимости `web_service.dart` повторно экспортирует `WebSocketUser` и
`WebSocketUserStatus`. Новый код может импортировать файл сессии напрямую.
Wire-формат, задержка авторизации, обработка ошибок, config/RPC-команды и
отключение пользователей при остановке HTTP-сервера сохраняются. Перенос
не меняет существующую политику таймаутов и очистки WebSocket pending-запросов.

## Реестр RPC-сериализаторов

Единственный список передаваемых типов находится в `lib/serializers.dart`:
`@RpcSerializers([...])` над `final Serializers serializers = _$serializers`.
Аннотация и runtime-интерфейс объявлены в `common/lib/serializers.dart`.
Отдельный пакет `rpc_serializers_generator`, соседний с backend, подключён
как path-зависимость в `dev_dependencies`. Он создаёт `lib/serializers.g.dart`
через обычный `dart run build_runner build` из `backend/`. В watch-режиме
используется `dart run build_runner watch` или `./generate_models.sh`.
Генерируемый файл хранится в Git; редактировать его вручную не нужно.

Классовые `fromJson`/`toJson` по-прежнему создают json_serializable/Freezed.
Новый builder генерирует только их регистрацию, сохраняя 57 прежних типов,
формат `["EchoCommand", {"id": 7, "text": "hi", "type": "echo"}]`, порядок
проверок, обработку неизвестных типов и прежнее поведение декодирования.
Имя класса становится строкой при генерации; `Type.toString()` и рефлексия
во время выполнения не используются. Переименование класса меняет wire tag.
Isolate, транспорт и вызовы потребителей реестра не изменяются.

Старый `bin/gen_serializers.dart` удалён: он содержал второй, неполный список
и мог перезаписать актуальные регистрации. Добавляйте тип только в аннотацию
и запускайте build_runner. Диагностика дублей, требования к моделям, пример
подключения и тесты builder описаны в [README генератора](../rpc_serializers_generator/README.md).

Обнаружение забытых типов и полнота тестового охвата отложены:
[три уровня будущей статической проверки](../doc/plans/rpc-contract-coverage-plan.md).

## Локальные проверки

[Ответственность тестов сериализации/OTA и быстрые команды](../doc/testing.md).

Из каталога `backend/`, без обновления зависимостей:

```bash
dart analyze
dart test --concurrency=1
dart test --concurrency=1 test/device_event_bindings_test.dart test/hardware_screen_test.dart \
  test/frame_state_reader_test.dart test/frame_state_test.dart test/web_socket_user_test.dart \
  test/web_socket_config_test.dart
```

Для HTTP-регрессий нужны разрешённые локальные сокеты. Тесты подписок используют
управляемые потоки и подменяемое питание: проверяют передачу кнопок/MQTT,
присутствие, порядок уведомлений, отмену ожидающих событий и завершение cleanup.
WebSocket-тесты проверяют авторизацию, echo, proxy RPC, config, корреляцию ответов
и явное отключение через существующий сериализатор. Дополнительно настоящий
локальный HTTP/WebSocket проверяет подключение через маршрут `WebService` и
отключение сессии при закрытии сервера. Физические GPIO, MQTT broker, DPMS
и питание экрана локально не проверяются.

Тесты `FrameStateReader` проверяют поля снимка, все фазы экрана, объединение
чтений и отсутствие кеширования завершённого снимка, отказы frontend и проверки
жизненного цикла владельца. Интеграционные RPC-тесты дополнительно проверяют
трёхсекундный timeout, чтение после управления, старый ответ во время нового
запроса, сохранение входных RPC id и закрытие во время обеих фаз управления.
Проверки этого этапа по решению пользователя выполняются только локально.
Синтетическая локальная AOT-проба выделения WebSocketUser/DeviceEventBindings
проверяла по 300 000 входных событий и 50 000 echo в процессе, FD 8→8;
одноразовый комплект удалён при очистке 29.10.2026. Это датированное наблюдение,
не подтверждение текущей аппаратной производительности. Действующее покрытие
сохраняется в backend tests; числа старых тестовых прогонов не являются приёмкой
нового кода.

Правила аппаратных запусков и восстановления службы — в
[руководстве RaPi5](../doc/raspberry-pi-benchmarks.md), инструменты измерений —
только в [benchmarks](../benchmarks/README.md).
