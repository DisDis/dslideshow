# Backend фоторамки

Backend предоставляет сервисы устройства, медиатеки, настройки, HTTP/WebSocket
и OTA. Локальные зависимости и общие команды сборки описаны в
[руководстве приложения](../dslideshow_flutter/README.md).

## Руководства и конфигурация

* [Язык фоторамки](../doc/language.md): корневой `language`, значения по умолчанию
  и применение после перезапуска.
* [Настройки эффектов](../doc/effect-settings.md): `slideshow.effects`, хранение
  карты `EffectType`, удаление defaults, Fade для пустого набора; диапазоны
  и сочетания проверяет config_app, backend сохраняет разобранную модель.
* [Специальные экраны](../doc/special-screens.md): типы, расписания, JSON,
  обработка неизвестных экранов и правила компактной сериализации.
* [Галерея](../doc/gallery.md): FFmpeg/JPEG, API, publication/revision,
  budgets, cache policy, конфигурация и диагностика.
* [Медиа и OTA](../doc/uploads.md): потоковый приём, серверные HTML-формы,
  импорт/экспорт `config.json`, ограничения и ошибки. OTA работает в процессе
  Flutter; отдельной recovery-службы нет. HTTP 200 означает приём пакета,
  итог установки передаётся отдельно. Настройки применяются после перезапуска.
* [Google Photos](../doc/plans/google-photos-plan.md): открытые вопросы доступа
  к альбому и автоматизации внешнего googleapis.
* [Яндекс Диск](../doc/yandex-disk.md): `YandexDriveStorage`, несколько аккаунтов,
  почасовой импорт выбранных папок, Device Flow и приватное хранение токенов.

Подтверждение запуска/остановки `WebServerControlCommand` ждёт реального
HTTP bind/close; ошибка возвращается через обычный RPC-отказ. `alwaysEnabled`
сохраняет приоритет. [Экран доступа, диагностика и регрессии](../doc/config-page-states.md).
По указанию пользователя код выводится на INFO при обновлении, настройке
постоянного кода и старте web-сервера для отладки рамки.

### Wi-Fi: завершение RPC и диагностика

Изменяющие команды `rescan`/`add`/`remove` подтверждаются только после
успешного завершения системной операции. Отказ запуска, ненулевой exit code
или истечение срока возвращают ошибку с ID исходного RPC; ошибка чтения списка
также не подменяется пустым успешным результатом. Автоматического повтора
мутаций нет. После подтверждения панель запрашивает актуальные списки.

`WiFiService` использует `BoundedSystemCommandRunner` со сроком 60 секунд,
лимитом вывода 64 КиБ и эскалацией TERM → KILL через одну секунду. На Linux
завершается вся принадлежащая операции группа процессов; ошибка возвращается
после завершения процесса и чтения его каналов. `close()` прекращает активные
команды и ожидает cleanup; `HardwareService.dispose()` ожидает и этот сервис.
Панель ждёт каждый Wi-Fi RPC 65 секунд; остальные RPC сохраняют срок 15 секунд.
Disconnect/таймаут транспорта означает неизвестный результат: панель предлагает
проверить рамку перед повтором и не повторяет мутацию самостоятельно.

Категория `WiFiService` пишет начало и итог системной операции на INFO,
отказ — на WARNING. `action`, безопасный
тип/код ошибки позволяют различить отказ запуска и ненулевой
exit code/таймаут; исходные исключения сохраняются вместе со стеком. Обычное закрытие имеет причину `cancelled` и
уровень INFO. Отдельных дампов аргументов и stdout/stderr нет; текст исходного
исключения, включая реквизиты, не маскируется. Наружу передаётся прикладное исключение без
ссылки на исходный `ProcessException`. Некорректная строка ответа nmcli
диагностируется номером строки, исходной ошибкой разбора и стеком.

`HardwareService` связывает начало/итог Wi-Fi RPC через `rpcId`; `WifiTabBloc`
записывает начало/итог операции, отказ, неизвестный результат или отмену,
передавая исходное исключение и стек в logger по [общим правилам](../doc/logging.md).

`WiFiService(commandRunner: ...)` позволяет подменять только внешнее выполнение
процесса. Регрессии используют рабочие сервисы и реальные записи logger:

```sh
dart test --concurrency=1 test/wifi_service_test.dart test/wifi_service_diagnostics_test.dart test/wifi_rpc_completion_test.dart test/system_command_runner_test.dart
```

Wi-Fi-проверки не запускают `sudo`/`nmcli` и не изменяют сеть машины.
Проверки bounded runner используют локальные дочерние процессы для deadline,
cleanup и ограничения вывода. Реальное переключение сети и доставка ответа
после смены Wi-Fi требуют отдельной аппаратной приёмки.

Подтверждённая мутация отдельно записывается как `WifiTabBloc event=acknowledged`.
Если последующее чтение списков не удалось, панель сообщает об ошибке обновления
списков, сохраняя известный итог операции; в логах `refreshFailed` содержит
исходное действие.

### MQTT: подключение, команды и освобождение

`MqttService` публикует discovery и текущее состояние рамки, подписывается на
три точных command topic (`pause`, `screen`, `menu`) и принимает только `ON`/`OFF`.
Остальные topic и некорректные payload не меняют состояние. Автоматическое
восстановление транспорта выполняет `mqtt_client`: он сохраняет собственный
subscription manager и восстанавливает подписки. Сервис повторно публикует
discovery и актуальное состояние, сохраняя по одной подписке на входящие сообщения
и изменения `ApplicationStateService`.

Помимо `pause`, `screen`, `menu` и бинарного `motion` публикуется обычный sensor
`storageStatus` с именем `Storage Status`. Его discovery prefix определяется
`getDiscoveryPrefix('sensor', 'storageStatus')`; состояние в стандартном `/state`
содержит имя enum: `download`, `off` или `done`. Discovery публикуется в `/config`.
Изменения всех полей `ApplicationState`, включая `storageStatus`, проходят через
общий trailing debounce 500 мс. При подключении и восстановлении MQTT сразу
публикует актуальное состояние агрегата.

`ready` позволяет дождаться первой попытки подключения. `close()` отключает
автовосстановление, отменяет принадлежащие сервису подписки, отключает клиент
и закрывает потоки действий; `HardwareService.dispose()` ожидает его.
Отказ отмены подписки диагностируется, но не прерывает остальное освобождение.
Позднее завершение подключения и сохранённые callback не создают новых действий
после закрытия. Переданный через `client:` внешний MQTT-клиент позволяет
проверять этот контракт без broker.

Категория `MqttService` пишет переходы подключения, восстановления и закрытия
на INFO; ошибки — на WARNING с безопасным типом. Входящий пакет имеет одну
сводку `received`/`accepted`/`rejected`/`ignored`. Topic, payload, учётные данные
не дампятся отдельно; исходные исключения и стек передаются в logger. Подтверждение команды
публикуется только после проверки её topic и значения.

```sh
dart test --concurrency=1 test/mqtt_service_test.dart test/hardware_screen_test.dart
```

Эти VM-тесты используют рабочий `MqttService` и fake внешнего клиента.
Они не проверяют TCP/TLS, согласование с настоящим broker или устройство.

## Key-value хранилище приложения

`AppStorage` сохраняет рабочие значения в `storage.json`, отдельно от
конфигурации `config.json` и выбора медиапровайдера. Отсутствующий файл даёт
пустую карту; повреждённый JSON, `null` и документ другого типа также
восстанавливаются как пустая карта. Ошибка файлового чтения или записи
передаётся вызывающему коду. `getValue<T>` сохраняет строгий тип; `getInt`
дополнительно читает прежнее строковое представление целого числа.

Первое изменение планирует одну запись через 10 секунд; последующие изменения
попадают в эту запись и не переносят срок. Явный `save()` отменяет таймер,
при отказе сохранения значения остаются в памяти для явного повтора.
Возврат прежних значений выполняется обычным `setValue`: другие изменения
и их общий таймер не отменяются. Если явная запись уже завершилась отказом,
`setValue` снова планирует сохранение восстановленных и остальных значений.
Ошибка фонового сохранения диагностируется и сохраняет значения в памяти;
новая правка или явный `save()` могут повторить запись. Ошибка явного
`save()` по-прежнему передаётся вызывающему коду.
Сбой питания и атомарная замена файла этим контрактом не покрываются.
Категория `AppStorage` сообщает начало/итог загрузки и сохранения, тип
отказа, исходное исключение и стек. Текст ошибки не маскируется; отдельного дампа JSON нет.
Проверки: `dart test --concurrency=1 test/app_storage_test.dart`.

## Сервисы и изоляты

### Провайдеры хранилищ

В `hw_frame.serviceMain` GetIt регистрирует
`registerFactoryParam<Storage, StorageType, void>`: аргумент `StorageType`
определяет создаваемую реализацию. `StorageProviderRegistry()` использует
`GetIt.instance`, читает выбранный Storage из применённого `AppConfig`
и получает экземпляры через `get<Storage>(param1: type)`.
Обычная фабрика создаёт новый объект при каждом вызове; реестр сохраняет
единственный экземпляр каждого типа и создаёт его только по необходимости.
`HardwareService` использует его выбранный Storage для показа,
а `DriveCommand` передаёт через `executeDriveCommand` по полю `provider`.
В координаторе нет типов, OAuth-сервиса, действий и ошибок Яндекса.

`CloudStorage` — абстрактный базовый класс поверх `DiskStorage`. Реализация принимает общий
`DriveCommand` и возвращает `DriveResult`; публичные состояния, авторизация,
папки и ошибки также используют модели `Drive*`. В JSON команда содержит
`type: "drive"`, обязательный `provider` из `StorageType` и `action`.
Отсутствующий или неизвестный provider отклоняется при декодировании;
неизвестное действие становится `DriveAction.unknown` и отклоняется
провайдером. Старого Yandex RPC и совместимых aliases нет.

Реестр вызывает `init()` **только у выбранного** Storage. Создание неактивного
облачного провайдера для OAuth или выбора папок не создаёт файловый индекс,
наблюдатель `images` и таймер синхронизации. `runtime.active` становится true
после успешного `init()`; ручная синхронизация и пауза до этого возвращают
`notActive`. Один экземпляр обслуживает и команды, и показ, если выбран он.

Реестр владеет всеми созданными экземплярами и освобождает каждый один раз,
включая неактивные. `HardwareService.dispose()` вызывает только освобождение
реестра, без отдельного закрытия выбранного Storage или OAuth-сервиса.
GetIt регистрирует фабрику создания, а не владеющие экземплярами singleton
регистрации; реестр не сбрасывает общий контейнер при завершении.
`YandexDriveStorage` владеет внутренним `YandexDriveService` и закрывает его
даже без предшествующего `init()`. Все провайдеры получают общий единственный
writer `AppStorage`; секреты остаются вне `AppConfig`.

### Индикация состояния хранилища

Каждый Storage имеет текущий `status` и поток `onStatusChanged` с общим
`StorageStatusEnum` из common: `download` — операция синхронизации,
`off` — ошибка или недоступность ресурса, `done` — завершение без ошибок.
Повторное значение не создаёт уведомления. Disk сообщает сканирование локального
каталога, отказ чтения и восстановление; его явный `sync()` повторяет сканирование.
Яндекс и Google сообщают собственную облачную синхронизацию. Локальный кеш
облачного Storage не подменяет статус текущей облачной операции. Частичный
отказ Яндекса или неподключённый выбранный аккаунт оставляет `off` после прохода;
следующий успешный проход возвращает `done`.
Прежние `onStartSync`/`onEndSync` и их контроллеры удалены: состояния и
подписки обслуживаются единственным `onStatusChanged`.

Общая Freezed/JSON-модель `ApplicationState` находится в common и включает
`hasInternet`, `isScreenOn`, `storageStatus`, `isMenu`, `isPaused`, `isMotion`.
Неизвестный `storageStatus` разбирается как `off`. ApplicationStateService
получает готовые ScreenService, GPIOService и выбранный Storage, сразу читает
его текущий статус и подписывается перед `init()` провайдера. Storage остаётся
владельцем своего состояния, агрегатор владеет только подпиской. В точке сборки
провайдер создаётся раньше агрегатора, HardwareService — после обоих; циклов нет.

Публикация изменений всех полей ApplicationState, включая Storage, использует
общий trailing debounce 500 мс: быстрые переходы могут объединиться в последнее
состояние. Этот агрегат используется MQTT и не передаётся во frontend.

HardwareService отдельно подписывается на выбранный Storage и передаёт его
начальный статус и последующие изменения через `StorageStatusCommand`.
Подписка сразу отправляет каждое уведомление через межизолятный RPC, без
очереди ожидания предыдущего подтверждения и без повторов; debounce ApplicationState
на этот канал не распространяется. Неактивные провайдеры не управляют
индикацией или агрегатом. FrontendService хранит только текущий `storageStatus`
и публикует его изменения в `onStorageStatusChanged`. SlideshowStatusBloc
сразу читает это значение при создании, затем слушает поток. Статус Storage
не изменяет меню и паузу и не создаёт обратного RPC.
Подписки освобождаются до закрытия провайдеров; закрытие потока Storage не ждёт
приостановленного наблюдателя.

В заголовке рамки зелёный значок скачивания остаётся видимым после мигания
до смены статуса. Красный значок означает `off`, белый отмечает успешное
завершение и скрывается после существующей анимации. Переходы логируют
`Storage` и `FrontendService` на INFO; публикацию снимков ApplicationStateService,
доставку HardwareService и применение SlideshowStatusBloc — на FINE.
Ошибки доставки — WARNING с безопасным типом.
Это события переходов состояния, а не уведомления о каждом файле.

`DiskStorage` владеет корнями `folder` и ненулевым `final Directory hidden`.
По умолчанию hidden вычисляется один раз как
`galleryStateDirectory(folder)/hidden`; явный аргумент конструктора позволяет
использовать другой каталог состояния. Само создание Storage не создаёт
каталоги. `mediaExists(relativePath)` проверяет файл относительно images
и hidden через максимум два `File.exists()`, без обхода сегментов в файловой
системе. Симлинки в пути допустимы; ссылка на существующий файл считается
его наличием, отсутствующий файл или каталог возвращают false. Проверка
корректности относительного пути выполняется в памяти.
Яндекс и Google используют этот общий контракт.

`CloudStorage.publishDownloadedMedia` принимает поток, создаёт временный файл
рядом с целевым, проверяет размер и доступные checksum, затем локально
переименовывает готовый файл. Метод возвращает `true` после публикации,
`false` при наличии файла в images/hidden; отказ передаётся безопасным
`CloudStorageException`. Начатое скачивание файла завершается вместе с проверкой
и локальной публикацией: пауза, отключение аккаунта и `release()` не прерывают
его. Они останавливают дальнейший импорт; `release()` ожидает текущий файл
и начатые запросы метаданных до закрытия принадлежащих Storage сетевых ресурсов.
Обход проверяет существующие состояния паузы, подключения аккаунта и закрытия
Storage перед следующим запросом или файлом. Отдельного токена остановки
синхронизации нет. Быстрые пауза и продолжение во время запроса позволяют
продолжить тот же проход. OAuth также использует состояние самой сессии:
отмена сразу устанавливает `cancelled` и останавливает таймеры. Текущий HTTP-запрос
завершается; после ответа проверяются текущая сессия, её статус и закрытие сервиса.
Отменённый или истёкший ответ не сохраняет credentials и не начинает следующий
шаг. Отдельного объекта отмены нет. Закрытие ожидает все начатые OAuth-запросы,
включая запросы прежних отменённых сессий.
`YandexDriveApi.download(token, remotePath)` и `resources(token, remotePath, offset)`
не принимают токен отмены; фиктивный токен внутри загрузчика также не создаётся.
Ошибки сети, ограничения приёма и отказ записи по-прежнему
завершают файл ошибкой. Временный файл очищается при пропуске или отказе.
Этот механизм общий для Яндекса и Google, callback публикации и межизолятного
RPC нет.

Облачная публикация не вызывает `GalleryCatalogService.markDirty` и не посылает
панели события для обновления списка. Пользователь сам обновляет галерею.
Существующий файловый watcher каталога только помечает backend-кеш устаревшим
для следующего запроса и не вызывает перерисовку открытого интерфейса.
`CloudStorage` пишет FINE для начала/итога публикации, пропуска и отказа
с безопасным кодом; на INFO нет записи для каждого медиафайла. Остановка
прохода диагностируется отдельно от успешной публикации текущего файла
и не считается ошибкой.

Доступ реестра к локатору согласован пользователем как исключение для владельца
ресурсов. Конструктор один — `StorageProviderRegistry()` без параметров.
В тестах регистрации изолируются через GetIt scopes и удаляются после проверки;
отдельной ветки конструктора для тестов нет.
Fixture временно отключает сырой отладочный вывод GetIt и восстанавливает
его настройку после закрытия scope: ожидаемые ошибки фабрик проверяются
через результат команды и безопасный logger реестра, без печати стека
`Error while creating Storage` в успешном прогоне.
Остальные рабочие сервисы по-прежнему получают готовые зависимости явно.
У `HardwareService` все зависимости — обязательные именованные параметры.

Логи `StorageProviderRegistry`: INFO для начала/итога инициализации и закрытия,
FINE для создания провайдера и маршрутизации команд, WARNING для отказов
с enum провайдера, исходной ошибкой, стеком и итоговыми счётчиками. Содержимое команды
целиком не дампится. Провайдер диагностирует
предметное действие и причину отказа. Добавление провайдера требует его
фабрики в точке сборки и реализации `CloudStorage`; `HardwareService`
от него не зависит. Google Photos наследует `CloudStorage` для локальной
публикации; новые команды управления аккаунтами пока возвращают явный отказ.

```sh
dart test --concurrency=1 test/storage_provider_registry_test.dart test/cloud_storage_hardware_test.dart test/cloud_storage_publication_test.dart test/yandex_drive_provider_commands_test.dart test/drive_rpc_test.dart
```

Входящий `Service.processing` журналирует тип команды, ID протокола и порт,
а не сериализованное тело. При отказе декодирования или исполнения в этом
общем слое сохраняются исходное исключение и полный стек. Текст исключения
может содержать payload и URL; он не маскируется. Рабочие сервисы добавляют тип действия,
код отказа и итоговые счётчики.

### Обнаружение доступной рамки

Web-isolate публикует `_dslideshow._tcp.local` через Avahi/D-Bus после
успешного HTTP bind. SRV содержит фактический TCP-порт, имя экземпляра
строится из системного hostname; конфликты имён разрешаются с Avahi.
При выключении доступа регистрация снимается, `alwaysEnabled` сохраняется.
Смена порта применяется после перезапуска рамки. Отдельные UUID, настройки
discovery и HTTP API не вводятся.

Нужны Avahi 0.8+ и системная D-Bus; DEB объявляет эти зависимости.
Отказ регистрации не останавливает HTTP и слайдшоу: остаётся ручной адрес.
После восстановления Avahi заново выключите/включите web-доступ на рамке
либо перезапустите рамку. Постоянного фонового retry нет.
Каждая регистрация и клиентская сессия поиска владеют своим соединением
D-Bus и закрывают его при завершении; управляющие вызовы имеют предел 3 секунды,
разрешение сервиса — 6 секунд, чтобы не опережать пятисекундный resolver Avahi.
Окно поиска клиента — 8 секунд; результаты отображаются по мере поступления.
`AvahiDiscovery` пишет безопасный тип/код отказа на WARNING,
успешное разрешение — на FINE. Отказ содержит исходное исключение и стек.

Logger `FramePublisher` пишет начало/итог публикации, порт, удаление и
безопасный тип отказа; детали конфликта имени — FINE. Ошибка на границе
WebService дополнительно отражается в его logger. Для службы используйте
`journalctl -u dslideshow --no-pager`. Поиск, сеть и авторизация описаны
в [руководстве панели](../doc/config-app.md#поиск-рамок-на-странице-входа).

### Рабочие сервисы

Сервис — обычный объект Dart; выделение класса или файла не создаёт isolate.
Существующие точки входа остаются прежними:

* `hw_frame.serviceMain` — backend-isolate с GPIO, MQTT, экраном, хранилищем,
  Wi-Fi и SystemInfo; он запускает web-isolate.
* `web_server.serviceMain` — HTTP/WebSocket и галерея.
* `ota.serviceMain` — обновления, запускается frontend отдельно от backend.

Глобальные `FrontendService`, `HardwareService`, `WebService` и `OTAService`
живут до завершения приложения/своего isolate. Владелец вызывает их
`dispose()`/`close()` один раз; отдельный Future для защиты от двойного
завершения не хранится. Отмена активных ожиданий, таймеров и подписок остаётся
частью штатного завершения, поздние результаты не публикуются в закрытые потоки.

Каждая генерация миниатюры запускает один процесс FFmpeg без новых Dart-isolates.
Выделение подписок, WebSocket-сессии и сборщика состояния не добавляет изолятов, таймеров, очередей
событий или сетевых клиентов.

## Локальные зависимости миниатюр

В PATH должен быть `ffmpeg` (Debian/Ubuntu: пакет `ffmpeg`).
Проверены FFmpeg 5.1.9 (Debian 12 и команда на RaPi arm64) и 8.0.1 (Linux x64).
Для другой сборки сначала выполните обязательные codec-тесты: набор демультиплексоров/кодеков и EXIF может отличаться.
Установка пакетов скриптами проекта не выполняется.

```sh
ffmpeg -version
# Из backend/; Python 3 нужен для процессных регрессионных тестов.
dart test test/ffmpeg_thumbnail_worker_test.dart test/thumbnail_service_test.dart test/gallery_http_test.dart test/gallery_config_test.dart --concurrency=1
```

Linux-проверки освобождения исходных файлов обходят `/proc/self/fd` без
следования по ссылкам: дескриптор может закрыться между перечислением и чтением
его ссылки. Ошибки чтения отдельной ссылки не срывают проверку; ошибка самого
обхода не превращается в пустой результат. Проверки timeout, завершения
дочернего процесса и отсутствия оставшихся открытых исходников сохраняются.

`FfmpegThumbnailWorker` запускает один FFmpeg на задачу, без новых Dart-isolates.
Для миниатюр `ffmpeg` обязателен, `ffprobe` не нужен; при отсутствии executable миниатюры дают
503, оригиналы остаются доступны. Слот удерживается до cleanup дочернего процесса.

Все размеры, качество, бюджеты и JSON заданы в едином
[руководстве галереи](../doc/gallery.md#настройки-gallery).
Подробное логирование web-isolate включается через `log.web = "ALL"` после
перезапуска; [категории и сбор лога](../doc/gallery.md#диагностика-на-рамке).
Несовместимость RGBA drawbox с FFmpeg 5.1 и проверка RGB-фона сохранены в
[отчёте](../benchmarks/reports/gallery-ffmpeg51-diagnostics-2026-10-27/report.md).

## Инструменты управления медиатекой

Галерея использует единый `GalleryMediaSection` (`published`, `hidden`, `trash`),
`GalleryEntry`, `GalleryCatalog` и ссылки `{section, mediaId, sourceRevision}`.
Чтение каталогов, оригиналов, metadata и миниатюр имеет общий маршрут с разделом;
resolver использует существующие индексы и проверяет один запрошенный файл.
Прежние маршруты удалены; контракт приведён в [руководстве API](../doc/gallery.md#api-и-инвалидация).

Индекс каталога строится и хранится в памяти. ID — SHA-256 относительного пути,
версия — хеш stat-полей и общей метки инвалидации. `serverId` отсутствует.
На диске остаётся только `catalog.epoch` размером 32 байта: обычный scan его
не меняет, `forceInvalidate` заменяет. `catalog.json` не используется.
ID и версии неизменённых файлов сохраняются после перезапуска; список файлов
не сериализуется на диск. Последние 64 ID обновлений помнятся только в памяти.

Версии оригиналов основаны на типе, размере, `mtime` и `ctime`. После загрузки,
поворота, переноса в корзину или восстановления web-isolate вызывает
`GalleryCatalogService.markDirty()`. Уведомление хранится только в памяти;
оно не теряется при завершении уже начатого scan. `GalleryPublication` и
`publication.version` удалены. Неизменённые файлы сохраняют свои миниатюры.
Внешние изменения обнаруживаются watcher/периодической stat-сверкой; Google
Photos в схеме уведомлений не учитывается. При совпадении всех stat-полей
нужна явная инвалидация кеша;
подробности — в [руководстве версий](../doc/gallery.md#api-и-инвалидация).

Коллекция фоторамки может содержать **50 000+ медиафайлов**; это штатный объём
для проектирования сервисов. Индексы каталога, ограниченные очереди и ленивые
миниатюры описаны в [руководстве больших коллекций](../doc/gallery.md#большие-коллекции-50-000-медиафайлов).
Лимиты кандидатов Czkawka, размера JSON каталога корзины и числа файлов в команде
считаются отдельно от общего размера библиотеки.
Диагностические сводки и безопасные ID — часть приёмки;
[категории и уровни логов управления](../doc/gallery.md#логи-управления-медиатекой).

Настроенный каталог `images` может быть симлинком, в том числе цепочкой
относительных ссылок для `bin/web_server_test.dart`. Файловые операции фиксируют
его канонический корень и проверяют дочерние пути внутри него; симлинки медиа
и вложенных папок по-прежнему отклоняются. После перенастройки ссылки корня
нужен новый экземпляр сервиса: прежний возвращает `revisionMismatch`
с безопасной диагностикой `reason=rootChanged`. Корзина находится в
`<gallery state>/trash` (обычно `images.gallery/trash`), а не рядом с целью
симлинка оригиналов.
Пересечение её физического дерева с оригиналами и перенос между разделами
не допускаются. Причины отказа вроде `symlinkSegment` и `rootOverlap`
попадают в ограниченные сводки без раскрытия реальных путей.

Корзина — обычное дерево с исходными относительными путями:
`images/album/photo.jpg` → `images.gallery/trash/album/photo.jpg`.
Соседние `thumbnails/` и `duplicates/` принадлежат своим сервисам; очистка
миниатюр не удаляет корзину. Удалять весь `images.gallery` как кеш нельзя.
Manifest, sidecar-файлы и результаты операций в ней не сохраняются.
Список и версии строятся из файловой системы. Перенос использует `File.rename`
без FFI: занятый при проверке путь возвращает конфликт. Проверка и перенос
выполняются отдельно; создание целевого файла внешним процессом между ними
может привести к его замене. Требования и ограничения — в
[руководстве корзины](../doc/gallery.md#корзина).

Сведения и физический поворот выполняются на backend, поиск дубликатов —
отдельным headless-процессом. При установке DEB `postinst` скачивает Czkawka CLI
12.0.2 ARM64 с проверкой SHA-256 и запуска; остальные инструменты задаются
зависимостями DEB. Для локальной разработки их нужно установить отдельно.
Нужные executable должны быть доступны службе через PATH:

| Назначение | Executable | Пакет Debian/Ubuntu |
| --- | --- | --- |
| Миниатюры и сведения о видео | `ffmpeg`, `ffprobe` | `ffmpeg` |
| Поворот JPEG без повторного сжатия | `jpegtran` | `libjpeg-progs` или `libjpeg-turbo-progs` |
| Сохранение прав доступа результата поворота | `chmod` | `coreutils`, базовый Essential-пакет Debian |
| Точные копии и похожие фотографии | `czkawka_cli` | ARM64 release 12.0.2 из `postinst`; для разработки — совместимый `czkawka-cli` или release binary |

DEB создаёт `/usr/local/bin/czkawka_cli`; служба systemd получает явный PATH
с `/opt/dslideshow/bin` первым. Интернет при установке, офлайн-повтор,
системные зависимости, отказ установки и диагностика описаны в
[README упаковки](../deb_factory/readme.md#установка-czkawka-cli-на-фоторамке).

Адаптер JSON явно принимает ветки Czkawka CLI **8.x и 12.x**. Неизвестная ветка
возвращает типизированный отказ `unsupported`; совпадение имени executable
само по себе не подтверждает контракт. Оба режима ожидают итоговый JSON после
завершения CLI. Для 8.x используются общие аргументы; вывод результатов
в stdout считывается и отбрасывается, служебный кеш изолирован во временном
каталоге задачи. Для 12.x дополнительно отключается кеш и печать результатов.
stderr и время процесса ограничены. JSON результата читается целиком через
`readAsString()` после завершения CLI и разбирается в worker-isolate;
лимиты `maxResultBytes` и `maxStateBytes` удалены. Временные JSON/кеш/конфигурация
удаляются после cleanup процесса. При отсутствии executable API возвращает
HTTP 503 с `GalleryErrorCode.unavailable`; для асинхронного поиска этот код
сохраняется в состоянии `failed` задачи.

Одинаковые наборы участников из точного и похожего режимов сводятся к одной
группе с приоритетом «Точных копий». Более широкие похожие группы сохраняются
отдельно. Нормализация применяется также при чтении `job.json`, без его
перезаписи; новые результаты сохраняются уже без повторных групп.

В похожем поиске явно передаётся `--image-filter Lanczos3`, чтобы уменьшение
до перцептивного хеша было устойчивее к исходному разрешению. Порог, размер
и алгоритм хеша остаются штатными параметрами CLI; точный режим не меняется.
В сводке запуска похожего режима виден безопасный `imageFilter=Lanczos3`.
Изменение применяется только к новым поискам после обновления backend;
сохранённый `job.json` не пересчитывается. Это не гарантия обнаружения любых
вариантов кадра: в Czkawka 12.0.1 две группы с несколькими одинаковыми копиями
разных перцептивных хешей могут оставаться раздельными. Подробнее — в
[руководстве поиска](../doc/gallery.md#поиск-и-сравнение-дубликатов).

Локальные реальные codec/CLI-регрессии проверяют Czkawka 8.0.0, 12.0.1 и 12.0.2,
FFmpeg 8.1.2, Dart `exif` 3.3.0 / `image` 4.12.0,
JPEG IJG 9f и libjpeg-turbo 3.1.3 на Linux x64.
Оба варианта `jpegtran` допустимы: проверка `jpegtran -version` не используется,
поскольку IJG 9f не поддерживает этот аргумент. Наличие команды и поддержка
`-perfect`, преобразований и `-copy all` проверяются настоящим поворотом.
Новая комбинация версий требует тех же проверок качества, EXIF/ICC и cleanup.

```sh
command -v ffmpeg ffprobe jpegtran chmod czkawka_cli
czkawka_cli --version
# Из backend/; Python 3 нужен для управляемых процессных отказов.
dart test --concurrency=1 test/gallery_tool_runner_test.dart \
  test/gallery_media_tools_test.dart test/gallery_duplicate_cli_test.dart
# Только real CLI-тест допускает отдельный абсолютный путь для проверки адаптера:
CZKAWKA_CLI=/absolute/path/to/czkawka_cli dart test test/gallery_duplicate_cli_test.dart
```

EXIF и сведения изображений читаются в Dart пакетом `exif`; разрешение
берётся из заголовков JPEG/PNG/WebP/GIF, ICC — из контейнера. PNG поворачивается
пакетом `image` в отдельном worker-isolate с обновлением EXIF Orientation
и размеров. ExifTool не входит в runtime-зависимости. Политика сохранения
метаданных JPEG/PNG различается: JPEG оставляет результат `jpegtran -copy all`,
а изменение прочитанных пакетом `exif` тегов даёт безопасный WARNING без
возврата исходных EXIF-блоков. Проверки формата/геометрии/ICC остаются.
Подробности — в
[руководстве поворота](../doc/gallery.md#поворот-оригинала).

Отсутствие инструмента в настоящем codec/CLI-тесте — явная ошибка prerequisite,
а не пропущенный сценарий. VM-тесты проверяют локальные файлы и процессы;
они не подтверждают ARM64 ABI, нагрузку слайдшоу или производительность RaPi.
Установщик DEB проверяет запуск закреплённой ARM64-сборки на текущей ОС рамки;
это не заменяет проверку поиска на устройстве. Подключать unstable-репозиторий
или обновлять ОС ради утилиты не требуется. Политика Depends и загрузки
описана в [README упаковки](../deb_factory/readme.md).

## Границы ответственности

| Класс | Ответственность и владелец |
| --- | --- |
| `HardwareService` | RPC-обработчики, готовность сервисов и отправка уведомлений Storage/экрана из подписок. Создаёт `DeviceEventBindings`, принимает готовый `FrameStateReader` через конструктор и освобождает сервисы. |
| `DeviceEventBindings` | Подписки на кнопки/присутствие GPIO, подготовку видимости экрана и команды MQTT. Живёт в том же backend-isolate; вызывает переданные обработчики и существующий `ScreenService`. |
| `FrameStateReader` | Сбор `FrameState` из frontend, наблюдений `ApplicationStateService` и текущего состояния `ScreenService`. Каждый вызов читает frontend через обычный межизолятный RPC; собственных ресурсов, кеша и состояния жизненного цикла нет. |
| `WebService` | HTTP-сервер, маршруты, сервисы галереи и список активных WebSocket-пользователей. Создаёт `WebSocketUser` на каждое соединение. |
| `WebSocketUser` | Авторизация, кодирование сообщений, config-команды, RPC proxy и ожидающие ответы одного соединения. Реализация находится в `lib/src/web_server/web_socket_user.dart`. |

`DeviceEventBindings` подключает потоки в прежнем порядке: кнопки GPIO,
подготовка экрана, присутствие GPIO, MQTT pause, screen и menu. Значения pause
и menu передаются без преобразования; screen сохраняет инверсию значения,
которую ожидает frontend-действие `SlideshowAction.toggleScreen`. Поля кнопки
передаются без изменений. Категория и сообщения логирования сохранены.

`HardwareService.dispose()` ожидает отмену всех этих подписок перед освобождением
`ApplicationStateService`, экрана, GPIO, Storage, SystemInfo, Wi-Fi и MQTT.
Уведомления Storage и
экрана отправляются непосредственно из подписок, без цепочек `Future`: ответ
предыдущего RPC не задерживает следующий. Закрытие не ждёт уже отправленные
уведомления; их поздние ответы и ошибки обрабатываются без новых отправок.
Владелец вызывает завершение один раз. Сам `DeviceEventBindings` владеет только подписками:
он не закрывает внедрённые сервисы и не ожидает уже отправленные RPC.
Состояние и переходы экрана остаются в `ScreenService`, current/next — в Storage.
Подробнее: [сон экрана и присутствие](../doc/screen-presence.md).

### Снимок состояния рамки

`FrameStateReader` находится в `lib/src/service/hardware/src/frame_state_reader.dart`
и работает в существующем backend-isolate. `HardwareService` делегирует ему сбор
снимка для `GetFrameStateCommand` и после подтверждения `SetFrameControlCommand`.
Управление, RPC id и формирование ответов/ошибок остаются в фасаде.
В точке сборки `hw_frame` сервис-локатор регистрирует готовый Reader как singleton
и передаёт его в конструктор HardwareService. Порядок зависимостей:
Screen/GPIO/выбранный Storage → ApplicationStateService → FrameStateReader →
HardwareService. Reader получает frontend RPC, ScreenService и ApplicationStateService
через конструктор; обратных callbacks в HardwareService и циклов DI нет.
Поля присутствия, питания, блокировки и фазы экрана читаются после ожидания
frontend; время снимка задаётся в UTC. Системные метрики остаются в SystemInfo.

Каждое чтение отправляет собственный запрос состояния frontend и ждёт его
результата или ошибки. Межизолятный RPC надёжен по контракту проекта: локальных
таймаутов, дополнительных Completer, кеша незавершённого запроса и восстановления
после предполагаемого зависания нет. Ошибка чтения оставляет `frontend: null`
в снимке с доступными сведениями backend; ошибка управления возвращается клиенту
с исходным RPC id. Команды автоматически не повторяются.

После подтверждения команды управления HardwareService запрашивает новый снимок.
Уже начатые опросы завершаются со своими результатами и не подменяют новое чтение.
Проверка жизненного цикла принадлежит HardwareService: после ответа RPC закрытый
сервис отклоняет снимок или не начинает следующую фазу управления. Закрытие не
ждёт внешний RPC и не создаёт для него искусственный ответ. Reader не владеет
ресурсами и не требует `dispose()`.

Категория `FrameStateReader` пишет недоступность frontend с безопасным типом
ошибки на FINE. `HardwareService` пишет начало и подтверждение управления на FINE,
тип отказа на WARNING; завершение запросов при закрытии — на FINE.
Исходные исключения транспорта и стек передаются в эти логи.

### WebSocket-сессии

Для совместимости `web_service.dart` повторно экспортирует `WebSocketUser` и
`WebSocketUserStatus`. Новый код может импортировать файл сессии напрямую.
Wire-формат, задержка авторизации, обработка ошибок, config/RPC-команды и
отключение пользователей при остановке HTTP-сервера сохраняются. Перенос
не меняет существующую политику таймаутов и очистки WebSocket pending-запросов.

## Реестр RPC-сериализаторов

Единственный список передаваемых типов находится в `lib/serializers.dart`:
`@RpcSerializers([...])` над `final Serializers serializers = _$serializers`.
Аннотация и runtime-интерфейс объявлены в `common/lib/serializers.dart`.
Отдельный пакет `rpc_serializers_generator`, соседний с backend, подключён
как path-зависимость в `dev_dependencies`. Он создаёт `lib/serializers.g.dart`
через обычный `dart run build_runner build` из `backend/`. В watch-режиме
используется `dart run build_runner watch` или `./generate_models.sh`.
Генерируемый файл хранится в Git; редактировать его вручную не нужно.

Классовые `fromJson`/`toJson` по-прежнему создают json_serializable/Freezed.
Новый builder генерирует только их регистрацию, сохраняя 57 прежних типов,
формат `["EchoCommand", {"id": 7, "text": "hi", "type": "echo"}]`, порядок
проверок, обработку неизвестных типов и прежнее поведение декодирования.
Имя класса становится строкой при генерации; `Type.toString()` и рефлексия
во время выполнения не используются. Переименование класса меняет wire tag.
Isolate, транспорт и вызовы потребителей реестра не изменяются.

Старый `bin/gen_serializers.dart` удалён: он содержал второй, неполный список
и мог перезаписать актуальные регистрации. Добавляйте тип только в аннотацию
и запускайте build_runner. Диагностика дублей, требования к моделям, пример
подключения и тесты builder описаны в [README генератора](../rpc_serializers_generator/README.md).

Обнаружение забытых типов и полнота тестового охвата отложены:
[три уровня будущей статической проверки](../doc/plans/rpc-contract-coverage-plan.md).

## Локальные проверки

[Ответственность тестов сериализации/OTA и быстрые команды](../doc/testing.md).

Из каталога `backend/`, без обновления зависимостей:

```bash
dart analyze
dart test --concurrency=1
dart test --concurrency=1 test/device_event_bindings_test.dart test/hardware_screen_test.dart \
  test/frame_state_reader_test.dart test/frame_state_test.dart test/web_socket_user_test.dart \
  test/web_socket_config_test.dart
```

Для HTTP-регрессий нужны разрешённые локальные сокеты. Тесты подписок используют
управляемые потоки и подменяемое питание: проверяют передачу кнопок/MQTT,
присутствие, порядок уведомлений, отмену ожидающих событий и завершение cleanup.
WebSocket-тесты проверяют авторизацию, echo, proxy RPC, config, корреляцию ответов
и явное отключение через существующий сериализатор. Дополнительно настоящий
локальный HTTP/WebSocket проверяет подключение через маршрут `WebService` и
отключение сессии при закрытии сервера. Физические GPIO, MQTT broker, DPMS
и питание экрана локально не проверяются.

Тесты `FrameStateReader` проверяют поля снимка, все фазы экрана, независимые
чтения без кеша и отказы frontend. Интеграционные RPC-тесты дополнительно
проверяют ожидание результата без локального timeout, чтение после управления,
старый ответ во время нового запроса, сохранение входных RPC id и закрытие
во время обеих фаз управления.
Проверки этого этапа по решению пользователя выполняются только локально.
Синтетическая локальная AOT-проба выделения WebSocketUser/DeviceEventBindings
проверяла по 300 000 входных событий и 50 000 echo в процессе, FD 8→8;
одноразовый комплект удалён при очистке 29.10.2026. Это датированное наблюдение,
не подтверждение текущей аппаратной производительности. Действующее покрытие
сохраняется в backend tests; числа старых тестовых прогонов не являются приёмкой
нового кода.

Правила аппаратных запусков и восстановления службы — в
[руководстве RaPi5](../doc/raspberry-pi-benchmarks.md), инструменты измерений —
только в [benchmarks](../benchmarks/README.md).
