# Галерея: проверка реализации 26.10.2026

Это локальные наблюдения Linux AOT HTTP и настоящего Chrome BrowserClient. RaPi5, Wi-Fi, прокрутка Flutter UI, FPS и аппаратная приёмка не выполнялись.

Основное A/B: `baseline` → `candidate-accepted`. Архивы прочих промежуточных вариантов сохранены и не смешиваются с этой таблицей. [Машинная сводка](comparison.json) сохраняет сравнение и отдельные значения CPU/RSS/FD.

## Условия и воспроизводимость

Baseline заморожен из HEAD `239fa81f2ea1bac73e67f43df4577d064c6f6ea9` до production-правок: `baseline/source.tar`, `sources/`, исходные package configs, SHA256 manifest и provenance. Candidate сохраняет текущие backend/common, pubspec/lock и переписанный absolute package config в собственном каталоге. SDK и существующий pub cache не включены в архивы; AOT binaries сохранены.

На момент отчёта production `backend/lib` и `common/lib` совпадают с candidate; после freeze вне этого прогона изменился только `backend/pubspec.yaml` (версия 10.2.0+3 → 11.0.0). Чужая правка сохранена, повторный freeze ради версии не делался.

Один и тот же server harness SHA256 `7cd59ee27fc86094233616ba978a1a57ac113e7a30e67dbf4e150cf3ede150d9` и Python runner `6f833099cf3eb45e206592e54ec9010b5a524b7a317c884ce8f6bd6e43583fbe` применены к обеим версиям. Dart: `Dart SDK version: 3.13.5 (stable) (Tue Sep 29 01:00:52 2026 -0700) on "linux_x64"`. Report generator проверяет совпадение harness/runner/SDK, матрицы, исходных manifest и AOT hashes.

По три свежих процесса на 1k/10k отдельных пустых JPG плюс три встроенных декодируемых JPEG fixtures `photo_a.jpg`, `photo_b.jpg`, `photo_large.jpg`. Пустые файлы проверяют только метаданные и никогда не передаются декодеру. Непустые встроенные JPEG копируются без изменений; SHA256/размеры сохранены в каждом `raw.json`. `photo_large.jpg` — синтетический fixture 8000×6000, 10 192 467 байт. Эти файлы не заменяют реальную фототеку с разнообразными EXIF/ICC/форматами. Файловый кеш ОС прогрет созданием/копированием, не сбрасывается.

HTTP server — реальный WebService.handler через shelf на 127.0.0.1 в отдельном процессе; benchmark-only wrapper наблюдает body bytes, overlap, EOF/cancel и event-loop lateness. Тёплые grid и original-control используют 12 запросов на concurrency 1/4/10; Python клиенты читают по 64 KiB с паузой 1 мс. Холодный проход — три JPEG при concurrency=1 без искусственной паузы чтения. Baseline grid получает оригиналы; candidate grid — отдельные versioned миниатюры 256 px. Original-control в candidate получает оригиналы с revision URL. Контроль полноты списка и точного количества оригинальных байтов обязателен.

«Cold» ниже означает отсутствие backend derivative cache при новом процессе/fixture. «Warm» — готовые backend derivatives; HTTP/browser/client disk cache в A/B не эмулируется. Время CPU относится к серверному процессу со всеми его isolate threads. RSS — периодически наблюдавшийся максимум, не строгий пик и не доказательство утечки. Порядок сценариев одинаков; host остаётся общей рабочей машиной, не изолированным стендом.

Оригиналы передают прежнее число байтов. Для двенадцати tile-запросов три фото в данной выборке дают 76 382 932 → 456 208 байт (примерно 167× меньше). Это измеренный эффект размера производных, не установленный предел RPS shelf. Холодное создание миниатюр стоит CPU/времени; цифры тёплого кеша его не скрывают.

При списке 10k медиана trial-p95 `/info`: 44.487 → 1.558 мс. Полное время списка сопоставимо: асинхронный обход прежде всего снимает блокировку event loop. Первое построение v2 catalog измеряется отдельно в `raw.json/list_catalog`; у 10k оно занимает порядка секунды на этом host. Пагинация/инкрементальный индекс здесь не объявляются проверенными.

В каждом основном варианте 54 группы, HTTP и `/info` ошибок нет. В 18 условных tile GET candidate получены 304/0 байт; baseline возвращает 200/оригинал. Четыре socket-cancel по sparse-файлу 64 MiB дают четыре отмены source и возвращают active body/handler к нулю. Клиент читает 262 144 байта суммарно; backend может прочитать больше из-за буферизации TCP. Мгновенный backend overlap при отмене может кратко превышать число client slots до доставки disconnect; это не скрывается и не подменяется нулями.

RSS улучшение не доказано: candidate включает каталог и decoder worker, а наблюдавшиеся максимумы зависят от истории GC и стадии. Подробные CPU/RSS/FD/threads, RPS, body counts и timestamps находятся в raw/summary.

## Настоящий браузер

[`browser-accepted-wire/result.json`](browser-accepted-wire/result.json): 6 сценариев, passed=True. Используются установленный Chrome, две controlled loopback origins и actual frozen WebService AOT для отдельной проверки production CORS. Profile в /tmp, без установки браузера.

Проверены реальный peak=2 и дедупликация/тёплый encoded hit; изменение revision создаёт новый request. AbortableRequest до headers приводит к disconnect без тела. При отмене во время 32 MiB body сервер заканчивает раньше полного тела, loader освобождает active/pending/byte reservations. Проверены браузерные OPTIONS preflight, If-None-Match/304, Range/206, HEAD, exposed validator/range headers и отклонение ответа без CORS. Дополнительный сценарий делает GET/HEAD/304/Range именно к production WebService через другую origin. Это не Flutter scroll/визуальная проверка.

Для production Range и HEAD используются отдельные query URL, исключающие синтез ответа из HTTP-кеша Chrome после GET. Server body observer отдельно подтверждает 206/3 байта, 304/0 байт и 200/0 байт для HEAD. Ранее сохранённый `browser-accepted-direct` не завершился из-за гонки удаления временного Chrome profile; он не засчитан как PASS. Стенд повторяет только удаление профиля, не тестовые сценарии.

Provenance браузера содержит immutable production loader copy, package config, compiled JS hashes и Chrome version. Контролируемые body fixtures не декодируются как изображения.

## Исторические команды и повторение

Команды этого отчёта относились к сохранённому окружению 26.10.2026.
Генератор `gallery_http_report.py` и его зависимость `gallery_http.py` сохранены
в [архиве инструментов](archive-support/gallery-http-report-tools.tar.gz)
с manifest и SHA256; удалённые диагностические/browser entrypoints не являются
частью действующего инструментария. Для чтения достаточно этого Markdown,
`comparison.json` и исходных результатов. После очистки крупные распакованные
копии читаются из сохранённых архивов, см. [индекс](../README.md).

Новый HTTP-прогон выполняется по [текущему README стенда](../../README.md)
в отдельный experiment directory, с новыми baseline/candidate. Повтор браузерной
проверки требует отдельного согласия пользователя; очистка его не выполняла.

Loopback/Chrome и Flutter SDK lockfile требуют соответствующего разрешения sandbox. Первоначальные compiler telemetry и socket-denial диагностики сохранены отдельно; окончательные raw/compile logs относятся к указанным вариантам. Native encoded cache проверен 17 regression cases, включая atomic publication, отмену/close, LRU/reopen, pins через замену и eviction, transient oversized cleanup, corruption miss и настоящий FileImage→DecodePool first-frame при нулевых cache budgets. Дополнительно проверены внешний fcntl lock, overlapping handles/pinned close, worker-isolate memory fallback и failed-init recovery. Default disk каталог — `getApplicationCacheDirectory()/gallery-encoded-v1`; владение получает только root UI isolate через неблокирующий `.owner.lock`. При занятости/ошибке используется memory LRU 24 MiB/128 objects (disk LRU 128 MiB/512). Shared store держит lock до конца процесса; standalone close — до освобождения всех payload pins и cleanup. Неуспешная инициализация останавливает sweeps до unlock. Первый full frontend suite выявил зависимость одного concurrent test от порядка публикации; fixture исправлен явным remove перед проверкой последнего release, production не менялся. Остальные backend/common/frontend regressions и Web build перечислены в основном руководстве.

## Не выполнено

RaPi5, Wi-Fi, Web/Linux scroll UX на коллекции реальных больших фото, UI frame timings/клиентская память, смешанная коллекция с работающим видео, несколько реальных клиентов, полноценная RPC-нагрузка и аппаратное A/B. 50k entries входят в предыдущее исследование списка, но не в эту итоговую HTTP матрицу. Следующий прогон и критерии перечислены в [руководстве](../../../doc/gallery.md); он не запускается автоматически. Здесь не заявляется аппаратно подтверждённая плавность/оптимизация.

## Последующая LAN-диагностика клиента 26.10.2026

Эти наблюдения перенесены из рабочего руководства при аудите 29.10.2026.
Они относятся к отдельным последующим сборкам/кешам и не смешиваются с
таблицей frozen baseline/candidate выше. Полный UI FrameTiming и аппаратная
приёмка остаются открыты; [текущие критерии](../../../doc/gallery.md#открытая-приёмка).

### Повторный показ в Linux-клиенте

Диагностика подключения к `192.168.50.143` 26 октября сохранена в
[LAN-замерах](../gallery-live-2026-10-26/lan-warm.json) и
[наблюдениях Linux-клиента](../gallery-live-2026-10-26/client-warm.json).
Каталог содержал 2530 записей; готовые миниатюры 256 px приходили по LAN за
14–33 мс в ограниченной выборке. У проверенных 48 запросов были попадания в
native index и соответствующие FileImage paths в decoded cache. В ходе наблюдения
клиент работал в debug, DPR 1; одновременных лишних scopes и flood refresh не было.

Прежний native hit ожидал перезапись metadata с `flush:true` в общей очереди.
Эта запись убрана из пути показа. На замороженном локальном probe из 63 hits
медиана времени составила 43,272 → 18,224 мс, изменений metadata — 63 → 0.
[Отчёт и before/after](../gallery-native-cache-warm-2026-10-26/report.md)
отделяют Flutter VM test во временном каталоге от настоящего UI и его filesystem.
Наблюдаемый интервал между timestamp metadata не называется измерением длительности
отдельного `fsync`. Увеличение серверного кеша до 512 MiB / 2048 объектов —
отдельная правка; она начинает действовать после обновления backend фоторамки.

### Первое получение новых миниатюр в Linux

[Ограниченный cold/warm LAN-прогон](../gallery-live-2026-10-26/lan-cold.json)
проверил шесть JPEG-источников размером около 700 kB, чьи производные 256 px
отсутствовали в индексе рамки перед запросом. Последовательные cold-ответы заняли
183–650 мс, три одновременных — 186–489 мс; повтор тех же запросов — 10–14 мс.
Почти всё время холодного ответа прошло до первого байта. Оно включает очередь,
генерацию и публикацию на сервере, а не только CPU декодера. Служба и исходные
фото не изменялись; запрошенные производные создавались обычным endpoint.

Отдельно native-кеш Linux был заполнен до 512 объектов при 13,4 MiB данных,
значительно ниже прежнего ограничения 128 MiB. Поэтому увеличение только
серверного лимита не предотвращало вытеснение миниатюр из клиента. Теперь оба
дисковых кеша допускают 2048 объектов / 512 MiB. Новые значения действуют для
вновь созданного кеша после перезапуска панели; backend обновляется отдельно.

Cold native probe использует 63 одинаковых JPEG по 30 955 байт, четыре
одновременные записи и пять свежих каталогов на файловой системе работающего
Linux-клиента. В Flutter VM медиана записи серии составила 6,729 → 0,072 с.
Проверяются немедленная доступность полных байтов, отсутствие staging-файлов и
попадания после повторного открытия. Сеть, декодирование и UI в этот замер не
входят. [Исходные данные и сравнение](../gallery-native-cache-cold-2026-10-26/report.md)
сохраняются отдельно от warm-прогона.

В [отдельном Linux release A/B](../gallery-native-cache-cold-2026-10-26/linux-release-report.md)
на том же компьютере медиана такой серии составила 8,273 → 0,476 с (пять свежих
каталогов на вариант). Сохранены обе AOT-сборки, параметры и хеши. Engine работал
в отдельном Xvfb с software rendering; измерялась только запись файлов, без сети,
декодирования и времени показа UI. Эти числа не смешиваются с Flutter VM выше
и не означают ускорение всей галереи в том же отношении.
