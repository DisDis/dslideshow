## Что установлено

| Участок | Фактическое поведение | Значение для проблемы |
| --- | --- | --- |
| Сетка | `SliverGrid` лениво строит ячейки шириной до 200 logical px, включая область вокруг viewport | Виртуализация уже есть. Построение плитки не означает, что она сейчас видима |
| Фото | `ImageGridItem` запрашивает тот же оригинальный URL, что полноэкранный просмотр | Маленькая плитка загружает большой файл; серверного thumbnail API нет |
| Linux | `flutter_cache_manager` уже имеет FIFO, single-flight по ключу и предел 10 активных image fetch на default manager | Нельзя утверждать, что параллельность совсем не ограничена. Очередь не учитывает viewport и не удаляет устаревшие задачи |
| Web | Default `HtmlImage` идёт через `ui_web.createImageCodecFromUrl`, обходя файловый CacheManager | Linux-лимит 10 и его дисковый кеш здесь не действуют. Остаются Flutter ImageCache и HTTP-кеш браузера |
| Исчезновение фото | Текущая цепочка CachedNetworkImage не предоставляет реального abort запроса при dispose плитки | Ушедшие с экрана оригиналы могут продолжать загружаться и занимать очередь |
| Rebuild | Ключи image provider сравниваются по URL/cacheKey, scale и размерам; ImageCache объединяет pending/completed загрузки | Создание `GalleryItem` при build само по себе не доказывает повторный HTTP |
| GET файла | `existsSync`, два `statSync`, затем поток `File.openRead` | Сервер передаёт оригинал без уменьшения; целиком в RAM backend его не буферизует |
| HTTP-кеш | Уже есть `Last-Modified` и `Cache-Control: public, max-age=604800`; нет ETag и обработки условных запросов | Свежие копии могут не обращаться к серверу, но revalidation сейчас возвращает полное тело |
| Замена файла | Upload атомарно публикует новый файл по прежнему пути; URL остаётся тем же | Свежий недельный кеш может показывать старый файл |
| Список | HTTP `/list` использует рекурсивный `listSync` и ручную сборку всего JSON | Он блокирует web-isolate; ранее ускоренный `DiskStorage` — другой путь |
| Видео | Плитка создаёт плеер только по нажатию; fullscreen — автоматически | Просто появление новых видеоплиток сейчас не создаёт загрузку видео. Активные плееры используют отдельный сетевой путь |

Основные исходники: [сетка](../../../config_app/lib/features/gallery/presentation/widgets/gallery_widget.dart),

Дополнительные воспроизведённые ошибки HTTP-пути: список включает каталоги и
`.part`, имя с кавычкой ломает JSON; `bytes=99-` для файла из десяти байтов
возвращает полное тело вместо 416; `If-Range` игнорируется. Это реальные
пограничные ошибки, но их вклад в наблюдаемое торможение не измерен.
Несколько диапазонов сейчас игнорируются с полным 200 — это отдельное
зафиксированное поведение, а не доказательство перегрузки.

Список клиента загружается целиком без timeout/отмены/pagination. `GalleryBloc`
пока не переводит исключение загрузки в имеющийся `ErrorGalleryState` и не
защищает результат от более позднего refresh. Повторные load-события могут
выполняться конкурентно. Это необходимо учесть при изменении lifecycle.

## Что подтверждают локальные пробы

Использованы настоящие `WebService.handler`, Dart 3.13.5, локальный Linux x64,
без аппаратных сервисов. Список измерялся в AOT, без HTTP-транспорта, на пустых
файлах с расширением JPG после создания fixtures: файловый кеш ОС не очищался.
Для каждого размера три последовательных повтора в одном процессе.

| Файлов | Handler, медиана | Диапазон | Опоздание таймера, назначенного через 1 мс |
| --- | ---: | ---: | ---: |
| 1 000 | 4,28 мс | 3,83–5,32 мс | 2,94–4,47 мс |
| 10 000 | 40,57 мс | 40,41–41,68 мс | 39,72–40,81 мс |
| 50 000 | 241,19 мс | 229,10–327,32 мс | 228,84–327,28 мс |

Обработка списка задерживает выполнение других событий того же isolate.
Это не замер WebSocket/RPC на устройстве и не p95/p99. Ускорение обхода списка
само по себе не уменьшит тела фото при прокрутке уже открытой галереи.

GET `photo_large.jpg` из встроенных медиа вернул все **10 192 467 байт** исходника
8000×6000. Это подсчёт тела handler, а не замер фактических браузерных байтов:
browser cache hit может вообще исключить передачу. `If-Modified-Since` с текущей
датой и `If-None-Match: *` на тестовом файле вернули 200 и полное тело.

Отдельно проверен настоящий локальный TCP-разрыв: клиент закрыл соединение
после первого chunk ответа на файл 64 МиБ. В финальном AOT-прогоне backend
прочёл 192 КиБ (в предыдущих — 256 КиБ), подписка
на источник была отменена, открытых FD этого файла после отмены не осталось.
Следовательно, текущий shelf/Dart IO путь способен остановить чтение при
реальном разрыве. Эта проверка не подтверждает, что Flutter-плитка вызывает
такой разрыв, и не заменяет проверку на Pi.

Фиксированного ограничения shelf в запросах/сек не обнаружено. `backlog: 32`
в запуске сервера — очередь ещё не принятых соединений ОС, не лимит RPS.
По коду shelf запросы обрабатываются конкурентно, тело передаётся `addStream`.

## Причины и оставшиеся гипотезы

Самый обоснованный первый объект оптимизации — большие оригиналы для плиток
в сочетании с работой, устаревшей после прокрутки. Это следует из кода и
контрактных проб, но доминирующую причину на RaPi5 ещё предстоит измерить.
Возможны одновременно несколько ограничений:

* Wi-Fi и суммарные байты, медленный накопитель, конкуренция чтений и FD;
* синхронные metadata/list операции и доступность web-isolate для RPC;
* декодирование и память клиента. Один RGBA-буфер 8000×6000 занимает около
  183 МиБ, до дополнительных копий и кешей; это расчёт, не измеренный RSS;
* возврат к уже просмотренным плиткам после eviction и повторная загрузка
  после изменения auth-code/URL;
* активное видео, refresh списка и несколько клиентов одновременно.

Пока не сняты реальные RPS/параллельность, браузерные cache hits/повторы,
CPU/I/O/FD backend и клиентский frame time. Поэтому конкретный «безопасный
лимит запросов» и обещание плавной прокрутки сейчас были бы предположением.

## Сравнение вариантов

| Вариант | Состав | Плюсы | Ограничения |
| --- | --- | --- | --- |
| A: управление текущими оригиналами | Общая очередь с приоритетом viewport, реальный abort, дедупликация, ограниченный prefetch; исправление HTTP-кеша и асинхронного списка | Быстрее ограничивает лишнюю работу; нет серверного декодирования | Каждый холодный полезный запрос всё ещё передаёт большой оригинал и требует декодирования на клиенте |
| B: очередь и ленивые миниатюры **(рекомендуется)** | A + versioned thumbnail API, конечная очередь генерации, single-flight, дисковый LRU с бюджетом | Уменьшает полезные сетевые тела и клиентский decode; готовит только нужную часть коллекции | Холодный miss требует тяжёлого decode на Pi; нужны отдельные worker/лимиты, инвалидация и обработка ошибок |
| C: предварительная подготовка | B + подготовка миниатюр при ingest и низкоприоритетный проход существующей коллекции | После подготовки мало холодных thumbnail miss, предсказуемее скролл | Стоимость всей коллекции по CPU/I/O/диску, миграция/прерывание/resume. Нельзя делать полный eager-проход при каждом открытии галереи |

Начать с B, а фоновую подготовку C добавлять по результатам холодных прогонов.
Новые uploads можно ставить в ту же низкоприоритетную очередь после публикации,
не задерживая успешный upload декодированием. Для существующей библиотеки —
lazy first; явный фоновый проход обсуждать отдельно с учётом работы фоторамки.

Reverse proxy/static server не уменьшит оригиналы и не устранит устаревшую
клиентскую очередь. Рассматривать его только если после B профиль покажет
издержки Dart-передачи готовых файлов при прочих равных. Установку nginx или
смену сервера сейчас ничто не обосновывает. Транзитивный `shelf_static` можно
сравнить как HTTP-helper, но он также не решает revision, авторизацию, общие
лимиты, `If-Range` и согласованность stat/open автоматически.
